# P2 — 移行計画とパリティゲート

**前提**: [P1-architecture.md](P1-architecture.md) の層構造、[S5-verification.md](S5-verification.md) の検証仕様、
[S3-data-migration.md](S3-data-migration.md) の移行仕様。
**原則**: R1（データ連続）/ R3（数値パリティゲート）/ R4（旧系を止めない）。

## 1. 計画を規定する 3 つの制約

診断で判明した制約が、着手順序を**選択の余地なく**決めている。

### 制約 1: パリティ検証は暦時間に律速される（最重要）

G-05 の実測: **信号レベルで 30 日を再生できる台帳が存在しない**。
`sensor_observation_ts` は TTL 24h、30 日以上を持つのは post-scoring aggregate のみ。

つまり **「retention を延ばした日」から数えて 30 日経つまで、パリティゲートは物理的に実行できない**。
コストを度外視しても、この待ち時間は買えない。

> **帰結: retention 延長は本プログラムの最初の作業**であり、他のすべてに先行する。
> 実装が 1 日目に始まろうと 60 日目に始まろうと、cutover 可能日は「retention 延長 + 30 日」より前には来ない。

### 制約 2: パリティの前提条件が現行系に無い

- **F-05**: 採点ティックが非冪等（Z-score 算出が走行統計を書き換える）→ 同一入力でも再現しない
- **A-01**: 旧系の採点は GET ハンドラ駆動 → 「旧系側で replay を回す」こと自体が自明でない
- **G-06**: replay スクリプト群は既に削除済、`conclusion_diff_log` も drop 済 → 並走装置はゼロから

> **帰結**: パリティハーネスは「旧系の既存機構を使う」のではなく、
> **両系を同一の観測台帳から駆動する**設計にする（§4）。

### 制約 3: v3 自身が新しい沈黙失敗を作りうる

今回 7 件の沈黙失敗（F-02/F-06/F-08/F-09/G-02/G-07/G-15）が見つかったが、
それらは**すべて「作った時は正しく動いていた」もの**である。v3 が同じ轍を踏まない保証は無い。

> **帰結**: L5（自己検証層）は v3 の一部としてではなく、**先に、現行系に対して**作る。
> 現行系の既知 7 件を検出できることをもって L5 の正しさを検証する（§3 Phase 1）。

## 2. オーナー裁定事項（cutover 条件の確定に先立つ）

以下は **P2 の数値を左右する**ため、実装着手前に裁定が要る。各項に現時点の推奨を付す。

| # | 論点 | 推奨 | 理由 |
|---|---|---|---|
| **1** | **TL1 がドメイン数を要求しない**（TL2 は 2 ドメイン必須なのに上位の TL1 は単一ドメインで発火。ACCIDENTAL A6） | **現行式を維持し、v3 でも変えない** | パリティ検証中に式を変えると「差分が改善か劣化か」を判定できなくなる。式の是非は cutover **後**に、L5 の発火統計を見ながら別途裁定する。ただし NP2 との逆転は S5 の監視項目に載せる |
| **2** | **retention 拡大の容量**（信号 60 日 + 結論 365 日 → 定常 6〜8 GB、現行 1.9 GB） | **実施する。SQLite も継続** | パリティゲートの前提条件（制約 1）であり選択肢が無い。単独運用・1 ユーザーで 8 GB は SQLite の実用範囲内。**ただし §3 Phase 0 で実測して見直す** |
| **3** | **fail-open 3 件**（空ドメイン信頼度 1.0 / CheckHost 欠測を健全扱い / recall ゲートの「不確実なら許可」） | **v3 では fail-closed を既定にする。ただし現行系では変えない** | NP1（見逃しは誤検知より悪い）に照らせば fail-open は誤り。しかし現行系で変えると TL 分布が動きパリティの基準線が崩れる。**v3 側の意図的な差分としてパリティ条件に例外を明記**（§5-C） |
| **4** | **tradecraft の処遇** | **v3 に持ち込まない** | D4 で実データが全量テスト残骸と判明（行数が 82 回のテスト実行と完全一致）。export 保全の必要すら無い |
| **5** | **climate の処遇**（G-18: 閾値 30 件以上がハードコード、registry 未登録、Gauge 境界 15/8/3 の導出根拠がどこにも無く、完全無テスト） | **v3 初期リリースに含めない（凍結）** | NP6（導出開示）を構造的に満たせない。根拠不明の閾値を移植すると v3 が同じ債務を引き継ぐ。climate が出す結論の価値が実証されてから、仕様を書き直して再実装する |
| **6** | **UNREFERENCED 8 endpoint / v1 API sunset** | **drop / v3 cutover と同時に v1 契約終了** | D6 で curl 運用の可能性も否定済み |

**裁定が 1〜3 で変わった場合**: §5 のパリティ条件と §6 の許容差を再計算する。

## 4. パリティハーネスの設計

### 4.1 両系を同一の観測台帳から駆動する

制約 2 により「旧系の replay を回す」方式は採らない。代わりに:

```
  L1 観測台帳（60 日）
        ├──→ 旧系採点（GET ハンドラを迂回する薄いドライバ経由）──→ 旧系の結論系列
        └──→ v3 L2/L3 ────────────────────────────────────────→ v3 の結論系列
                                                                      ↓
                                                               系列比較（§5）
```

- 旧系側は **採点ロジックだけを呼ぶ薄いドライバ**を書く（HTTP 層を通さない）
- 前提として **F-05（非冪等）を旧系側でも解消する**か、統計更新をドライバ側で凍結する
- LLM 依存部分は**記録済み判定を再生**する（新規 LLM 呼び出しをしない）ことで決定論性を確保

### 4.2 比較の単位

| 比較対象 | 単位 |
|---|---|
| TL 系列 | シナリオ × 時刻。**必ず `severity = 6 − TL` に変換して比較**（反転事故 2 回の教訓） |
| 結論型別の可用性 | 型 × シナリオ。「結論できた/できない」の一致 |
| 結論不可の理由 | v3 は 4 種を区別、旧系は実質 1 種（F-12）→ **意図的差分**として §5-C に計上 |
| 寄与センサー集合 | 結論ごとの集合一致（Jaccard） |
| provenance の解決可能性 | v3 側で 100% 要求（NP6） |

## 5. Cutover 条件（数値）

**原文（2026-08-05）**:

> S5-VERIF の CUT-01〜14 を本計画の文脈で確定する。**全条件の同時成立が必要**。

> ### 2026-08-09 全面改訂 — パリティの目的は**同一性ではなく差分の帰属**である（ADR-V3-011、オーナー承認）
>
> オーナーの問い: 「v3 を shadow として扱うのは、v1 の結果が**正しい**ことを前提にしていないか。
> なぜ v3 に切り替えないのか」。
>
> **前半は正しく、旧条件はこの問いに耐えない**。参照系である v1 は測定可能に誤っている — 移植中に読んだ
> だけで D2 §H の 7 件（BGP 異常検知の完全死 / 再起動をまたいで変わる方向確信度 / 自分の docstring が
> 禁じる帰属を dual-core で行う分岐 / 27 家系が個別異常事象から構造的に除外 / 誤帰属をテスト fixture が
> 期待値として固定していた ISO2 総当たり走査 / 実質 Dismiss である Defer / bit 再現しない IDF 指数）、
> これに Phase D の 89 件と較正事故 3 件が乗る。**その参照に対して数値的同一性を要求するゲートは、
> 形が誤っている。**
>
> **後半（「なぜ切り替えないのか」）は結論として採らない**。shadow の価値は v1 が正しいことに依存して
> いない。v3 自身の初起動は **7,403 テスト green・パリティ fixture 13/13 一致**の状態で、数時間のうちに
> **6 件の欠陥**を出した（初回掃引の livelock G-19 / 読取ハンドルのスレッド欠陥 / 書込ハンドルの同型 /
> 全ティック失敗中に healthy を返す `/healthz` / 1 サイクル診断の不健全 / 平文パスワードの永久保存
> V3-SEC-01）。shadow が測るべきは「v1 と同じか」ではなく **「v3 が走るか」と「差分が説明されているか」**
> である。**shadow は残し、目的を差し替える。**
>
> **改訂後にゲートが答える問い**:
> 1. v3 と v1 の**すべての**差分が §7-2 の登録エントリに写像されるか（未登録の差分がゼロか）
> 2. **insensitive** な差分（v1 が見えていて v3 が見えない）が、**1 件ずつ**正当化されているか
> 3. 比較そのものが**有効な参照点**の上で行われているか（死んだ検出器との一致は何も測っていない）
> 4. ゲートが**覆っていない層**が、別の条件で覆われているか
>
> **sensitive な差分（v3 が見えて v1 が沈黙している）は cutover を阻害しない。insensitive な差分は、
> 個別に正当化されない限り阻害する。** この非対称が、NP1 を受け入れ条件として書いたものである。
>
> **条件数は 14 → 17**（14 件を改訂または無改訂で存続 + 3 件を新設）。
> **同一性が正しい物差しである面は同一性のまま残す** — C-10 / C-11 / C-12 は ETL の忠実性についての
> 条件であり、検知能力についての条件ではない（R1）。本改訂の「同一性ではない」は**検知・結論の比較**に
> ついての言明である。
>
> **ハーネス側の未追随（本改訂の負債）**: `v3/parity/conditions.py` は旧 14 条件の定義（override 禁止は
> C-02 / C-08 / C-14 の 3 件）を実装している。本改訂はドキュメントのみで、**コードは変更していない**。
> **WP-5.1 で条件表・override 禁止集合・VOID 除外・新設 3 条件をハーネスへ反映する作業が必要**。

**VOID の規律**:
1. 除外は**レポートに VOID として名前つきで出す**。分母から黙って消さない。
2. 追加は §7-2 と同じ規律 — **発見時点で本表に追加する**。黙って除外する選択肢は無い。
3. **VOID を増やすことでゲートを通してはならない**。追加には D2 の欠陥 ID と、「v1 側の量が測定では
   ない」ことの実測証跡を要する。**時間限定の VOID（V-1）は期間を書く** — 恒久として書くと、修理後も
   永久に測らない条件になる。

### D. 走らせた系についての条件（2026-08-09 新設）

**新設の理由**: 現行ハーネスは **L1 に保管済みの行をカーネルへ射影する**（`v3/parity/driver_v3.py` に

### 意図的差分の扱い（§5-C）

**原文（2026-08-05）**:

> 裁定 3（fail-closed 化）と F-12（結論不可の細分化）により、**v3 は旧系と意図的に異なる出力を出す**。
> これらは C-03 の不一致 5% 枠に計上し、**事前に一覧化して「予期された差分」として登録する**。
> 登録外の差分が出た場合は cutover 中止。

**改訂（2026-08-09）** — 「5% 枠」は C-03 の改訂により消滅した。差分は**枠で受けるのではなく、
1 件ずつ帰属させる**。

1. **選択肢は 2 つしかない** — (a) コードを現行系に合わせて戻す、(b) §7-2 に登録する。
   **黙って残す選択肢は存在しない**（§7-2 の標準規律を本計画の条件へ昇格）。
2. **方向は 3 値**: `sensitive`（v3 が見え、v1 が沈黙）/ `insensitive`（v1 が見え、v3 が沈黙）/
   `neutral`。**sensitive と neutral は cutover を阻害しない。insensitive は阻害する** —
   エントリごとに retire 条件、または「v1 側の量が測定でない」証跡を持つ場合に限り通過する。
3. **包括エントリの禁止**: 「その他の差分」「一部のセンサー」のようなエントリは登録ではない。
   各エントリは対象（シグナル / 家系 / 条件）を名指し、テストで反証可能でなければならない。
4. **承認の粒度**: §7-2 #1〜#53 はオーナー包括承認済。**#54 以降のうち `insensitive` 方向は
   1 件ずつ承認を要する**（`sensitive` / `neutral` はバッチ承認で可）。cutover 判定の直前に諮る。
5. **VOID（§5-0）の追加も同じ規律**に従う。
6. **方向判定の述語 — insensitive に数えるのは「v1 が実測に基づいて出した結論を v3 が出さない」場合に
   限る**。v1 側の量が捏造（欠測を測定値として読んだ値、根拠のない定数床、再現しない量）である場合は
   insensitive に数えない。この述語が無いと、**v1 の欠陥を直すたびに insensitive 差分が増えて
   cutover が遠のく** — NP1 が要求する方向と正反対になる。根拠: H-05 の backfill で「0 を混ぜると
   真の撤回が沈黙する」ことが実測され、ADR-V3-006 の fail-closed 化も同じ形（v1 の fail-open は
   検知ではない）。

| 遷移タイミング | 方向を混ぜた p95 ≤ 1 tick | **insensitive 側単独でも** p95 ≤ 1 tick |
| L5 の green | 「全項目 green」 | **実行記録が期待間隔内にあること**（無記録は green ではない） |
| 移行表 | 35 表の行数一致 | 分類済み**全表** + **未分類 0 件** |
| 照合 | サンプルハッシュ | **全数照合**で不一致 0 |
| NP6 遡及 | 100% 解決 | 100% 解決 **かつ分母が空でない**（空集合は NOT_MEASURED） |
| 較正窓 | 断絶しない | **無印の断絶ゼロ**（意図的エポックは印を要求） |
| null-zone | 旧系と同等以下 | **絶対基準 ≤ 7 日 + 登録済み例外** |
| 有効 cell | 非退化 ≥ 4 | **非退化 ∧ VOID 非依存 ≥ 4**（数は減りうる） |
| 走行実績 | 条件なし | **C-16**（連続 30 日、説明のつかないティック失敗ゼロ） |
| 阻害欠陥 | §5 に不在 | **C-17**（override 禁止） |

**緩んだ点は 1 つだけ**: C-03 の severity 一致率 0.95 が合否の閾値でなくなった。ただしこれは
**未登録の不一致をゼロに要求する条件と引き換え**であり、正味では厳しい。旧条件下では
「一致率 0.96 で未登録差分が残っている」状態が通ったが、新条件では通らない。

## 6. Rollback 条件

cutover 後 30 日間の強化監視期間中、以下のいずれかで即時ロールバック:

| ID | 条件 |
|---|---|
| R-01 | recall が cutover 前ベースラインから **0.05 超の低下** |
| R-02 | L5 の監視で **未知の沈黙失敗**を検出 |
| R-03 | 結論不可が **7 日連続**（NP5+8 の設計失敗基準） |
| R-04 | データ破損の兆候（整合性チェック失敗） |
| R-05 | アナリストが運用継続不能と判断（人間の判断を最終ゲートに残す — NP7） |

**ロールバック可能性の保証**: cutover 後も旧系の DB スナップショットを 90 日保持し、
旧系を再起動できる状態に置く（ADR-V2-003 の sunset 90 日と整合）。
