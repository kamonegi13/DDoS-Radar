# S1 — フロントエンド挙動仕様（アナリスト視点）

**スコープ**: アナリストに **何がどう見え、どう操作でき、いつ更新されるか**。画面の意味論・状態遷移・閾値・
操作の副作用。DOM 構造 / CSS / 関数名 / モジュール分割は扱わない（ADR-V3-003: 構造は P で導出する）。
**隣接仕様との境界**: スコアリング式 → [S1-scoring-core.md](S1-scoring-core.md)（本書は「その数値をどう見せるか」）。
結論 envelope と結論不可理由の生成 → [S1-conclusions.md](S1-conclusions.md)。API 契約 → S2。i18n 辞書・パネル
クローム契約・INTEL GUIDE → S4（参照のみ）。較正提案の中身 → [S1-calibration.md](S1-calibration.md)。

**規約**: [S0-spec-conventions.md](S0-spec-conventions.md)。分類 CORE / ACCIDENTAL / DEFECT-PRESERVE。
条項数が多いため **根拠 / 検証 / 分類 の 3 欄は 1 行にまとめて記す**（欄そのものは省略しない）。
DEFECT-PRESERVE 条項の **v3 規範は §5 の表**に集約する（条項側は DP 番号で参照）。
**検証の前提**: 現行フロントのテストは切り出し済み pure module 6 本（計 160 件）のみで、**画面本体のカバレッジは
0%**（D1-frontend §5.8、D2 A-08）。よって大半の条項は `未検証`。pure module に規範実装があるものは
**式を再記述せず参照**する（D3 §2 keep 判定）。

## 1. 用語

CLAUDE.md の定義（country / scenario / participant / coupling weight / role / adversary / focused /
background / C-lite）に従う。本書固有:

- **TL**: 脅威レベル。**1=CRITICAL … 5=NORMAL（DEFCON 式）**。比較は必ず `severity = 6 − TL` 経由
- **HUD**: 画面上部の常時表示帯。Row 1 = TL 系、Row 2 = ドメイン別ドライバ、Row 3 = 信頼性（AP3）
- **チップ**: 1 指標の最小表示単位（ラベル + 値 + 状態帯 + 説明 + 任意のクリック導線）
- **Alert Lane**: AP1 の注目対象提示面。dormant / pin-dock / critical-banner の 3 表示モード
- **ドリルダウン**: 結論 1 件の全導出根拠を開示するモーダル（NP6 の UI 実装契約）
- **overlay**: participant weight をアナリストが仮説検証用に一時上書きする機構
- **規範実装（keep）**: v3 へそのまま引き継ぐ pure module 6 本。条項はそこを一次ソースとして参照する

## 2. 挙動条項

### 2.1 起動・認証 UX

### S1-UI-001: 未認証時はログインゲートが全画面を遮蔽する
**挙動**: 有効なアクセストークンが無い状態ではゲートが全 UI を覆い一切の操作を許さない **MUST**。保存済み
トークンは保護エンドポイントでの生存確認に成功したときのみ解除 **MUST**。生存確認が**ネットワーク障害で
失敗**した場合はゲートを維持しつつ理由を表示 **MUST**（「ログアウトされた」と「接続不良」を区別）。
**根拠**: login-init.js:9-38、radar.js:80-90 / **検証**: 未検証（radar.js カバレッジ 0%） / **分類**: CORE

### S1-UI-002: ログイン成功後は全画面を再初期化し、リフレッシュトークンを SPA に持たない
**挙動**: 認証成功時、アクセストークン・ユーザー名・役割・トークン寿命秒を永続化し**初期ロードと同じ経路で
全体を再初期化 MUST**。リフレッシュトークンは JS から読めない httpOnly Cookie として受領する **MUST**。
**根拠**: login-init.js:62-74、radar.js:16-24 / **検証**: 未検証 / **分類**: CORE（XSS でのリフレッシュトークン奪取を構造的に封じる）

### S1-UI-003: トークンは先行更新し、401 は背景更新 + 1 回だけの再試行で吸収する
**挙動**: 寿命の **80% 経過時点で自動更新を試行 MUST**（既定寿命 3600 秒、ログイン応答値が優越）。401 に対しては
リフレッシュを 1 回試み、成功したら元リクエストを **1 回だけ再送 MUST**、失敗したらゲートを表示 **MUST**。
同時多発 401 に対しリフレッシュは **1 本に直列化 MUST**。再帰的再試行は行わない **MUST**。
**根拠**: radar.js:10-14, 32-49, 125-143 / **検証**: 未検証 / **分類**: CORE（401 がアナリストの操作に到達しないことが目的）

### S1-UI-004: 役割は 3 段の全順序で UI 要素を出し分ける
**挙動**: 役割は `viewer < analyst < admin` の**全順序 MUST**。各 UI 要素は必要最小役割を宣言し、現役割が
それ以上のときのみ表示 **MUST**、役割不明時は最低権限とみなす **MUST**。非表示化の結果アクティブなタブが
不可視になったら**最初の可視タブへ自動遷移 MUST**（空白画面禁止）。
**根拠**: radar.js:887-903, 2871-2880 / **検証**: 未検証 / **分類**: CORE

### S1-UI-005: クライアント側ログアウトはリフレッシュ Cookie を失効できない
**挙動**: ゲート表示時にアクセストークンを破棄するが、リフレッシュ Cookie は JS から削除できず残存する。
認証エラー文言の一部が辞書を経由せず直接埋め込まれている。
**根拠**: radar.js:80-90、login-init.js:34 / **検証**: 未検証 / **分類**: DEFECT-PRESERVE（→ §5 DP16 / DP17）

### 2.2 データ同期の意味論

### S1-UI-006: メインデータは 15 分周期でポーリングし、非表示時は 60 分へ緩める
**挙動**: 主データ面は可視時 **15 分**、不可視時 **60 分**間隔でポーリング **MUST**。可視へ復帰したら**即時 1 回
取得してから通常間隔へ戻す MUST**。リクエストは focused scenario・ミュート中センサー・force モードを含む **MUST**。
**根拠**: radar.js:1948, 8177-8183, 9630-9645 / **検証**: 未検証 / **分類**: CORE（NP1: 復帰時の即時取得が無いと見逃し窓ができる）

### S1-UI-007: 手動同期は 2 段（snapshot / sensors）で、押下中の状態を必ず示す
**挙動**: **snapshot**（キャッシュ TTL 無視・遅いセンサーへ扇形取得しない）と **sensors**（加えて許可リスト内
センサーの背景取得を起動）の 2 モード **MUST**。押下中は同期中状態を表示し、**例外発生時も必ず原状復帰 MUST**。
**根拠**: radar.js:1950-1957, 8155-8174, 8252-8262 / **検証**: 未検証 / **分類**: CORE

### S1-UI-008: 取得失敗時は直前データを保持し、画面を空にしない
**挙動**: HTTP エラーまたは例外で失敗した場合、**直前の成功データを保持 MUST**、初期状態へ戻さない **MUST**。
これは主データ面・全 AP3 チップに共通する。現行は劣化標識が無くコンソールのみである。
**根拠**: radar.js:8184-8187, 2421, 5303, 5490-5493, 5604-5606, 5676-5678, 5718-5720 / **検証**: 未検証 / **分類**: CORE（NP3）+ DEFECT-PRESERVE（→ §5 DP2）

### S1-UI-009: WebSocket push は主データを部分マージし、ポーリングを置換しない
**挙動**: push は採点結果のみを運ぶ。受信時は主データを**全置換せず該当部分だけ差し替える MUST**。
ポーリングは push の有無にかかわらず継続 **MUST**、push でポーリングタイマーをリセットしない **MUST**。
種別ごとの効果は下表に限定 **MUST**。センサー名にプロトタイプ汚染語が来た場合は無視 **MUST**。

| push 種別 | 効果 |
|---|---|
| 採点更新 | 採点部を差し替えて全描画。最終同期表示に「WS Live」を付す |
| 待ち伏せ警報 | 専用警報を可視化し危機演出を付与（自動では消えない） |
| シーケンス事象 | 連鎖パネルのバッジを更新 |
| センサー状態 | 当該センサーの状態のみ更新し既存フィールド（ドメイン/最終取得/CB 状態）を保持 |
| 通知結果 | 最終同期欄を 4 秒だけ成否表示に差し替え、その後復帰 |
| インテル更新 | インテル面を再取得（push 本体のデータは表示に使わない） |

**根拠**: radar.js:9549-9631 / **検証**: 未検証 / **分類**: CORE

### S1-UI-010: focus 不一致の push は破棄する
**挙動**: push が対象シナリオ ID を自己申告している場合、**現在の focus と不一致なら破棄 MUST**。申告が無い
push は「主張なし」として受理 **MUST**。これが無いと focus 切替前に計算が始まった tick の結果が切替後に
着弾し、新 focus の表示を上書きする。
**根拠**: radar.js:9553-9569 / **検証**: 未検証 / **分類**: CORE（NP6: 表示中の値がどの focus のものか一意でなければならない）

### S1-UI-011: WS 接続状態は 3 値で常時可視化する
**挙動**: 接続表示は **connected / disconnected / degraded の 3 状態 MUST**。接続確立失敗（トークン失効・CORS・
過負荷）は disconnected と区別して degraded を出す **MUST**（「WS 生存」と「無言でポーリングに退行」を区別）。
切断中もポーリングは継続し加速しない **MUST**。
**根拠**: radar.js:9521-9548 / **検証**: 未検証 / **分類**: CORE

### S1-UI-012: 描画スキップ判定は表示に影響する全データを含まなければならない
**挙動**: 冗長再描画を抑止する署名を持つ場合、**focus 変更時・ログイン完了時・Replay 適用時は署名を必ず
破棄 MUST**。現行署名は タイムスタンプ / 採点要約 / 対象要約 / v2 envelope 時刻 のみで、**地図オーバーレイ・
participants・相関マップを含まない**ため、タイムスタンプが動かない限りこれらの変化は描画されない。
**根拠**: radar.js:156-157, 2241, 8646-8665, 14395 と 9309-9320 の対比 / **検証**: 未検証 / **分類**: DEFECT-PRESERVE（→ §5 DP3）

### S1-UI-013: 1 回のポーリング完了は 8 系統の従属更新を起動する
**挙動**: 主データ取得の成功は順に **(1) WS 購読先の再評価、(2) 全描画、(3) 地図遮蔽への「v1 到着」通知、(4) NP7
注意書きの補充、(5) v2 結論 envelope 更新（内部で Alert Lane 更新を連鎖）、(6) 自己評価チップ、(7) LLM 健全性チップ、
(8) Watchpane 行と LLM インテル面** を起動 **MUST**。(4)-(8) は結果を待たず、失敗しても主描画を妨げない **MUST**。
加えて一部センサーの実測が空のときは **60 秒後に 1 回だけ再取得 MUST**（多重予約禁止）。
**根拠**: radar.js:8195-8248 / **検証**: 未検証 / **分類**: CORE。**後段の個別救済は ACCIDENTAL**（§4-A1）

### S1-UI-014: AP3 チップは主同期と独立に自前周期でポーリングする
**挙動**: 自己評価系（RECALL/NULL-ZONE/DRIFT/SKEW/FAULT/OBS-BG）TTL 5 分・安全網 30 分／LLM 健全性 60 秒／
MODEL 5 分／AUTO-CAL 60 秒／CHRONIC 60 秒／ANCHOR 5 分／LLM 機能 60 秒／AUTO-TUNE 60 秒。集約層は無い。
常時表示でないパネルは**可視またはドック時のみ**再描画し、非表示時は要更新印だけ立てる **MUST**。
**根拠**: radar.js:5501-5523, 9039-9052、llm_features_hub.js:325-330、autotune_wizard.js:428-436 / **検証**: 未検証 / **分類**: DEFECT-PRESERVE（→ §5 DP5）

### S1-UI-015: v2 結論キャッシュは focus 単位・30 秒 TTL で、競合を必ず破棄側で解決する
**挙動**: v2 結論 envelope は **focused scenario をキーに 30 秒 TTL** で保持 **MUST**。競合制御として (a) Replay 中は
更新しない、(b) 同一 focus の多重取得を抑止、(c) 先行要求を中断、(d) 応答受領後とパース後の 2 点で focus 変化を
再確認し**変わっていたら結果を破棄**、(e) 中断・503・404 はキャッシュを触らず失効に任せる、を **MUST**。
focus 変更時は**旧 focus のエントリを削除 MUST**。
**根拠**: radar.js:2000-2006, 2064-2070, 6978-7027, 14392-14394 / **検証**: 未検証 / **分類**: CORE（NP6: 表示中の結論がどの focus のどの時点のものか一意であること）

### 2.3 HUD 意味論（Row 1 / Row 2）

### S1-UI-016: TL とドメイン値は v2 結論を正、v1 採点を代替とする単方向オーバーレイで表示する
**挙動**: **新鮮な v2 結論があればそれ、無ければ v1 採点値 MUST**。TL の採用条件は「結論が存在」「結論不可理由が
null」「state が整数として解釈可能」の**3 条件すべて**。ドメイン別は 3 キーが**常に存在 MUST**（欠測時 score=0 /
status=NORMAL）で、v2 のスコアは**数値のときだけ**、状態語は**空でないときだけ**採用し、それ以外は**キー単位で v1 へ
縮退 MUST**。入力を変更してはならない **MUST**。規範実装は `hud_v2_overlay.js`（keep）。
**根拠**: hud_v2_overlay.js:66-99、radar.js:6957-6963, 8680 / **検証**: tests/test_hud_v2_overlay.js（21 件） / **分類**: CORE（NP3: v2 障害時も TL 表示が消えない）

### S1-UI-017: v1 と v2 の TL 不一致は警告として明示する
**挙動**: 両者が**ともに有限で不一致のとき**、両値を並記した警告を出す **MUST**、一致または一方が欠測なら
非表示 **MUST**。表示には「どちらが正か（v2）」「なぜ一時的に食い違うのか」を必ず添える **MUST**。
**根拠**: radar.js:8917-8923, 10387-10409 / **検証**: 未検証 / **分類**: CORE（NP6: 2 系統の値の併存を隠さない）

### S1-UI-018: TL の説明は決定論的テンプレートで生成する（AP2）
**挙動**: 新鮮な v2 結論があるとき **LLM を用いないテンプレート生成 MUST**（規範実装 `self_explanation.js`、keep）。
含む要素は 脅威レベル状態／スコア・アクティブドメイン・収斂ボーナス・確信度／**超過済み閾値の全列挙**／**次に超える
閾値 1 件**／calibration 状態／反証条件／最終確認からの経過／NP7 注意書き。結論不可時は理由と詳細のみを述べて
早期終了 **MUST**。v2 が無ければ v1 内訳へ縮退 **MUST**。
**根拠**: self_explanation.js:53-128、radar.js:8689-8719 / **検証**: tests/test_self_explanation.js（18 件） / **分類**: CORE（AP2 の中核。再現性のため LLM 不使用が要件）

### S1-UI-019: TL クリックは完全開示へ、開示不能なら v1 根拠面へ落とす
**挙動**: 新鮮な v2 `threat_level` 結論が **id を持ちかつ結論不可でない**ときドリルダウンを開く **MUST**、それ以外は
v1 の根拠パネルを開く **MUST**（無反応は禁止）。ドメインバーはスコア 10 で飽和し、色は**サーバの状態語のみに
従う MUST**（フロントは数値閾値を持たない。NP6）。
**根拠**: radar.js:8875-8878, 8930-8938 / **検証**: 未検証 / **分類**: CORE

### S1-UI-020: 状況チップは明示条件で表示可否を決め、条件外では非表示にする
**挙動**: 以下のチップは値の有無ではなく**明示条件**で表示可否を決める **MUST**。条件外は「—」ではなく
**非表示 MUST**（誤解を招く 0 や薄い根拠を見せない）。

| チップ | 表示条件 | 補足 |
|---|---|---|
| ADV/TGT 内訳 | `adv + tgt ≥ 0.05` | 表示 1 桁、ホバー 2 桁 |
| TL 継続時間 | `> 60 秒`。`≥ 7,200 秒` で強調 | 正常性バイアス対策 |
| ETA | 近接ラベルが「上昇近接」「下降近接」 | 速度が小さく ETA 不能なら**チップは出したまま時刻欄のみ空**（NP5+8） |
| 時間帯 Z | 同時間帯サンプル `n ≥ 7`。色帯 \|z\| ≥ 2.5 / 1.5 / 1.0 | 少数サンプルの Z は見せない |
| 無線封鎖 | `\|velocity\| < 0.00005` かつ `total_score ≥ 3` | 「スコア高いが速度ゼロ」＝通信封鎖の兆候 |
| background 急上昇 | 非 focus のうち `Δ1h` 最大かつ `≥ 1.0` を 1 件 | クリックで当該シナリオ詳細へ |
| インテル収斂 | 値が存在すれば **0 件でも表示** | 0 と欠測を混同しない |

**根拠**: radar.js:10677-10686, 10733-10834, 10837-10865 / **検証**: 未検証 / **分類**: CORE。**無線封鎖の速度閾値 0.00005 は ACCIDENTAL**（§4-A2）

### S1-UI-021: 24 時間スパークラインは focused シナリオ固有で、focus 変更時に即座に切り替える
**挙動**: **focused シナリオの TL 履歴 24 時間 MUST**（キャッシュ TTL 60 秒）。focus 変更時は表示中バッファを即座に
破棄 **MUST**。棒高は severity（6−TL）に比例し、**TL5 にも最小高さを与えて「データ無し」と区別 MUST**。
遅延応答は focus が変わっていれば破棄 **MUST**。暫定系列は現行、全シナリオ混成である。
**根拠**: radar.js:8906-8915, 10415-10492 / **検証**: 未検証 / **分類**: CORE + DEFECT-PRESERVE（→ §5 DP14）

### S1-UI-022: 根拠面は寄与・反証・ギャップの 3 面を同時に示す
**挙動**: (a) **寄与ウォーターフォール** — 対象は **FIRED かつ非 suppressed かつ score > 0** のみ（S1-SCORE-001 と
同一規則）。実効値 `score × confidence`（欠測時 1.0）、分母は実効値合計 + 収斂ボーナス。構成比 **1% 未満は非描画・
8% 未満はラベル省略**、分母 0 以下または根拠行列欠落時は**ブロックごと非表示**。(b) **反証シグナル / 情報ギャップ**
— 非発火かつ非抑制のセンサーを、**健全性が正常/劣化なら「反証シグナル（安心材料）」、異常/CB 開/陳腐化/無効なら
「情報ギャップ（見えていない）」に分類 MUST**、健全性不明はどちらにも入れない **MUST**。根拠行列に無いが健全性が
異常なセンサーもギャップへ **MUST**。
**根拠**: radar.js:10125-10219 / **検証**: 未検証 / **分類**: CORE（NP1 の中核。「発火していない」が「安全」か「見えていない」かを分ける）+ DEFECT-PRESERVE（→ §5 DP13）

### S1-UI-023: 未知の状態語は中立色で描き、取得失敗は失敗として表示する
**挙動**: サーバ由来の状態語を色へ写像する面は、**対応表に無い語を任意の色へ落としてはならず、中立色（不明）で
描く MUST**（未知状態を「正常」にも「危険」にも見せない）。現行、天候ブリーフと SALUTE は HTTP ステータスを

## 7. 未決事項

1. **AP3 チップ閾値の所在**（§4-A4）: 境界値を registry へ出すと「信頼度の基準をアナリストが動かせる」ことになる。NP6（透明性）と較正の健全性のどちらを優先するかはオーナー裁定を要する。本書は現行を CORE として記述した
2. **Replay の as-of 範囲**（§4-A8、DP11）: 「結論だけが過去」で足りるのか、テレメトリ全体を過去断面にすべきか。後者は v1 テレメトリの時系列保存を要求し S3（スキーマ）に波及する
3. **ack のサーバ化**（§4-A6）: AP4 が「自動化判断を時系列で再生可能にする」ことを求める以上、アナリストの ack も台帳に載るべきだが現行はローカルのみ。判断履歴の完全性の定義に関わる
4. **What-If の 2 系統**（S1-UI-054 / DP4）: クライアント完結の除外シミュレーションと、サーバへ届く weight overlay が同じ「What-If」の語で提示されている。語彙と UI を分離するか一本化するかは設計判断
5. **DDoS レガシーの撤去範囲**（DP15）: L3/L7 ベクターは攻撃元フローの描画全体に配線されており、撤去は攻撃元表示の再設計を伴う。cyber ドメイン専用のサブ表示として残す選択肢がある
6. **地図レイヤの既定状態**（§4-A15）: 脅威地形と連携リンクは「信号にならなかった」ことを理由に既定で消えている。較正が進んだ現在も同じ判断が妥当かは実データでの再評価が要る
