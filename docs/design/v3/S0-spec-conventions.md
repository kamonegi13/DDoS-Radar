# S0 — 仕様記述規約（Phase S 共通）

Phase S の全仕様書（S1-*.md, S2-*.md, S3-*.md, S4-*.md, S5-*.md）はこの規約に従う。
目的: (1) v3 実装が現行コードを一切参照せずに書ける完全性、(2) NP6 流の遡及可能性、
(3) テスト→仕様トレーサビリティによる網羅性の機械的検証。

## 1. 条項フォーマット

すべての挙動は番号付き条項で記述する:

```
### <条項ID>: <一行要約>
**挙動**: <MUST/SHOULD/MAY で記述する規範文。実装方法ではなく入出力・状態遷移・数式を書く>
**根拠**: <file:line（現行コードの該当箇所）。複数可>
**検証**: <この挙動を検証する既存テスト（tests/xxx.py::TestClass::test_name）。無ければ `未検証` と明記>
**分類**: CORE | ACCIDENTAL | DEFECT-PRESERVE
```

- **条項ID**: `<文書>-<領域>-<連番3桁>`（例: `S1-SCORING-014`、`S2-API-003`）。欠番を作らない
- **CORE**: 意図された仕様。v3 で必ず保存
- **ACCIDENTAL**: 偶然そうなっている挙動。**保存/破棄はオーナー裁定**（S 出口でリスト提示）
- **DEFECT-PRESERVE**: 現行挙動は欠陥だが、パリティ比較のため「現行がこうである」ことを記録する
  （v3 では D2 の欠陥 ID を引いて修正内容を併記）

## 2. 数式・閾値の記述

- 数式は擬似コードまたは数式で完全に書き下す（「Z-score を計算する」は不可。窓幅・分母・ゼロ除算時の挙動まで）
- 閾値は **値 + config キー + デフォルト値 + 3 層解決の有無** を記録:
  `収斂ゲート: 独立ソース ≥ 2（config: CONVERGENCE_MIN_SOURCES, default 2, DB override 可）`
- TL は必ず「TL（1=CRITICAL…5=NORMAL）、比較は severity=6−TL 経由」と明記（反転事故 2 回の教訓）

## 3. 書いてはいけないもの

- 現行の関数名・クラス名・モジュール構造を仕様の本文に持ち込まない（根拠欄の file:line 引用のみ可）。
  ADR-V3-003: 構造は P で導出する。仕様は「何が起きるか」だけを語る
- 「現行実装では〜」という記述を規範文に混ぜない（分類欄で表現する）

## 4. 各仕様書の必須セクション

1. **スコープ**: 扱う挙動領域と、隣接仕様書との境界
2. **用語**: CLAUDE.md 用語定義の参照 + 領域固有語
3. **挙動条項**（§1 形式）
4. **閾値カタログ**（§2 形式の表）
5. **ACCIDENTAL 一覧**（オーナー裁定待ちの表）
6. **テストトレーサビリティ表**: この領域の BEHAVIOR/CONTRACT 級テスト（D5 台帳参照）
   全件について `テスト | 対応条項ID`。**対応条項が無いテスト = 仕様の穴**として `GAP` と記す
7. **未決事項**: 仕様化できなかった挙動（理由付き）

## 5. 網羅性の検証（S 出口ゲート）

- カバレッジ表（S-coverage.md）: D1 の全モジュール × 「仕様化済み（条項範囲）/ 理由付き除外」
- D5 の BEHAVIOR/CONTRACT 級テスト全件が、いずれかの仕様書のトレーサビリティ表に登場すること
- GAP と ACCIDENTAL の全件がオーナー裁定リストに集約されていること
