## 1. 用語

CLAUDE.md の用語定義に従う。本書固有: **CB** = サーキットブレーカー（連続失敗を検知して取得を
一時停止する機構）／**fetch** = 外部データ源への 1 回のネットワーク取得／**degraded** = 一部入力が
欠落・劣化した状態で結論を止めず品質を明示して継続する運転形態／**採点ティック** = 全 scorable
シナリオを 1 巡採点する単位（S1-PIPE-001）／**秘匿値** = API トークン・パスワード・webhook URL 等、
平文を露出してはならない設定値／**辞書** = UI 表示文字列の単一言語（日本語）テーブル。
TL は 1=CRITICAL … 5=NORMAL（DEFCON 式）、比較は `severity = 6 − TL` 経由。

## 2. 挙動条項

### 2.1 NP3 — 耐障害

#### S4-NF-001: 採点ティックは取得を行わず、センサー障害は実行文脈で隔離する
**挙動**: 採点ティックは外部取得を起動しては **MUST NOT**、各センサーの直近キャッシュを読むだけで完結 MUST。センサー未登録・キャッシュ空は空値として扱い例外を伝播させては MUST NOT。取得は**センサー 1 基につき 1 つの独立した実行文脈 MUST** とし、例外は当該文脈内で捕捉して他センサーおよび採点へ伝播させては MUST NOT。障害センサーの寄与は欠落として扱い、その事実を品質メタに記録 MUST。
**根拠**: radar/routes/core.py:390-480（約 40 センサー分のキャッシュ読出、全て None-guard 付き）、radar/scheduler.py:136-140（取得単位の捕捉）、radar/\_\_init\_\_.py:299-306（センサー 1 基 = 1 スレッド、起動スタガー付き）
**検証**: 未検証（スケジューラの取得ループは無テスト — D5 §カバレッジ）
**分類**: CORE

#### S4-NF-002: 外部への全 HTTP 呼出しに timeout を指定しなければならない
**挙動**: 外部ネットワーク呼出しは **connect / read の双方に有限 timeout を指定 MUST**。無指定の呼出しが存在しては MUST NOT（単一のハング接続が協調イベントループ全体を閉塞させ、全センサーが同時停止するため）。既定値は 1 箇所で宣言 MUST。
**閾値**: 既定 `(connect 10s, read 20s)`。個別指定の実測分布は 5 / 8 / 10 / 12 / 15 / 20 / 30 秒
**根拠**: radar/sensors/base.py:199。AST 走査で外部呼出し **65 件中 timeout 欠落 0 件**（2026-08-04 実測）
**検証**: 未検証（timeout 網羅を検査するゲートは無い）
**分類**: CORE。**D2 A-10 の「timeout 指定漏れ」は現時点で解消済み**だが再発防止機構が無い（S4-NF-061）

#### S4-NF-003: 全 fetch は CB を経由しなければならない
**挙動**: 外部取得は**成否が CB に記録される経路を必ず通る MUST**。CB が OPEN のセンサーは取得を試行 MUST NOT。CB 判定は**取得サイクルにつき厳密に 1 回 MUST**（複数回呼ぶと HALF_OPEN のプローブ枠を多重消費する）。
**根拠**: radar/scheduler.py:119-147（唯一の CB 経路。:122 skip 判定、:142 成功記録、:145 失敗記録）、radar/sensors/base.py:116（呼出回数の契約）
**検証**: tests/test_engine.py（CB 開閉閾値 — D5 §3 no.1）
**分類**: CORE

#### S4-NF-004: スケジューラ外の実行文脈にも CB を適用しなければならない
**挙動**: 独立ワーカ・手動起動・補償実行など、定期スケジューラ以外から行う取得も **S4-NF-003 と同一の CB 経路を通る MUST**。実行文脈によって CB 適用の有無が変わっては MUST NOT。
**根拠**: **バイパス 2 経路を実測確認** — (a) 背景観測ワーカの自前ループ radar/sensors/bg_observer.py:144-155（CB を一切呼ばず、:47-51 が「CB が開いていても走り続ける」と自認）、スケジューラ側の除外 radar/\_\_init\_\_.py:300-303。(b) 手動強制取得 radar/routes/core.py:83-92（並列に取得を直呼びし、例外は debug ログへ握り潰し）
**検証**: 未検証
**分類**: **DEFECT-PRESERVE**（D2 B-01: HIGH）。v3 は文脈非依存の単一取得経路 **MUST**

#### S4-NF-005: CB の状態機械・閾値・粒度
**挙動**: CB は `CLOSED / OPEN / HALF_OPEN` の 3 状態 MUST。CLOSED で連続失敗が閾値に達したら OPEN MUST。OPEN 中は回復遅延の経過後に HALF_OPEN へ遷移してプローブを 1 回だけ許可 MUST。プローブ成功で CLOSED へ復帰し失敗カウンタと回復遅延を初期値に戻す MUST。プローブ失敗で OPEN へ戻り**回復遅延を 2 倍にして上限で頭打ち MUST**。粒度は**センサー 1 基 MUST**（URL 単位・エンドポイント単位は MUST NOT）。**連続プローブ失敗の継続は通常の OPEN と区別して 1 度だけ通知 MUST**（回復見込みの無い障害の可視化）。
**閾値**: 連続失敗 5（`CB_FAILURE_THRESHOLD`）／初期遅延 300s（`CB_INITIAL_DELAY`）／上限 3600s（`CB_MAX_DELAY`）。いずれもハードコード、DB override 不可
**根拠**: radar/sensors/base.py:17-20,78-132、radar/scheduler.py:127-134
**検証**: tests/test_engine.py（CB 開閉閾値）
**分類**: CORE

#### S4-NF-006: CB 状態と運用状態は再起動を跨いで保持しなければならない
**挙動**: CB の開閉状態・失敗カウンタ・回復遅延、および重複抑止のクールダウン集合・重複排除集合は**永続 MUST**。再起動で初期化されると、障害中の外部ソースへ即座に再突入し、抑止済みの重複アラートが再送出される。
**根拠**: radar/sensors/base.py:34-38（プロセス内変数）、radar/persistence.py:65-108（**復元対象はキャッシュのみで CB 状態を含まない**。キャッシュも取得周期の 3 倍を超えた分は破棄）、radar/convergence_tracker.py:50、radar/sensors/rss_narrative.py:59
**検証**: 未検証
**分類**: **DEFECT-PRESERVE**（D2 B-05）。**再起動が事実上の「CB 全解除」手段になっている**

#### S4-NF-007: センサー健全性の状態値と導出順序
**挙動**: 各センサーは健全性を公開 MUST。導出は上から順に評価し最初に成立したものを採る MUST: `DISABLED`（運用者が無効化）→ `CIRCUIT_OPEN`（CB が OPEN）→ `DEGRADED`（部分取得成功）→ `ERROR`（直近取得が失敗）→ `STALE`（キャッシュ有りで鮮度切れ）→ `INITIALIZING`（キャッシュ無しで鮮度切れ）→ `OK`。健全性の**変化時にのみ**通知を送出 MUST（毎周期の再送は MUST NOT）。
**閾値**: 鮮度切れ = `経過秒 > poll_interval × 3`（ハードコード）
**根拠**: radar/sensors/base.py:134-148,66-67、radar/scheduler.py:111-117、radar/engine.py:44-60
**検証**: tests/test_sensor_tier_exposure.py（管理面への露出 3 tests）
**分類**: CORE

#### S4-NF-008: 劣化は除外ではなく確信度の減衰で表現する
**挙動**: 健全性は 0.0–1.0 の確信度係数へ写像 MUST。確信度は**健全性係数 × 標本充足係数 × ベースライン被覆係数**とし 1.0 で上限クリップ MUST。寄与スコアは確信度を乗じてから合算 MUST。これが degraded の一般原則である — 劣化した入力は減衰で扱い、劣化していること自体を結論に付記 MUST（NP5+8）。
**閾値**: 健全性係数 `OK 1.0 / DEGRADED 0.8 / STALE 0.5 / INITIALIZING 0.1 / ERROR 0.0 / CIRCUIT_OPEN 0.0 / DISABLED 0.0`。標本係数 `0.3 + 0.7 × (n / CONFIDENCE_MIN_SAMPLES)`、ベースライン係数 `0.5 + 0.5 × (b / CONFIDENCE_MIN_SAMPLES)`、`CONFIDENCE_MIN_SAMPLES` 既定 10
**根拠**: radar/sensors/base.py:149-171、radar/config.py:455、radar/engine.py:76
**検証**: tests/test_engine.py::TestConvergenceGating（最小確信度による収斂ボーナスのゲート）
**分類**: CORE

#### S4-NF-009: 欠測を「健全」と解釈してはならない
**挙動**: センサー欠測・取得失敗・確信度 0 を、**安全側（脅威なし）の観測値に置換しては MUST NOT**。欠測は欠測として伝播し、結論側で「その領域は観測できていない」と表明 MUST（NP1・NP5+8）。**欠測センサー数は結論の品質メタに載る指標 MUST**。
**根拠**: **反例 3 種を実測確認** — radar/routes/core.py:917-921（センサー未登録時の確信度を **1.0（満点）** で返す）、S1-scoring-core §4-A2（センサー 0 基のドメイン確信度が既定 1.0）、§4-A3（欠測を健全値 1.0 に読み替える fail-open）。加えて radar/sensors/base.py:159-160 により確信度 0 のセンサーは**加点が消えるだけ**で、欠測数はスコア側の指標に載らない
**検証**: 未検証
**分類**: **DEFECT-PRESERVE**

#### S4-NF-010: LLM は任意依存であり、不在でも採点は成立しなければならない
**挙動**: LLM 推論基盤は**任意依存 MUST**。既定は無効であり、無効時・接続不能時にも採点と結論導出は**完走 MUST**。LLM 不在は「LLM 由来の寄与が 0」として扱い、エラーとして採点を中断しては MUST NOT。可用性判定は例外を真偽値へ収束させる MUST（接続拒否・DNS 失敗・timeout をすべて「利用不可」に畳む）。1 呼出しは有限 timeout で打ち切り MUST、その値は**再起動なしで反映 MUST**。**LLM 不在によるセンサーの早期 return を「成功」として記録し CB を開かないこと MUST**（LLM の不在は外部データ源の障害ではない）。
**閾値**: `LLM_ENABLED` 既定 **false**、`LLM_HOST` 既定 `http://localhost:11434`、`LLM_MODEL` 既定 `llama3.2:3b`、生成 timeout `LLM_TIMEOUT` 既定 **30s**（DB override 可）、可用性判定 **5s 固定**、**リトライ 0 回**
**根拠**: radar/config.py:646-649,1187-1210、radar/llm_client.py:33-44,410-441,491-492,520,608,526-531。LLM 依存センサー 11 基が可用性ガードで早期 return（例: radar/sensors/ground_osint_sensor.py:115-119）
**検証**: 未検証
**分類**: CORE。早期 return が `DEGRADED`（係数 0.8）を招く副作用は ACCIDENTAL（§4-A2）

#### S4-NF-011: 定期ジョブのスケジュールは永続でなければならない
**挙動**: 日次・週次などの低頻度ジョブは、**次回実行時刻または最終実行時刻を永続化して駆動 MUST**。プロセス内カウンタの剰余で起動時刻を決める方式は **MUST NOT**（再起動でカウンタが 0 に戻り、高オフセットのジョブが一度も実行されない）。
**根拠**: radar/scheduler.py:175,179（毎時ワーカのローカルカウンタ。周期 3600s）、剰余 1〜12 で駆動する日次ジョブ **12 本**（:258,276,314,335,359,379,404,428,454,480,531,604,633）。DB に実行時刻を保持する表は **0 件**
**検証**: 未検証
**分類**: **DEFECT-PRESERVE**（D2 F-01: HIGH）。実測（2026-08-04）で稼働 9h・カウンタ 9 まで到達し、オフセット 10-12（提案ライフサイクル、追跡監視、再処理）は当該稼働では未実行

#### S4-NF-012: 起動時に未実行の定期ジョブを補償実行しなければならない
**挙動**: 起動時、各定期ジョブについて**最終実行時刻からの経過が周期を超えていれば 1 回だけ補償実行 MUST**。補償実行は通常実行と同一経路を通り、補償である旨を記録 MUST。同一周期内の多重実行は MUST NOT。
**根拠**: 現行の起動時処理は状態復元・整合性検査・センサー取得リトライ（`[60, 300, 600]`）のみで、**日次ジョブの補償は無い**（radar/\_\_init\_\_.py:280-285、radar/scheduler.py:151-157）。radar/scheduler.py:632-634 は補償しない方針を明示的に自認している
**検証**: 未検証
**分類**: **DEFECT-PRESERVE**（D2 F-01 の対処要件）

#### S4-NF-013: 永続層は自己修復し、消失を前提に設計する
**挙動**: 起動時に永続層の整合性を検査 MUST。破損時は**破損ファイルを退避して新規作成 MUST**（起動不能で停止しては MUST NOT）。これが許されるのは**永続データが上流から数時間で再構築可能**であることを前提とするため、**この前提を破る種類のデータ（較正結果・アナリスト判断・台帳）は別の保全戦略を持つ MUST**。
**根拠**: radar/database.py:1595-1630
**検証**: 未検証
**分類**: CORE。**較正・台帳の保全戦略は未定義** → §6 未決事項 2

#### S4-NF-014: 保護機構の障害はリクエスト処理を落としてはならない
**挙動**: レート制限機構および監査記録の内部障害は、**本体リクエストの成功を妨げては MUST NOT**。ただし障害は必ず記録し、無制限開放へ degrade した事実を運用面から観測可能に MUST（沈黙 degrade は MUST NOT）。
**根拠**: radar/\_\_init\_\_.py:170（レート制限器の障害を握り潰す設定。コメントに NP3 と明記）、radar/audit_middleware.py:144-145
**検証**: 未検証
**分類**: CORE。監査失敗の可観測性は現行では不足（S4-NF-031）

### 2.2 セキュリティ

#### S4-NF-015: すべての API パスは既定で認証を要求する（ホワイトリスト方式）
**挙動**: API 名前空間配下の全経路は**既定で認証必須 MUST**。認証不要な経路は**明示的な公開リストに列挙されたものだけ MUST**（ブラックリスト方式は MUST NOT）。公開経路はログイン・トークン更新・静的資産配信・起動時設定取得に限る MUST。
**根拠**: radar/\_\_init\_\_.py:204-220（一律強制）、:195-202（公開 6 経路）
**検証**: tests/test_auth.py（JWT 強制）
**分類**: CORE

#### S4-NF-016: アクセストークンとリフレッシュトークンの寿命
**挙動**: 短命のアクセストークンと長命のリフレッシュトークンの 2 段構成 MUST。両者の寿命は設定可能 MUST だが、**実行時変更を許さない不変値として扱う MUST**（実行中に変えると既発行トークンの寿命が不整合になる）。
**閾値**: アクセス 3600s（`JWT_ACCESS_EXPIRES`）／リフレッシュ 86400s（`JWT_REFRESH_EXPIRES`）。ともに immutable + bootstrap、DB override 不可
**根拠**: radar/auth.py:205-206、radar/config.py:1391-1403
**検証**: tests/test_auth.py::test_refresh_via_cookie_returns_new_access_token
**分類**: CORE

#### S4-NF-017: リフレッシュトークンはブラウザの JavaScript から読めてはならない
**挙動**: リフレッシュトークンは **httpOnly / SameSite=Strict / Secure / パス限定の Cookie でのみ配送 MUST**。応答 JSON 本体に含めては MUST NOT。Cookie を用いる経路には **CSRF 二重送信対策を既定で有効化 MUST**。
**閾値**: `JWT_COOKIE_SECURE` 既定 true、CSRF 既定有効（`RADAR_JWT_CSRF_DISABLED` 既定 false）
**根拠**: radar/auth.py:223-252、:489-495（応答 JSON からの除去）
**検証**: tests/test_auth.py::test_login_sets_httponly_secure_samesite_strict / ::test_refresh_without_cookie_rejected
**分類**: CORE

#### S4-NF-018: トークンは失効可能でなければならない
**挙動**: 発行済みトークンは (a) 明示的ログアウトによる個別失効、(b) パスワード変更による当該利用者の全セッション一括失効 の 2 経路で無効化できる MUST。失効判定は**トークン検証のたびに実施 MUST**（発行時点のチェックのみは MUST NOT）。
**根拠**: radar/auth.py:265-280（検証時の 2 段チェック）、:519-535、:697-700
**検証**: tests/test_auth.py::test_logout_revokes_token
**分類**: CORE

#### S4-NF-019: 権限は 3 階層のロールで表現し、書込経路を明示的にゲートする
**挙動**: ロールは `admin` / `analyst` / `viewer` の 3 値 MUST。状態を変更する経路は**必要ロールを宣言的に指定 MUST**。ロール不一致は 403、未認証は 401 と区別 MUST。**自分自身のロール変更は拒否 MUST**（権限昇格の自己適用防止）。
**根拠**: radar/auth.py:379-392（宣言的ゲート、適用 15 箇所）、radar/routes/\_\_init\_\_.py:53-67、radar/auth.py:611
**検証**: tests/test_analyst_permissions.py（3 ロール × 全 endpoint の権限行列 18 tests）、tests/test_auth.py::test_cannot_change_own_role / ::test_register_requires_admin_role
**分類**: CORE

#### S4-NF-020: パスワードはメモリハード関数でハッシュ化する
**挙動**: パスワードは **argon2id で保存 MUST**。旧方式のハッシュが残存する場合は**ログイン成功時に透過的に再ハッシュ MUST**（利用者への再設定要求は MUST NOT）。旧方式の照合は**定数時間比較 MUST**。ソルトは呼出しごとに暗号論的乱数から生成 MUST。ハッシュ実装が利用不能な環境では旧方式へ縮退しつつ WARNING を出す MUST。
**閾値**: argon2id RFC 9106 第 2 推奨（m=64MiB, t=3, p=4）／旧方式 PBKDF2-HMAC-SHA256 100,000 回
**根拠**: radar/auth.py:91-121,124-152,468-477
**検証**: tests/test_auth.py

## 7. 未決事項

1. **S4-NF-026（CSP の inline 排除）は単独では達成できない**。inline ハンドラ 136 箇所の撤廃
   = UI モジュール化（D2 A-07）と同一作業であり P のフロントエンド層設計に従属する。本書は要件だけを固定する
2. **S4-NF-013 が前提とする「永続データは数時間で再構築可能」は較正結果・アナリスト判断・
   台帳には成り立たない**。何を復旧不能と諦め何を別戦略（多重化・外部保管）で守るかの区分が
   未定義。D4 のデータ資産分類と突き合わせて P で決める
3. **S4-NF-066（構造目次の自動生成）を v3 でも継続するか**。S4-NF-062（800 行上限）が達成
   されれば存在理由が減衰する。ただしモジュール間の依存方向の可視化としては別途価値がある
4. **単独運用前提（S4-NF-057）の妥当性**。NP7 は本ツールを「組織的なインテリジェンス判断
   プロセスにおける一つのノード」と定義しており複数アナリスト運用を排除していない。
   「3 点同時見直し」要件は移行コストを明示したものだが、備えの範囲はオーナー裁定
5. **A8 が示す非機能要件の結合**。個々には低リスクの 3 判断（再ビルド必須 / 揮発スケジュール /
   揮発 CB）が組み合わさり「頻繁な UI 修正期間中は日次ジョブが走らず CB も毎回全解除される」
   実害を生んだ。S4-NF-006 と S4-NF-011 で解消するが、**同型の「独立に見えて結合している
   非機能要件の組」が他に無いかは未点検**
