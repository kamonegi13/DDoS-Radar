# S1 — 採点ティック・パイプライン 挙動仕様

**スコープ**: 1 回の採点ティックで「何がどの順で起きるか」。センサーキャッシュ読出し → ゲーティング
（ミュート / noise exclusion / confidence suppression）→ 収斂スコア → sequence event 登録 →
シナリオ採点 → conclusions 派生 → 永続化 → cache 書込み → WS emit、および周期ジョブ
（fetch ループ / CB 駆動 / cleanup / 較正 cron / persistence）の起動条件。

**隣接仕様との境界**: 数式・閾値そのものは [S1-scoring-core.md](S1-scoring-core.md) が持つ（本書は参照のみ）。
結論 envelope / calibration_status は S1-conclusions、センサー個別の状態判定は S1-sensors-*、
API レスポンス形状は S2。

**規約**: [S0-spec-conventions.md](S0-spec-conventions.md)。分類 CORE / ACCIDENTAL / DEFECT-PRESERVE。

**一次ソース**: D5 の判定どおり本領域は **専用テストがほぼ無い**（core.py / scheduler.py / state.py が
いずれも「無テスト」認定）。よって一次ソースは実装読解であり、§6 は大半が GAP になる。
これは本書の欠陥ではなく**現行資産の欠陥の可視化**である。

---

## 1. 用語

CLAUDE.md の用語定義（country / scenario / participant / focused / background / C-lite）に従う。本書固有:

- **採点ティック**: 観測の 1 スナップショットから全 scorable シナリオのスコアと TL を導出し、
  副作用（永続化・通知・cache 更新）を完了させるまでの一連の処理
- **ゲーティング**: 観測を採点に算入するか否かの判定。ミュート / noise exclusion / confidence suppression の 3 系統
- **primary_ec / secondary_ecs**: dual-core シナリオ（core_country=null）で per-country 参照に使う代表国と残り
- **transient 状態**: プロセス内メモリにのみ存在し再起動で消える状態（採点 cache、focus 登録簿）
- **周期ジョブ**: 一定周期で起動する背景処理。**日次ジョブは時刻でなく「時間毎サイクル通し番号のオフセット」で割当**

## 2. 挙動条項

### 2.1 ティック起動と focus 解決

### S1-PIPE-001: 採点はティック駆動でなければならない
**挙動**: 採点ティックは**スケジューラが一定周期で起動する MUST**。読み取り API は直近ティックの結果を返すのみで、**採点を起動しては MUST NOT**。
**根拠**: radar/routes/core.py:507-3173（GET `/api/threat_data` に全段が同居）
**検証**: 未検証
**分類**: **DEFECT-PRESERVE** — 現行は GET が採点副作用を駆動（D2 A-01: CRITICAL）。採点頻度がクライアントのポーリングに従属し、無観測時は履歴が欠落する。現行はこれを背景ワーカの HTTP 自己呼出で補償（S1-PIPE-046）。

### S1-PIPE-002: focused scenario の解決は 3 段フォールバック
**挙動**: 要求された focus が (a) 存在し (b) `is_scorable` ならそれを focused とする **MUST**。不成立なら既定シナリオ（`DEFAULT_FOCUSED_SCENARIO`）、それも不成立なら **scorable 集合の先頭 MUST**。scorable が 0 件なら**結論不可を返す MUST**（TL を捏造しない）。
**根拠**: radar/routes/core.py:514-524
**検証**: 未検証
**分類**: CORE

### S1-PIPE-003: 直近の focus は TTL 付きで登録し取得対象に反映する
**挙動**: focused 確定のたび `(scenario_id → 現在時刻)` を登録 **MUST**。登録簿は **TTL 1800s 以内**のみ有効、**同時保持上限 4 件**で超過時は**最古から破棄 MUST**。取得対象は「有効 focus 群の participants の**和集合** + 既定シナリオ」**MUST**。
**根拠**: radar/state.py:28-62、radar/scheduler.py:33-63
**検証**: 未検証
**分類**: CORE（NP1: アナリストが見ている対象のセンサーを止めない）

### S1-PIPE-004: セッション重みオーバーレイは analyst/admin のみ・非永続
**挙動**: リクエスト単位の participant 重みオーバーレイは analyst/admin のみ適用 **MUST**、viewer では無視 **MUST**。パース失敗は警告記録のうえ無視し、**ティックを失敗させて MUST NOT**。オーバーレイは focused の採点にのみ効き、background は常に store 由来のベースライン重みを使う **MUST**。
**根拠**: radar/routes/core.py:536-552, 2142
**検証**: 未検証
**分類**: CORE

### S1-PIPE-005: 再採点の起動条件は 3 つの論理和
**挙動**: 直近ティックからの経過が `SCORE_REFRESH_SEC`（既定 60s）を**超過**、または force 要求、または **focus が直前ティックと異なる**、のいずれかで再採点 **MUST**。いずれも不成立なら直近 cache を返す **MUST**（3 つ目は focus 変更時に最大 60 秒古い TL を見せないための条件）。
**根拠**: radar/routes/core.py:660-669
**検証**: 未検証
**分類**: CORE。v3 ではティック駆動化により (a)(c) が消え force のみ残る（S1-PIPE-001）

### S1-PIPE-006: force 取得は 3 状態・ロール制限・単一飛行・許可リスト・時限
**挙動**: force は `off` / `snapshot`（cache TTL のみ迂回）/ `sensors`（snapshot + 背景取得）の 3 状態 **MUST**。`off` 以外は analyst/admin に限定 **MUST**（viewer 要求は `off` に降格）。`sensors` は**同時 1 本のみ MUST**。取得対象は**許可リストの高速センサーのみ MUST**、全体 **45 秒の時限**で超過分は通常取得に委ねる **MUST**。取得結果は**次ティック以降に反映 MUST**。
**閾値**: 許可リスト 6 件、時限 45s、4 並列
**根拠**: radar/routes/core.py:59-96, 599-618, 649-653
**検証**: 未検証
**分類**: **DEFECT-PRESERVE** — 許可リストの識別子 2 件（`cf` / `ioda`）が実センサー名（`cloudflare_radar` / `ioda_bgp`）と**一致せず永久に不発**。最重要 2 センサーが force 取得から構造的に外れている。v3 では許可リストは実センサー識別子への参照整合性を持つ **MUST**（D2 未登録の新規発見）。

### 2.2 センサーキャッシュ読出し

### S1-PIPE-007: キャッシュ読出しは純粋でなければならない
**挙動**: ティック冒頭のセンサーキャッシュ収集は**副作用を持たない MUST NOT**（取得を起こさない・DB を書かない）。未登録センサーや欠落キーは**空の既定値**に落とす **MUST**。ティックは「その瞬間にキャッシュにある観測」のみを入力とする **MUST**。
**根拠**: radar/routes/core.py:383-504
**検証**: 未検証
**分類**: CORE（NP3: 取得の遅延・失敗が採点を止めない構造の要）

### S1-PIPE-008: 無効・未登録センサーは DISABLED として明示的に記録する
**挙動**: センサーが未登録または無効のとき、**沈黙させず** `DISABLED` 状態・スコア 0 の観測として証拠行に残す **MUST**。「観測が無い」と「観測して何も無かった」を区別可能にするため。
**根拠**: radar/routes/core.py:995, 1072, 1099, 1115, 1121, 1128
**検証**: 未検証
**分類**: CORE（NP5+8: 結論不可の明示）

### 2.3 ゲーティング（本仕様の核心）

### S1-PIPE-009: ゲーティングの入力・判定順序・出力（真理値表）
**挙動**: 観測 1 件を採点入力に変換する処理は以下の**順序で MUST**:
(1) アナリストミュート判定 → (2) 呼出側抑制フラグ（天候ノイズ / 宇宙天気 / 背景ノイズ分類）との**論理和** →
(3) 抑制理由の確定（**アナリストミュートが最優先**。ミュート時は呼出側理由が**上書き消失 MUST**）→
(4) noise exclusion 突合（**手順 1-2 でまだ抑制されていない場合のみ適用 MUST**）→
(5) 文脈分類（方向 / 時間 / 空間 / 対象）を**抑制の有無にかかわらず算出 MUST** →
(6) **抑制されていても証拠行に必ず残す MUST**（スコアは 0 化しない）→
(7) 発火かつ抑制のとき隠蔽シグナル台帳へ記録 **MUST** → (8) 戻り値 = `発火 かつ 非抑制` **MUST**。

真理値表（`M`=アナリストミュート、`S`=呼出側抑制、`N`=noise 規則一致、`F`=発火）:

| M | S | N | F | 抑制フラグ | 抑制理由 | noise 適用記録 | 隠蔽台帳 | 戻り値 |
|---|---|---|---|---|---|---|---|---|
| F | F | F | T | false | （呼出側の理由＝通常 null） | — | — | **true** |
| F | F | T | T | true | noise 規則（規則 ID 付き） | **追加** | **記録** | false |
| F | T | F | T | true | 呼出側の理由 | — | **記録** | false |
| F | T | **T** | T | true | **呼出側の理由**（noise 理由は不採用） | **なし** | **記録** | false |
| T | * | * | T | true | アナリストミュート | **なし** | **記録** | false |
| F | F | F | F | false | — | — | — | false |
| F | F | **T** | F | **true** | noise 規則 | **追加** | — | false |
| * | * | * | DISABLED | — | — | — | — | false |

**根拠**: radar/routes/core.py:923-990
**検証**: 未検証（**この表全体が無テスト**）
**分類**: CORE。4 行目・7 行目の挙動は §4-A2 / §4-A3 でオーナー裁定に回す

### S1-PIPE-010: noise exclusion 規則の突合規則
**挙動**: 規則は `(sensor, country, pattern, expires_at)`。突合は**センサー識別子の完全一致**、**country が一致または規則側が空（全 country）**、**失効時刻が未設定または未来**、かつ **pattern が観測の表示文字列の部分文字列**であること **MUST**。最初に一致した規則を採用 **MUST**。突合の country は **primary_ec MUST**。
**根拠**: radar/database.py:5113-5139、radar/routes/core.py:943
**検証**: 未検証
**分類**: **DEFECT-PRESERVE** — 突合対象が「表示用に整形された文字列」のため、**表示文言を変えると運用中の除外規則が無言で効かなくなる**。v3 では**構造化された観測値フィールド**に対して突合 **MUST**。

### S1-PIPE-011: confidence suppression はゲーティングでなくスコア減算である
**挙動**: 情報源の主張信頼度が閾値未満のとき、**発火状態を維持したままスコアを 1 段階減算 MUST**（0 で下限）。減算の事実は観測の表示値に明示 **MUST**。抑制フラグは立てず、証拠行の抑制欄にも現れない **MUST**。
**根拠**: radar/routes/core.py:1333-1341
**検証**: 未検証
**分類**: **ACCIDENTAL**（§4-A4）— 「抑制」が 3 系統で同語異義

### S1-PIPE-012: センサー信頼度は健全性・標本数・ベースライン被覆の積
**挙動**: 信頼度は `健全性係数 × 標本係数 × ベースライン係数`（上限 1.0、小数 3 桁）**MUST**。健全性係数 `OK=1.0 / DEGRADED=0.8 / STALE=0.5 / INITIALIZING=0.1 / ERROR=CIRCUIT_OPEN=DISABLED=0.0`、**0 のときは即 0.0 を返す MUST**（他係数を評価しない）。標本係数は標本数 < 最小標本数なら `0.3 + 0.7 × (標本数/最小標本数)`、以上なら 1.0 **MUST**。ベースライン係数は同様に `0.5 + 0.5 × 比率` **MUST**。
**閾値**: `CONFIDENCE_MIN_SAMPLES` 既定 10
**根拠**: radar/sensors/base.py:149-171、radar/routes/core.py:917-921
**検証**: 未検証
**分類**: CORE。**センサー未登録時に 1.0 を返す**点は §4-A5

### 2.4 sequence event 登録

### S1-PIPE-013: sequence event はゲーティング通過を条件とする
**挙動**: sequence event の登録は、根拠となった観測に対するゲーティングが **true を返した場合のみ MUST**。抑制・ミュートされた観測から登録して **MUST NOT**。
**根拠**: radar/routes/core.py:1203, 1223, 1254, 1278, 1350, 1638, 1704, 1774, 1813（CLAUDE.md §5 のレイヤー境界規約と一致）
**検証**: 未検証
**分類**: CORE

### S1-PIPE-014: 複合条件イベントは全構成観測の通過を要求する
**挙動**: 複数センサーの同時成立を意味するイベントは、**構成する全観測のゲーティングが true であること MUST**（例: 協調型 DDoS は「協調検知」と「ボットネット重複」の両方）。
**根拠**: radar/routes/core.py:1309-1310
**検証**: 未検証
**分類**: CORE（NP2 の実装）

### S1-PIPE-015: 事後走査型イベントは証拠行の発火・非抑制で判定する
**挙動**: 複数センサーの結合から導かれるイベント（検閲チェーン等）は証拠行集合を走査し、**発火かつ非抑制の行が両方存在する場合のみ登録 MUST**。この経路は戻り値でなく証拠行の最終状態を根拠とするが、**判定結果は同値でなければ MUST**。
**根拠**: radar/routes/core.py:1594-1600
**検証**: 未検証
**分類**: CORE

### S1-PIPE-016: 登録先国の解決規則
**挙動**: 単一 core シナリオでは常に core country 1 件 **MUST**。dual-core では、**シナリオ全体に対称な事象**（ナラティブ急増・協調 DDoS 等）は**全 effective core に登録 MUST**、**per-country 事象**は **primary_ec のみ MUST**（secondary のセンサーデータを検査していない以上、secondary の連鎖に登録すると出所を偽る）。空文字・重複は除去し**入力順を保存 MUST**。
**根拠**: radar/scoring.py:94-124
**検証**: **tests/test_seq_fire_targets.py::TestResolveSeqFireTargets（8 件全て）**

### S1-PIPE-017: 国が確定しない event は登録しない
**挙動**: 登録先 country が空の場合、event を**登録して MUST NOT**（後で相関できない空 country 行で台帳を汚さない）。
**根拠**: radar/scoring.py:170-174
**検証**: 未検証
**分類**: CORE

### S1-PIPE-018: secondary belligerent の per-country event は独立の証跡で登録する
**挙動**: dual-core で secondary の領域に固有のヒットが存在する場合、**primary の観測がゲートを通過していることを前提に**、secondary 自身のヒット集合を根拠として **secondary 宛に別途登録 MUST**。dedup 窓は primary と独立 **MUST**（primary への登録が secondary を沈黙させない）。
**根拠**: radar/routes/core.py:1263-1275, 1290-1300
**検証**: tests/test_per_ec_event_firing.py::TestSelectSecondaryEcHits（8 件、**ヒット抽出のみ**）

### S1-PIPE-019: event の重複排除と保持窓
**挙動**: 同一 (country, event 種別) は **dedup 窓（既定 300s）以内なら登録しない MUST**。登録のたびに保持窓（`SEQUENCE_WINDOW` 既定 86400s）より古い event を掃除 **MUST**。ボーナス算出式は S1-SCORE-021 / 022。

### 2.5 収斂スコア → シナリオ採点

### S1-PIPE-020: 収斂算出の実行順序
**挙動**: 全観測が出揃った後、**(1) 出所連鎖の付与 → (2) ドメイン集計 → (3) 陽動検知 → (4) 共起感度ブースト → (5) 信頼度加重合計 → (6) 収斂ボーナス → (7) 三角測量ボーナス → (8) 沈黙的乖離検知** の順で **MUST**。各段の数式は S1-SCORE-001〜006。
**根拠**: radar/routes/core.py:1937-1991
**検証**: 未検証（各段の**数式**は test_engine.py が検証。**順序**は未検証）
**分類**: CORE

### S1-PIPE-021: 派生観測を追加したら集計を再実行する
**挙動**: 検知器が新たな証拠行を追加した場合、**ドメイン集計・合計・収斂ボーナスを再計算 MUST**。追加前の値を最終結果として用いて **MUST NOT**。
**根拠**: radar/routes/core.py:1985-1991
**検証**: 未検証
**分類**: **ACCIDENTAL**（§4-A7）— 現行は沈黙的乖離のみ再計算し、陽動検知（スコア 0）では行わない

### S1-PIPE-022: ボーナス積み上げ後の合計に上限を課す
**挙動**: sequence ボーナス・時間的整合ボーナス加算後、合計を **15 で上限クリップ MUST**（ボーナス積み上がりで TL1 の閾値天井を無意味にしないため）。
**閾値**: 合計上限 15（ハードコード）
**根拠**: radar/routes/core.py:1993-1996
**検証**: 未検証
**分類**: CORE

### S1-PIPE-023: シナリオ採点用 signal 集合の構築順序と出所
**挙動**: signal 集合は以下を**この順で結合 MUST**: (1) 証拠行のうち **LLM インテル由来を除いたもの**（S1-SCORE-018 の採択条件を適用）/ (2) **focused 限定センサー**の観測には focused の core country（dual-core なら primary_ec）を付与 **MUST** / (3) **全 country 走査型センサー**の core 以外の異常は per-country signal として**別途注入 MUST**（background が自分の participants の異常を見られるように）。注入時も天候抑制を**一貫して適用 MUST** / (4) LLM インテル（確認済み・TTL 内・時間減衰済み）を country 重み付きで注入 **MUST** / (5) 背景観測キューを排出して注入 **MUST**。
**根拠**: radar/routes/core.py:2025-2123
**検証**: 未検証
**分類**: CORE

### S1-PIPE-024: signal 注入の失敗は沈黙させてはならない
**挙動**: LLM インテル注入・背景観測排出が例外で失敗した場合、**警告記録と自己評価台帳への失敗計上を MUST**。無言で空集合として続行して **MUST NOT**（排出は破壊的操作であり、握り潰すと観測が永久に失われる）。
**根拠**: radar/routes/core.py:2076-2088, 2109-2123
**検証**: 未検証
**分類**: CORE（NP1 + AP3。2026-05-01 監査 SF2/SF3 の修正）

### S1-PIPE-025: 1 ティックで全 scorable シナリオを採点する
**挙動**: ティックは focused だけでなく**全 scorable シナリオを採点 MUST**。focused は full、それ以外は lite として採点し（S1-SCORE-016）、**同一の signal 集合を共有 MUST**。
**根拠**: radar/routes/core.py:2129-2147

### S1-PIPE-026: focused のみ追加ボーナスを折り込み TL を再導出する

**根拠**: radar/routes/core.py:2149-2200

## 4. ACCIDENTAL（オーナー裁定待ち）

| ID | 事象 | 裁定の論点 |

| A1 | アナリストミュートがリクエストのクエリパラメータで毎回渡され、永続化されない | ミュートは運用判断であり監査対象のはず。NP6 上、誰がいつ何をミュートしたかが残らない |
