# P9 — UI/UX 再設計: 理解可能性の回復

**発端**: オーナー実見フィードバック(2026-08-13)—「UI がわかりづらい。現状では何が表されて
いるのかがよくわからない」。
**位置づけ**: P8 の導出(アナリスト一次ループ・Tier 構造・O→画面トレーサビリティ)は**正しく、
不変**。壊れているのは実装がループを画面に落とすときの 3 つの解釈であり、本書はそれを裁定し直す。
本書の裁定も「**推奨 = 実装既定**」(P6/P8 と同じ規律。覆す場合は本書を改訂する)。

---

## 1. 診断 — なぜ「何が表されているのか」わからないのか(現行実装の実測)

WP-4.2 の実装(`v3/ui/`)は仕様適合の内部品質が高い(純射影・誠実な状態語・空画面禁止)。
問題は**射影が正確であることと、画面が理解できることは別の性質**だという点にある。
NP6 は「導出を開示せよ」と言うが、開示は読者が読めて初めて開示である。

| # | 診断 | 実測根拠 |
|---|------|---------|
| **D-1** | **段階的開示の平坦化**。P8 の Tier 0/1/2 は「常時 / 1 クリック / 監査時」という**別々の画面**を意味していたが、実装は 5 ステージを 1 ページに縦積みした。10 秒で読むべき状況ボードの下に、監査用テーブル 7 枚(自己評価・センサー表・判断台帳・What-If・設定・ground truth)が常設され、「今見るべきもの」の区別が構造から消えた | `index.html:95-290` — `<main>` 直下に stage-1〜5 が全て同時表示 |
| **D-2** | **内部オントロジーの無定義提示**。カードとレーンが表示する語 — TL、severity、結論不可、scoring_mode、null-zone、C-lite、収斂 — は S 仕様の内部語彙であり、画面上に定義が無い。「TL4 / ELEVATED」は**答えではなく符号**。アナリストの問い「何か変わったか」に対する**文としての答え**が Tier 0 に存在しない(AP2 ナラティブは R6 レーン行にのみ供給) | `board.js:163-186` — カードは 12 フィールドの符号射影。summary 文スロットなし |
| **D-3** | **視覚階層の欠如**。全要素がほぼ同一の視覚重量(小型チップ・同サイズ表・同色調)。10 秒の問いに答えるには「支配的な 1 要素(シナリオ×TL の大型表示と変化の強調)」が必要だが、TL は他のフィールドと同格の 1 チップにすぎない | `v3.css` / カード DOM 構造 |
| **D-4** | **空状態が白紙**。冷起動シャドウでは board=結論不可、lane=空、Tier 2 テーブル=空。S1-UI-008(空画面禁止)により「空である」ことは言うが、「**この場所は何を表示する場所で、何が起きれば埋まるのか**」を言わない。初見者は画面の役割自体を学べない | 現行 emptyKey 群(`ui.board.empty.*` 等)は状態のみで役割を語らない |
| **D-5** | **「地理面」がリスト**。P8 §6 の問いは「異常は**どこで**起きているか」だが、実装は `<ul id="geo-markers">` の文字列リスト。座標をワイヤに載せない裁定(正しい)が「地理的表現を放棄する」に読み替えられた | `index.html:154-163`、`geo.js` |
| **D-6** | **未着地プレースホルダの露出**。`data-deferred="R11/C10/C8/C11/C12/C3"` の断片が本番ビューに説明なく散在し、画面全体の信頼感を下げる | `index.html:177-178, 284-287` |
| **D-7** | **「なぜ?」導線の断絶**。O-6(導出根拠)は NP6 の主役なのに、カード → 結論 → 導出ビューへの視覚的連鎖が無い。導出ビューは Tier 2 の 1 div として孤立 | `index.html:189-190` |

**総括**: P8 導出原則 1「画面はアナリストの問いに答える」に対し、実装は「サーバの値を正確に
射影する」で止まった。**射影は答えではない。**

### 1.2 第 2 回実見診断(2026-08-13、WP-4.3 着地後)

WP-4.3 は D-1〜D-7 を解消したが、オーナー実見は不合格 —「説明が抽象的で何を表しているのか
わからない」「事実を順に羅列しただけでは、アナリストの判断に寄与できていない」。§6 の規定
どおり診断を追記する。参照実装として、同一オーナーの姉妹ツール **kuebiko**
(`~/git/auto-post/frontend`)の UI を精査した — 以降の診断・裁定は kuebiko の実証済み
パターンを根拠に引く。

| # | 診断 | 実測根拠 |
|---|------|---------|
| **D-8** | **設計メタ言語の露出**。節見出しの下に「何か変わったか。今このツールを信じてよいか。(目標 10 秒)」というループ定義文がそのまま表示される。これは**ツールが自分の設計意図を語る文**であって、状況を語る文ではない。「(目標 10 秒)」は §6 の受け入れ基準であり画面語ではない。オーナーは「何を表しているのかわからない」と正しく読めなかった。kuebiko の見出しは全て内容語(「今日の要注意」「今動いているアクター(急増/新規)」)で、メタ言語の露出はゼロ | `strings.js:41-50`(`ui.stage.*_q` 全 5 件)、`index.html:148,171,201,253,270` |
| **D-9** | **偽りの順序性**。stage 番号 1〜5(`.stage-n`)とオンボーディングの①〜⑤が「順番に読み進めるもの」に見える。P8 §1 のループは**並列の問い**であって手順ではない。番号はドキュメント上の整理記号であり、画面構造に写した瞬間に誤った読み方を指示する | `index.html:146,169,199,251,268` の `<span class="stage-n">`、`strings.js:64-68` |
| **D-10** | **Tier 0 に地理がゼロ**。シナリオカードは数値と符号のみで、**どの地域の話なのか**が画面から読めない。タイル地図(WP-4.3d)はシナリオ面(Tier 1)にのみ在り、しかも focused シナリオしか見られない。v1 は地図を常設して状況の地理的把握を支えていた — その機能が v3 では初期画面から消えた | `index.html:239-246`(tilemap は `#view-scenario` 内のみ)。カードの地理情報は participantCount(数)と adversaries(ISO2 生値)だけ(`board.js:264-267`) |
| **D-11** | **数値の由来不在**。TL 4 という数字が**どこの何から算出されたのか**(どのドメインの・何件の観測・full/lite のどちらの採点範囲か)がカード上に無い。scoring_mode は無定義の符号チップ 1 個。kuebiko はティアバッジの隣に算出規則(`tier_rule`)平文と因子内訳を常置し、「数字だけを出す」ことがない | `board.js:236-269` — カードモデルに由来フィールドなし。ドメインバーは focused のみ(`board.js:263`) |
| **D-12** | **羅列は判断素材ではない(総括)**。状況ビューは「サマリ文 → カード列 → レーン」の縦一列で、事実が上から順に流れるだけ。判断には**比較(シナリオ間)× 変化(時間)× 空間(地理)× 根拠(由来)を 1 つの構図で重ね合わせる**ことが要る。kuebiko のダッシュボードは「KPI 帯+要注意リスト+構成変化」を 1 画面に構図として配置し、各要素からドリルダウンが伸びる | `index.html:116-182` — `#view-situation` は単一カラムの直列 |

**D-8/D-9 の根本原因**: 設計文書(P8 §1)の語彙を UI にそのまま射影した。D-1〜D-7 の根本原因
(「サーバの値の正確な射影」で止まった)と同型 — 今度は**設計文書の正確な射影**で止まった。
射影元がサーバ値から設計文書に変わっただけで、「射影は答えではない」の再演である。

### 1.3 第 3 回実見診断(2026-08-13 深夜、WP-4.4 着地後)

オーナー実見: **不合格** —「全体的にゴチャゴチャしていてわかりづらい」「(タイル地図を見て)
これだったら実際の地図を出して色を変えたほうがいいのでは」「v1 の洗練された UI が失われている」。

| # | 診断 | 実測根拠 |
|---|------|---------|
| **D-13** | **箱の地図は地図ではない**。国タイル・グリッド(WP-4.3d/4.4b)は「地域ブロックに並べた箱」であり、地理的直観(隣接・距離・形)を運ばない。v1 は Leaflet + CARTO ダークタイルの**実地図**(`radar.js:1732-1741`)に国サークルを置いており、オーナーはそれを洗練と評価していた。タイル地図はその代替になっていない | スクリーンショット実見。破線枠・地域箱・×N バッジが視覚ノイズとして加算 |
| **D-14** | **視覚的過密**。カード 1 枚に TL ブロック+変化文+メタ行+国旗ストリップ(2 行に折返し)+ドメインバー+由来行+採点範囲行+ⓘ 群が同居し、行数・枠数・破線が氾濫。kuebiko から**情報の型**(由来並置・内容語見出し・正直な状態語)は移植したが、**視覚的抑制**(1 カード= 1 支配要素+従属情報、バッジは 2 個+「+N」、控えめな線)を移植しなかった | スクリーンショット実見。kuebiko `rowBadges()` は行あたりバッジ 2 個+`+N` に制御(`ThreatsTab.tsx:307-315`) |

**裁定(D-13 への)— 座標の扱いの改訂**: 「**ワイヤに座標を載せない**」(サーバは座標を供給
しない)は不変。「**ブラウザに座標を持たない**」(geo.js の裁定)は本診断で改訂する:
国の**重心座標は表示専用のフロント資産**として `map_coords.js` に持つ。geo.js の懸念は
「バックエンドが drift を見張れない第 2 の読者」だったが、答えは見張りを CI に置くこと —
`tests/ui_v3/test_map_coords.js` が `geo_data.json` の `COUNTRY_COORDS` と機械照合し、
drift は commit 時に検知される。国重心は deployment データではなく普遍の表示定数であり、
結論の導出には一切関与しない(タイル配置表と同じ資産クラス、P9 §3.4 の延長)。

### 1.7 定義改訂 — 「表現」の公理化(2026-08-14、オーナー裁定)

6 巡の実見の根本原因分析から、**ツール定義そのものに欠けていた公理**が特定された。
オーナーの理解「シグナルから世界情勢を**表現**し、総合してスコアリングするシステム」に対し、
CLAUDE.md の定義文は検知(入力)と評価結論(出力)しか書いておらず、**表現という中間成果物が
無かった**。ADR-V3-003(実装からではなく定義から導出)に忠実な P8 は、定義に無いものを導出
できない — v1 の地図中心・操作豊富な UI はこの不文の公理から育っており、公理が文書化されて
いなかったために greenfield で消えた。6 巡の実見サイクルは欠けた公理の経験的補給だった。

**裁定**(オーナー承認 2026-08-14): CLAUDE.md 定義文を改訂(第 1 文に表現句、第 5 文を追加)し、
**NP9(表現原則)**を新設。実測の土台: シャドウ台帳でセンサー 24 基・**150 か国**・22,426 観測行
(cyber 5 / info 8 / physical 11 基)— 観測面は世界規模、評価はシナリオ限定という非対称を定義に明記。

**提案の敵対的評価で反映した修正**:
- **濃淡開示**: C-lite では focused 参加国だけが密に掃引される。観測レイヤが件数だけを描くと
  「見えた結果」と「見に行った回数」を混同させる(G-17 の新形)。NP9 (b) に掃引努力の開示を含めた
- **優先順位**: NP1 → NP4・NP9(成果物対)→ NP6 → …。NP6 に「透明性が担保できない表現は
  出さない」を対称追加(v1 What-If が壊れた線の再封印)
- **明確化**: 決定論は台帳→画面の区間の性質 / cutover 条件(ADR-V3-011)に波及しない /
  表現に結論不可状態は無い(空 = 観測なし/掃引なし)

**NP9 から導出される原則 R-H**: 一次数値には、それを操作して関係・時間・感度を体感できる導線を
併置する(「操作が関係を見せる」)。v1 の相関線・Replay・What-If 操作面はこの原則の実装だった。

## 2. 追加設計原則(P8 §導出原則への追補 3 件)

| # | 原則 | 内容 |
|---|------|------|
| **R-A** | **文が先、数値が後**(AP2 の画面適用) | Tier 0/1 のすべての一次要素は**日本語平文 1 文が主表示**、数値・バンド語・スコアは従属表示。文はサーバの決定論テンプレート供給(P7 §4 — LLM 不使用、再現可能)。例: 「**台湾正面: 脅威レベル 4(注意)。24 時間で変化なし。** Cyber 域のみ僅かな上昇。」 |
| **R-B** | **1 ビュー = 1 問い**(Tier の物理的分離) | Tier は「同一ページの節」ではなく**別ビュー**。起動画面には ①状況確認 + ②トリアージ のみ。③④はカード/行の選択で遷移、⑤は「検証」ナビから。P8 §2 の Tier 表の**内容と家は不変** — 変わるのは表示タイミングだけ |
| **R-C** | **用語は初出で自己定義** | 内部語彙(TL / 結論不可 / null-zone / scoring_mode / drift / recall 等)は表示時に ⓘ ツールチップで 1 文定義を持つ(i18n `term.*` 名前空間)。訳さない語の一覧(ja-localization.md §2)は維持 — 訳さないことと定義しないことは別 |

### 2.2 第 2 回追補(D-8〜D-12 に対応、kuebiko 実証パターンを根拠とする)

| # | 原則 | 内容 |
|---|------|------|

## 3. ビュー仕様(改訂)

### 3.1 起動ビュー「状況」(= 旧 stage-1 + stage-2)

上から順に:

1. **NP7 バー**(不変・常設)
2. **状況サマリ文(新設・R-A の頂点)**: サーバ生成 1〜2 文で①の問いに直接答える。
   例: 「監視中 4 シナリオのうち、前回確認から変化があったのは 0 件。最優先の注目対象は
   ○○(理由: 新規異常 2 件)。**ツール自己評価: 留保つき(掃引未完了のセンサーあり)**。」
   → R1 envelope に `board_summary`(テンプレート ID 付き)を追加(§5)
3. **シナリオカード列**(改訂):
   - **大型 TL 表示**(数値 + バンド語 + 色)がカードの支配的要素。カード面積の 1/3
   - シナリオ名は**日本語表示名**を主、`scenario_id` は tooltip(表示名は geo_data のシナリオ
     定義に `display_name_ja` を追加して供給)
   - 変化行は文: 「前回確認(2 時間前)から変化なし」/「TL 4→3 に**悪化**」
   - **結論不可カード**は理由と解消条件を文で: 「結論を出せません — ○○ の観測がまだ
     30 日分ありません(あと 12 日)」(O-7 の解消条件表示は R1 既存フィールドから合成)
   - focused カードのみドメイン・ミニバー(現行踏襲)。バーには域名を日本語併記
4. **注目レーン上位 3〜5**: `narrative`(R6 供給済み)を行の主表示に昇格。score・順位根拠は
   tooltip へ降格。行クリック → 事象詳細(Tier 1)
5. フッタ: 鮮度 + 信頼度チップ + WS 状態(現行踏襲)

### 3.2 遷移構造(R-B)

```
[状況] ──カード選択──▶ シナリオ面(③: 結論 5 型 + 平文説明 + 結論不可理由)
   │                       │
   │                       └─「なぜ?」──▶ 導出ビュー(式→閾値→兆候→観測→一次ソース)
   ├──レーン行選択──▶ 事象詳細(地理面・タイムラインへのタブ)
   └──ナビ[検証]──▶ 検証ビュー(⑤: Tier 2 一式)
[フィードバック(④)] はシナリオ面・事象詳細の文脈内に置く(独立ビューにしない)
```

ナビゲーションはトップレベル 2 項のみ: **[状況] [検証]**。SPA のビュー切替(URL ハッシュ)で
実装し、パネルマネージャは引き続き持たない。

### 3.3 検証ビュー(= 旧 stage-5、内容不変・提示改訂)

- テーブル群の内容・供給 API は P8 §2 Tier 2 表のまま**不変**
- 各テーブルの直上に**リード文 1 行**(このテーブルは何の問いに答えるか)を必須化。
  例: 「センサー健全性 — どの観測源が生きていて、どれが沈黙しているか」
- **未着地面(新設)**: 現行の `data-deferred` 断片を全廃し、検証ビュー末尾の 1 節
  「未着地の機能」に集約(繰延 ID・理由・着地予定 WP を表で)

### 3.4 地理面(D-5 の解消)

- Tier 1 のまま。**国タイル・グリッド地図**を一次表現とする: 座標もタイル画像も使わず、
  参加国を地域ブロック(東アジア / 東南アジア / 中東 / 欧州 / 北米 …)に配置した CSS グリッド。
  各国タイルは 国旗絵文字 + ISO2 + 異常事象ドット(ドメイン色)+ 役割リング(participant role)
- 現行のリスト表示はアクセシビリティ代替として維持(`aria` 経由で同内容)
- ワイヤに座標を載せない裁定は不変 — タイル配置は静的定数(フロント資産)で足りる

### 3.5 空状態の規約(D-4 の解消)

すべての空可能要素は 3 点を必ず言う:
(a) **ここは何を表示する場所か** (b) **いま空である理由** (c) **何が起きれば埋まるか**。
例(レーン空): 「注目対象はありません。異常兆候が検知されると、優先度順にここに並びます。
最終スキャン: 3 分前・センサー 24/25 稼働」。i18n キーは `empty.<surface>.role / reason / fills_when`
の 3 点セットで統一。

### 3.6 初回オンボードカード(R-C)

初回ログイン時のみ、状況ビュー冒頭に閉じられるカード 1 枚: このツールが答える 5 つの問い
(= P8 §1 の①〜⑤)と画面の対応を 5 行で。表示状態は利用者設定に永続(サーバ側 — ブラウザ
localStorage 単独にしない。S1-UI-035 の規律)。

### 3.7 状況ビューの構図(第 2 回改訂 — R-D/R-E/R-F/R-G の実装)

§3.1 の要素(NP7 バー・サマリ文・カード・レーン)は維持し、**配置と見出しを改める**:

```
[NP7 バー]
[状況サマリ文 — 画面の頂点。R1 board_summary をそのまま、最大の活字で]
┌─ シナリオ地図(全シナリオ)────────┬─ シナリオカード列 ─────────────┐
│ 参加国タイルを、その国が参加する     │ 大型 TL + 変化文(現行維持)      │
```

- **見出しの内容語化(R-D)**: 「1 状況確認」+問い行 → **削除**(サマリ文が節の役割を果たす。
  カード列に節ラベルが要る場合は「シナリオ別の脅威レベル」)。「2 トリアージ」→「**注目すべき
  事象(優先度順)**」。「3 ドリルダウン」→ **シナリオ表示名そのもの**。「4 フィードバック」→
  「この判断へのフィードバック」。「5 検証」→「検証 — 系の健全性と判断履歴」。stage 番号
  (`.stage-n`)は全廃

  **最深刻(severity 最大)のシナリオの色**で塗り、tooltip に全所属を列挙。イベントドットは
  Tier 0 では描かない(R2 は focused 限定のため — 描けないものを描かない、S1-UI-048 と同旨)

  「なぜ? →」(シナリオ面へ)。供給は R1 拡張(§5)
- **オンボーディング書き換え**: ①〜⑤の番号列 → 「この画面でできること」の**並列**箇条書き
  (順序含意なし・目標秒数なし)
- 狭い画面では地図とカード列は縦積みにフォールバック(CSS grid 1 カラム化)

## 4. 用語定義(R-C の実装)

- i18n に `term.*` 名前空間を新設。初期セット(最低限):

  データまたは較正不足で結論を出せない状態。故障とは区別される)/ `term.null_zone` /
  `term.scoring_mode`(full = 全センサー稼働、lite = LLM+グローバル信号のみ)/ `term.drift` /

- 表示規約: 該当語の**ビュー内初出**にのみ ⓘ を付す(全出現に付けると視覚ノイズ)
