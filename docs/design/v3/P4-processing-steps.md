# P4 — 処理ステップ設計（入力 → 出力の機能分解）

**位置づけ**: [P1-architecture.md](P1-architecture.md) が「コードがどこに住むか」（層・依存方向・管轄）を決めるのに対し、
本書は **「データが入口から出口まで何をされるか」** をステップに分解する。
**両者は直交する**。P1 は静的な構造、P4 は動的な流れ。実装者は両方を見る必要がある。

**本書の目的**: ツール全体を 1 本の流れとして見通せるようにすること。
判断基準は「**各ステップが答える問いを 1 文で言えるか**」。言えないステップは分解が誤っている。

---

## 1. 入力と出力（設計の両端）

### 入力（3 種。性質が違うので混ぜない）

| # | 入力 | 性質 | 頻度 |
|---|---|---|---|
| **I-1** | 外部ソースの計測値（BGP・航跡・電波・地震・RSS・Telegram・CT log 等 34 系統） | 不安定・非同期・欠測する・形式が変わる | センサーごと 5 分〜4 時間 |
| **I-2** | アナリストの入力（focus 選択・feedback ラベル・human anchor・設定変更・snooze/dismiss） | 少量・高価値・不定期 | 日〜週 |
| **I-3** | 外部の事後事実（GDELT トーン・ACLED 死者数・報道） | 遅れて届く・較正の教師信号 | 日次 |

### 出力（ツール定義が要求するもの）

| # | 出力 | 由来 |
|---|---|---|
| **O-1** | 全体脅威レベル（シナリオごと TL 1-5） | 定義文 |
| **O-2** | トレンド | 定義文 |
| **O-3** | ドメイン別兆候 | 定義文 |
| **O-4** | 個別異常事象 | 定義文 |
| **O-5** | 推定攻撃シナリオ | 定義文 |
| **O-6** | **導出根拠**（式・閾値・一次ソース・LLM プロンプト） | 定義文 / NP6 |
| **O-7** | **結論不可の明示**（理由と解消条件つき） | 定義文 / NP5+8 |
| **O-8** | 「最終判断ではない」の常時表示 | NP7 |
| **O-9** | 次に注目すべき対象の順位 | AP1 |
| **O-10** | なぜその数値かの平文説明 | AP2 |
| **O-11** | ツール自身の信頼性メトリクス | AP3 |
| **O-12** | 過去の自動化判断の再生 | AP4 |

**設計の要請**: O-6〜O-8 は「おまけ」ではなく O-1〜O-5 と同格の出力である。
したがって**後から組み立てられる構造では要件を満たせない**。各ステップが自分の寄与分の根拠を
その場で残さなければならない。

## 2. 処理ステップ — 11 段

各ステップは **1 つの問いにだけ答える**。それが機能分解の単位。

```
 I-1 外部ソース
      │
      ▼
 ┌─ S1 取得 ────────── 取れたか？
 │    ▼
 ├─ S2 正規化 ──────── 何が観測されたか？
 │    ▼
 ├─ S3 文脈化 ──────── それは普通か？
 │    ▼
 ├─ S4 判定 ────────── 異常と呼ぶか？
 │    ▼
 ├─ S5 収斂 ────────── どれだけ集まったか？
 │    ▼
 ├─ S6 結論 ────────── 何と結論するか / できないか？   → O-1..O-5, O-7
 │    ▼
 ├─ S7 説明 ────────── なぜそう言えるか？               → O-6, O-8, O-10
 │    ▼
 └─ S8 優先順位 ────── 次に何を見るべきか？             → O-9
      │
      ▼  アナリスト（I-2）
      │
 ┌─ S9 較正 ────────── 閾値は正しかったか？   ← I-3
 ├─ S10 自己評価 ───── この系は生きているか？            → O-11
 └─ S11 記録 ───────── いつ何を判断したか？              → O-12
```

S1〜S8 は**前向きの流れ**（信号 → 結論 → 提示）。
S9〜S11 は**横断的な流れ**（すべてのステップを対象にする）。

---

### S1 取得 — 「取れたか？」

| | |
|---|---|
| **入力** | ソース定義（URL・認証・周期） |
| **出力** | 生ペイロード + 取得結果メタ（成功/失敗/遅延/HTTP 状態） |
| **責務** | 外界と話す。timeout・リトライ・レート制限・サーキットブレーカー |
| **決めないこと** | **意味を一切解釈しない**。「取れなかった」も正当な出力 |
| **1 実装であるべき理由** | 現在 34 センサーが各自ハンドロールし、429 処理は 8 基のみ。取得の癖がセンサーごとに違う |

**設計判断**: ソースアダプタは「何を取りに行くか」だけを宣言し、**「どう取りに行くか」は宣言できない**。
これにより取得の品質がソース間で不均一になる余地を消す。

---

### S2 正規化 — 「何が観測されたか？」

| | |
|---|---|
| **入力** | 生ペイロード |
| **出力** | **観測（Observation）**: 対象国 / ドメイン / 計測値 / 観測時刻 / 出所 |
| **責務** | パース・抽出・語彙統一（country / scenario）・欠損の明示 |
| **決めないこと** | 正常か異常かを判断しない。**事実だけを記録する** |

**設計判断**: ここが「事実」と「判断」の境界。以降のステップは観測を書き換えない（append-only）。
壊れた入力（malformed XML 等）への耐性はここに集約する（現在は 6 実装で耐性がバラバラ）。

---

### S3 文脈化 — 「それは普通か？」

| | |
|---|---|
| **入力** | 観測 + ベースライン（時刻帯別 / 曜日別 / ローリング） |
| **出力** | **逸脱（Deviation）**: Z-score・前回比・傾き。「どれだけ普通でないか」 |
| **責務** | 平常時との比較。**比較のみ** |
| **決めないこと** | 閾値を当てない。「Z=3.2」までで、それが異常かは S4 が決める |

**設計判断（最重要）**: **ベースラインの更新は S3 とは別のジョブにする。**
現行は Z-score 算出が走行統計を書き換えるため、同じ入力を 2 回流すと違う答えが出る（非冪等）。
これが replay パリティ検証の前提を壊している。**S3 は読むだけ、更新は別**。

ベースラインは永続。実効窓は「サンプル数 × 取得周期」で定義し、日数から直接サンプル数を導かない
（30 日のつもりが 7.5 時間になる事故が実在した）。

---

### S4 判定 — 「異常と呼ぶか？」

| | |
|---|---|
| **入力** | 逸脱 + 閾値 + 抑制条件 |
| **出力** | **兆候（Indicator）**: FIRED / OK / 抑制済（**抑制理由つき**） |
| **責務** | 閾値の適用と、抑制の判断（ノイズ・ミュート・低信頼・宇宙天気等の外因） |
| **決めないこと** | シナリオへの寄与を計算しない。単一の観測に対する判定のみ |

**設計判断**:
- 閾値は**すべて宣言的レジストリ経由**。直読み禁止（現在 98 キー中 96 キーが迂回している）
- 閾値と被比較値は**単位を型で区別**（比率と百分率の取り違えでセンサー 1 基が恒久無発火だった）
- **抑制したら抑制を記録する**。「なぜ兆候にしなかったか」も NP6 の対象

---

### S5 収斂 — 「どれだけ集まったか？」

| | |
|---|---|
| **入力** | 兆候群 + シナリオ定義（participant・重み・役割） |
| **出力** | **シナリオスコア**: ドメイン別スコア + 収斂レベル + 寄与内訳 |
| **責務** | 独立ソースの dedup → 参加国重み付け → ドメイン集約 → 収斂ボーナス |
| **決めないこと** | 脅威レベルに変換しない。数値の集約まで |

**設計判断**:
- **純関数・冪等**。同じ兆候群からは常に同じスコアが出る
- dedup は `(signal_source, country)` で MAX。複数センサーが同じ物理事象を見ている場合の二重計上を防ぐ
- 収斂ボーナスは**最も弱いソースの信頼度で律速**（NP2 の数式化）
- 寄与内訳（どのセンサーがいくら寄与したか）を**この時点で残す**。後から復元できない

---

### S6 結論 — 「何と結論するか / できないか？」

| | |
|---|---|
| **入力** | シナリオスコア + 履歴 + 較正状態 |
| **出力** | **結論**（O-1〜O-5）**または結論不可**（O-7）。どちらも provenance 付き |
| **責務** | スコアを判断に変換する。**出せない場合は「出せない理由」を出す** |
| **決めないこと** | 表現・言い回しは S7 の担当 |

**設計判断（NP4 / NP5+8 の中核）**:
- 結論不可は**例外でも欠損でもなく、結論型の一級市民**。理由・不足しているもの・解消条件を持つ
- 現行は 4 種の理由のうち 3 種に生成経路が無く、すべて「データ不足」に潰れている。
  **v3 では各理由に生成経路とテストが対で存在する**
- **データ欠測と真の平穏を区別できること**が要件（現行は SALUTE が空キャッシュでも「ROUTINE」を返す）
- 結論は provenance 無しに構築できない。**後付けで監査証跡を組み立てる構造にしない**

---

### S7 説明 — 「なぜそう言えるか？」

| | |
|---|---|
| **入力** | 結論 + 各ステップが残した根拠 |
| **出力** | 監査証跡（O-6）+ 平文ナラティブ（O-10）+ NP7 免責（O-8） |
| **責務** | S1〜S6 の各ステップの寄与を 1 本の導出経路に編む |
| **決めないこと** | 新しい判断をしない。**既にある根拠を提示するだけ** |

**設計判断**: ナラティブは**テンプレート + スロット埋め**で生成する（LLM を使わない）。
再現性と監査可能性が要件だから（AP2）。同じ結論からは常に同じ説明が出る。

**この設計が成立する条件**: S1〜S6 の各ステップが自分の根拠をその場で残していること。
S7 が後から掘り起こす構造だと、根拠の欠落が S7 まで発覚しない。

---

### S8 優先順位 — 「次に何を見るべきか？」

| | |
|---|---|
| **入力** | 結論群 + アナリストの状態（既読・snooze・過去の focus） |
| **出力** | 注目順位（O-9）と、その順位の根拠 |
| **責務** | 「新規性 × 確信度の変化 × アナリストの盲点」で順位付け（AP1） |
| **決めないこと** | 結論の中身を変えない。並べ替えるだけ |

**設計判断**: **順位付けの結果も台帳に残す**（現行はフロントエンドにしか実装が無く、
AP1 の判断がどこにも記録されない = AP4 から AP1 だけが抜けている）。

---

### S9 較正 — 「閾値は正しかったか？」

| | |
|---|---|
| **入力** | 過去の結論（S6 の出力）+ 実際に起きたこと（I-3）+ アナリスト判断（I-2） |
| **出力** | 閾値の変更提案（適用は別途ゲート） |
| **責務** | 検知の当たり外れを測り、閾値を提案する |
| **周期** | 前向きの流れとは**別の遅い周期**（日次〜週次） |

**設計判断**:
- **ラベルと baseline は系列 ID を持つ**。ラベル生成規則が変わったら系列が変わり、
  系列を跨いだ比較は機械的に拒否される（現行は帰属修正の前後を無防備に比較できてしまう）
- 提案の生成・適用・却下は**単一のガード評価器**を通る（現行はテストされている経路と動いている経路が違う）
- 較正に影響する書き込み（feedback ラベル等）は権限を要求する

---

### S10 自己評価 — 「この系は生きているか？」

| | |
|---|---|
| **入力** | S1〜S9 の全ステップの稼働状態 |
| **出力** | 信頼性メトリクス（O-11）+ 異常の提示 |
| **責務** | **各ステップが「動いているつもりで死んでいない」ことを検査する** |

**このステップが存在する理由**: 診断で 7 件の「沈黙した失敗」が見つかった。
いずれも S1 は成功し、health は OK を返し、UI は正常に見え、CI は通り、**S4 の判定だけが死んでいた**。
前向きの流れの中に検査を置くと、検査対象と検査者が同じ故障で同時に死ぬ。**だから独立させる**。

**検査項目はステップに対応する**:

| 検査 | どのステップの死を見るか |
|---|---|
| 取得生存 | S1（センサーが取れているか） |
| **発火生存** | **S4**（判定が一度でも発火しているか。恒久無発火を検出） |
| 窓健全性 | S3（ベースラインの実効窓が宣言と一致するか） |
| 単位整合 | S4（閾値と被比較値のスケールが合っているか） |
| 設定到達性 | S4（レジストリの値が実際に読まれているか） |
| ゲート生存 | S9（安全ゲート自体が機能しているか） |
| 系譜健全性 | S9（ラベル生成が退化していないか） |

**S10 自身の生存**: 最終評価時刻を出力し、アナリストから見える場所に置く。

---

### S11 記録 — 「いつ何を判断したか？」

| | |
|---|---|
| **入力** | S4〜S9 のすべての判断 |
| **出力** | 時系列で再生可能な台帳（O-12） |
| **責務** | 自動化判断の事後検証を可能にする（AP4） |

**設計判断**: 再生に必要な**入力側の保持期間**が要件を規定する。
結論だけを保存しても、寄与内訳や個別異常事象は復元できない。
**信号レベルの観測を replay 窓の 2 倍保持する**（現行は 24 時間しか保持しておらず、30 日再生が物理的に不可能）。

## 3. なぜ現在は見通しが悪いのか — ステップに「家」が無い

現行系の問題は機能が多いことではなく、**上の 11 ステップがモジュール境界と一致していない**ことである。

| ステップ | 現在どこにあるか | 症状 |
|---|---|---|
| S1 取得 | 34 センサーに各自ハンドロール | 取得の癖がセンサーごとに違う。429 処理は 8 基のみ |
| S2 正規化 | センサー内。RSS パースは **6 実装** | 同じ壊れ方でセンサーごとに挙動が違う |
| S3 文脈化 | センサー内。**しかも統計更新と同居** | 採点が非冪等になり replay できない |
| S4 判定 | センサー内 + `get_threat_data` 内の closure に分散 | 抑制判断が 2 箇所に分かれ、片方は理由を残さない |
| S5 収斂 | `engine.py` と `scoring.py` に**式が重複** | 修正が片方だけに入る危険 |
| S6 結論 | `conclusions/` にあるが、TL 導出式は**4 箇所に複製**（うち 1 つは値が違う） | どれが正なのか分からない |
| S7 説明 | バックエンドとフロントに分散 | 根拠の欠落が発覚しにくい |
| S8 優先順位 | **フロントエンドにしか無い** | AP1 の判断が台帳に残らない |
| S9 較正 | `calibration/` にあるが、ガードが**二重経路** | テストされている式と動いている式が違う |
| S10 自己評価 | **存在しない** | 7 件の沈黙失敗が長期間発見されなかった |
| S11 記録 | 結論台帳はあるが**入力側の保持が足りない** | 30 日再生が物理的に不可能 |

**「どのステップにも家が無い」ことが見通しの悪さの正体**である。
機能を消すのではなく、**各ステップに 1 つの家を与える**ことが本設計の中心。

## 4. P1（層）との対応

P4 のステップと P1 の層は 1 対 1 ではない。対応は次のとおり:

| ステップ | 主な担当層 |
|---|---|
| S1 取得 | L0 |
| S2 正規化 | L0（出力を L1 に格納） |
| S3 文脈化 | L1（ベースライン）+ L2（比較） |
| S4 判定 | L2 |
| S5 収斂 | L2 |
| S6 結論 | L3 |
| S7 説明 | L3（根拠の編成）+ L7（表示） |
| S8 優先順位 | L3/L4 境界（台帳に残す）+ L7（表示） |
| S9 較正 | L4 |
| S10 自己評価 | **L5** |
| S11 記録 | L1（台帳）+ L6（replay API） |

**層は「誰が管轄するか」、ステップは「何をするか」**。
実装時は「このコードはどの層に住み、どのステップを担うか」の両方が言えなければならない。

## 5. この分解が正しいことの判定基準

1. **各ステップが答える問いを 1 文で言える** — §2 の見出しがそれ
2. **隣接ステップの責務が重ならない** — 例: S3 は「どれだけ普通でないか」まで、S4 が「異常と呼ぶか」
3. **各ステップが単独でテストできる** — 入力を与えれば出力が決まる（S1 と S9 以外は純関数に近い）
4. **各ステップの死を S10 が検出できる** — 検査項目がステップに対応している（§S10 の表）
5. **1 つの機能追加が触るステップが最小** — 新センサー追加は S1/S2 のアダプタ 1 つで済む
   （現行は取得・パース・統計・判定を全部書く必要がある）

**5 が「追加に追加を重ねて複雑化する」ことへの構造的な回答**である。
新しいセンサーを足すときに 6 つの実装を選んで真似する必要が無くなる。
