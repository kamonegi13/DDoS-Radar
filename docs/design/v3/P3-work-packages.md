## Phase 0 — 前提条件の確保

### WP-0.1 — 信号台帳 retention 60 日化 【最優先・即時着手】

**目的**: パリティゲートの物理的前提を作る。
**なぜ最優先か**: `sensor_observation_ts` は現在 TTL 24h で、**信号レベルの 30 日 replay が物理的に不可能**（D2 G-05）。
retention を延ばした日から 30 日経つまでパリティ測定はできない。実装がどれだけ速くても、
cutover 可能日は「本作業の完了 + 30 日」より前には来ない。**実装計画の完成を待たずに着手する。**

**前提として読む**:
- `docs/design/v3/S3-data-migration.md`（retention 条項）
- `docs/design/v3/S5-verification.md` S5-VERIF-018（60 日が要求される理由）
- ADR-V3-005

**完了条件**:
1. `sensor_observation_ts`（および信号レベルの台帳）の retention が 60 日に延長されている
2. retention 値が設定として可視（**ハードコードしない**。ただし G-15 により registry 経由が機能しないので、
   到達性は WP-1.2 で検証する）
3. 延長した日付を `docs/design/v3/P2-migration-plan.md` §7 に記録し、**パリティ可能日 = その日 + 30 日**を明記

**検証手順**:
- 60 日前のデータが実際に残ることを、7 日後・30 日後に再確認する（**1 回の確認で完了としない**）
- 容量の増加を WP-0.3 で追跡

**やってはいけないこと**:
- 他の retention（conclusions の 365 日化）を同時に変更しない。容量影響が切り分けられなくなる
- ホスト側から `sqlite3` で直接操作しない（WAL 破損。コンテナ内から実行する）

### WP-0.3 — 容量実測とバックアップ健全性指標

**目的**: ADR-V3-005（retention 拡大）の妥当性を実測で検証し、保全を確実にする。

**前提として読む**: `docs/design/v3/S4-nonfunctional.md` S4-NF-053、`docs/design/v3/S3-data-migration.md`（容量試算）

**完了条件**:
1. WP-0.1 後の DB 成長を計測し、60 日到達時点の実サイズを推定
2. S3 の試算（定常 6〜8 GB）と実測の乖離を記録。**乖離が大きければ ADR-V3-005 を再検討**
3. **最新バックアップからの経過時間**が指標として取得でき、閾値超過で可視化される
   （2026-07-04〜08-03 に 1 ヶ月沈黙欠測した前科がある）

**完了記録（2026-08-07）**: `radar/verification/ops_health.py`（L5 検査 5 本目）。**7 月沈黙欠測の構造的原因を特定・解消** — バックアップはホスト側 `backups/`、DB はコンテナ volume 内で、**アプリからバックアップの存在自体が構造的に見えなかった**。backup スクリプトが成功時に volume 内へ原子的マーカー（tmp + os.replace）を書き、欠如/破損/時計スキューは 3 種の別 reason で全て INSUFFICIENT（決して OK に読めない — 欠測が必要としていた故障方向）。
容量: 日次サンプル（DB/WAL バイト + 厳選 12 テーブル行数、5 秒予算・打ち切りは明示）→ 最小二乗で 60 日射影、S3 試算 6-8GB の周囲 [3,16]GB 帯で乖離判定（≥3 サンプル要、7 日未満は early_estimate）。ADR-V3-005 は不変更。
**本番初回実測（2026-08-07）**: DB 総量 **1.92GB**、信号台帳 **43,789 行 / 2.0 日（≈21.9k 行/日）**。成長推定と backup マーカーは設計どおり数日間 INSUFFICIENT（マーカーは次回 04:00 実行後に出現、推定は ≥3 サンプル後 — **2026-08-10 頃に乖離判定を確認**）。
実行面の教訓: `python -m` 起動は親パッケージ import が先行しアプリ 2 個目を起動するためガード不能 — `scripts/run_ops_health.sh` を唯一の正規実行経路として同梱（radar/__init__ の import 時スレッド起動が根因、v3 L0/L6 で解消予定）。新規 63 テスト / 全スイート 2537 passed。

## Phase 1 — L5 自己検証層（現行系に対して構築）

> **この Phase の意義**: 今回見つかった 7 件の沈黙失敗は**すべて「作った時は正しく動いていた」**。
> v3 が同じ轍を踏まない保証は無い。**既に起きた失敗を検出できない監視は、次の失敗も検出できない。**
> よって L5 は v3 の一部としてではなく、先に現行系に対して作り、既知 7 件で検証する。

### WP-1.1 — 発火生存監視

**目的**: 「センサーは動いているが判定だけが死んでいる」を検出する。

**前提として読む**: `docs/design/v3/S5-verification.md` §2.1、`docs/design/v3/D2-defects.md` §F の「沈黙した検知失敗」節

**完了条件**:
1. 各センサー × 各判定フラグについて「最後に True になった時刻」が記録される
2. 長期無発火が異常として提示される（閾値はセンサーの性質による — 一律にしない）
3. **受け入れ検証**: 修正前の gps_jamming（F-08）を「恒久無発火」として検出できる

**やってはいけないこと**: WP-0.2 で F-08 を修正した後に作ると検証できない。**修正前のデータか、合成データで検証する**

**完了記録（2026-08-06）**: `radar/verification/`（flag_catalog: 23 センサー / 42 フラグ + `NO_DETECTION_FLAGS` 11 で全 34 センサーを第三状態なしに全数分類、firing_monitor）、DB migration v55（`sensor_flag_state` / `sensor_flag_fire_log` 60d / `l5_check_result` 365d / `l5_job_state`）。記録点は `BaseSensor.set_cache()`（1 評価 = 1 トランザクション）、日次検査は `l5_job_state` の永続スケジュール駆動（F-01 の揮発カウンタ不使用・再起動時は超過分を補償実行）。`detection_health` は fetch 側 health と**別軸**で追加（採点 confidence に入る既存 health は不変更 — パリティ基準線保護）。露出は `/api/v2/self_eval` の `firing_liveness` ブロック（照会失敗は `firing_liveness_error` として可視化、S5-VERIF-006）。
**受け入れ検証（条件 3）**: 実 `GpsJammingSensor.fetch()` に 8% 不良比率の合成タイル（正しい単位なら発火すべきデータ）→ `is_jammed=False` を確認した上で 31 日分評価 → `ANOMALY / never_fired` を両フラグで検出（`tests/test_f08_acceptance.py`）。gps_jamming.py は無改変。新規テスト 204 件 / 全スイート 2100 passed / check_ci.sh 全ゲート通過。

**その途中でゲートを無効化する沈黙欠陥が 1 件出た**: `record.py::_record_cf_origin_baseline` はスナップショットを**毎サイクル `observed_at=now` で再押印**しており（読み直しただけのサイクルも）、齢を読むゲートは 900 秒ごとに 0 に戻されて**一度も発火しない**。しかも行は `stored` と表示し続けるので外からは正常に見える。齢の供給側を直さずにゲートだけ足していれば「実装したのに効いていない」がテスト緑のまま成立していた。修正は本番と同じ「`baseline_set` は再取得した `if` の中だけ」（`core.py:739-742`）。取得負荷は対象国あたり 1 日 **192 → 2** 送信（登録時の見積り「+190」と一致）。

**変異試験が掃引の設計欠陥を検出した**。`GLOBAL_SHARE_FLOOR` と `PER_ORIGIN_L7_PCT_MIN` の変異は初回の掃引（`uniform(0, 45)`）を**生き延びた**。定数が死んでいたのではなく、両方とも**小さい値の隅**でしか効かない（前者は対象国が世界攻撃トラフィックの 0.1% 未満のとき、後者は 1.5% 未満の攻撃元が adversary フロア 0.5% に対して跳ねているとき）ため、一様掃引がその領域に質量をほとんど置いていなかった。生成器を**値ではなくスケールを引く**形（`_PCT_SCALES` / `_SHARE_SCALES`）に変えて **19/19 撃墜**。生存変異を「報告対象」と定めた規律が、掃引そのものの不足を暴いた。
