# P1 — v3 目的駆動アーキテクチャ

**位置づけ**: ADR-V3-003 に従い、本書の構造は**現行コードからではなく、ツール定義（4 文）+ NP1-NP7 + AP1-AP4 から演繹**する。
Phase S の 714 条項は**挙動**の入力であり、構造の入力ではない。D1 のモジュール分解表・サブシステム表は
「現状がどう壊れているか」の証拠であって、本書の下敷きではない。

**設計の検証手段**: 各層・各決定に対し「どの原則から導かれるか」と「D2 のどの欠陥を構造的に不可能にするか」を明示する。
この 2 欄が埋まらない構造は採用しない。

---

## 1. 設計の出発点

### 1.1 ツール定義から直接導かれる 5 つの構造要求

| # | 定義の文言 | 構造要求 |
|---|---|---|
| R-A | 「フリーかつオープンの情報ソースを**統合**し」 | 多数の異種ソースを取り込む**取得層**が要る。ソースの死・仕様変更は恒常（D2 D-02）なので、**差し替えが安価**でなければならない |
| R-B | 「技術的に実行可能な**最大の**評価結論を出力する」 | 結論導出は「出せるものは出す」が既定（NP4）。データ不足で黙るのではなく、**不足の事実を結論として出す** |
| R-C | 「その導出に用いた**式・閾値・一次ソース**と併せて出力する」 | provenance は出力の付属物ではなく**結論の構成要素**。後付けで組み立てられる構造では NP6 を満たせない |
| R-D | 「**結論不可**の状態を明示する」 | 結論不可は例外でも欠損でもなく、**結論型の一級市民** |
| R-E | 「組織内の**一つのノード**として機能する」 | 出力は常に「最終判断ではない」を含む。UI と API の両方で強制される必要がある |

### 1.2 診断が追加した 1 つの構造要求（当初計画に無かったもの）

Phase D/S で **6 件の「沈黙した検知失敗」**が見つかった（F-02 / F-06 / F-08 / F-09 / G-02 / G-07）。
共通形は次のとおり:

> センサーは fetch に成功し、health は OK を返し、UI は正常に見え、CI は通る。
> **判定だけが死んでいる。**

| # | 要求 | 根拠 |
|---|---|---|
| **R-F** | **自己検証が層として存在する**。「動いているつもりで動いていない」を機械が検出する | NP1（見逃しは誤検知より悪い）+ 実測 6 件。**これは v3 の最重要要求**であり、リビルドの主目的を「構造の整理」から「検知の生存保証」へ更新する |

R-F は D2 §D（構造では直らない欠陥）への回答でもある。ラベル生成器のバグ・外部 API の脆さ・
運用者の錬度依存はアーキテクチャでは消せないが、**壊れたことを検出する層**は設計できる。

## 2. 層構造

依存は上から下への一方向のみ。**逆流は禁止**（D2 A-05/A-06 の構造的解消）。

```
  L7  提示層         UI（pure-core + 薄い DOM）
  L6  公開層         読み取り API（射影）/ 指令 API（明示的な状態変更）
  ────────────────── 契約境界（S2）
  L5  自己検証層     生存監視・整合検査・系譜監査          ← R-F（新設）
  L4  較正層         ラベル生成・閾値調整・提案
  L3  結論層         結論導出（結論不可を含む）+ provenance 組立
  L2  採点層         純関数の採点カーネル
  L1  観測層         観測台帳・ベースライン基盤（単一管轄の永続層）
  L0  取得層         ソースアダプタ + 共有取得カーネル
  ──────────────────
  K   カーネル       型・単位・provenance・閾値レジストリ（全層が依存）
```

### なぜこの分割か

- **L0/L1 を分ける**: 取得（外界と話す、失敗する）と観測（事実の保存、失敗しない）は失敗モードが違う。
  現行はセンサーが自分で `set_cache` し、ベースラインを in-mem で持ち、第 2 SQLite まで作った（D2 A-03/A-09）
- **L1/L2 を分ける**: **採点が統計を書き換えてはならない**。現行は Z-score 算出が走行統計を更新するため
  ティックが非冪等になり、replay パリティ検証の前提が壊れている（D2 F-05）
- **L2/L3 を分ける**: 採点は数値、結論は判断。結論不可（R-D）は L3 の概念であり L2 には存在しない
- **L5 を独立させる**: 自己検証が L3/L4 の内部にあると、**検証対象と検証者が同じ故障で同時に死ぬ**。
  6 件の沈黙失敗はすべて「その機能自身は自分の異常を報告できない」形だった
- **L6 を射影に限定**: GET が採点を駆動する現行構造（D2 A-01）を構造的に不可能にする

## 3. K — カーネル（型で不正状態を表現不能にする）

診断で見つかった欠陥のうち **4 件は型で消せる**。

| 型 | 責務 | 構造的に不可能になる欠陥 |
|---|---|---|
| `ThreatLevel` | TL 1-5 を保持し、**大小比較を禁止**。順序比較は `severity()`（= 6−TL）経由のみ提供 | TL 反転事故（較正インシデント #2）。「TL を直接比較しない」という運用規約が**型で強制**される |
| `Ratio` / `Percentage` | 単位を型で区別。相互変換は明示的コンストラクタのみ | **F-08**（gps_jamming が比率と百分率を比較して恒久無発火）。閾値と被比較値の単位不一致がコンパイル/検証時に落ちる |
| `Window` | 「サンプル数」と「時間幅」を区別し、`Window.from_days(30, cadence)` のように**取得周期を要求**する | **F-06**（telegram のベースライン窓が 30 日のつもりで 7.5 時間）。日数を直接サンプル数として使えない |
| `Threshold` | 値 + レジストリキー + 既定値 + 解決経路を保持。**直読み（getenv/定数）を禁止** | **G-04**（registry 登録済みなのにセンサーが getenv 直読みで DB override が効かない）、D2 A-13 |
| `Provenance` | 式 ID・閾値の実効値・一次ソース・LLM プロンプト参照を保持。**結論はこれ無しに構築できない** | NP6 の後付け不能化。E-08（プロンプト記録の欠落） |
| `Evidence` | 観測の出所（センサー・時刻・鮮度）を保持。鮮度未確認の観測を消費できない | **B-03**（ground_osint が STALE を無視）、G-05 の replay 要件 |

**設計規律**: K 層の型は「正しい使い方しかできない」ことを目標にする。
ドキュメントで注意を促す方式は、今回の診断で**実際に破られた**（E-18: docstring が実装と食い違い、
F-06 は「rss_narrative と同じロジック」という虚偽の自己申告に隠れていた）。

## 4. L0 — 取得層

### 構造

```
  SourceAdapter（ソースごと。宣言のみ）
       ↓ 使う
  取得カーネル（共有。ここを通らない外界アクセスは存在しない）
       - HTTP: timeout 必須・リトライ・レート制限・429 処理
       - サーキットブレーカー: 全経路に適用（例外なし）
       - RSS/XML: tolerant パーサ + feed 死活分類
       - LLM 投入: プロンプト構築 → 解析 → 確信度 → キュー投入
```

`SourceAdapter` が宣言するのは **何を取りに行くか / どう正規化するか**だけ。
**どう取りに行くか（timeout・リトライ・CB・レート制限）は宣言できない**。

### 解消する欠陥

| 欠陥 | 解消の仕方 |
|---|---|
| A-02（RSS 4-6 複製、LLM 投入 8 複製） | 複製する場所が存在しない。tolerant パーサの有無がソースごとに違う状態を作れない |
| A-10（基底ヘルパー採用ゼロ） | 「基底に置いて使ってもらう」ではなく**取得経路自体を閉じる**。S4-NF-061 の規範 |
| B-01（bg_observer が CB を迂回） | 独自 thread から外界へ出る経路が無い |
| F-02（force 取得の名前不一致） | アダプタ識別子は型で、文字列リテラルの許可リストは存在しない |
| F-09（見出し照合が英語専用） | 照合は言語非依存（正規化 + 埋め込み）を既定とする。NP2 の入力が英語圏に偏らない |
| D-02（外部 API の脆さ） | 消えない。ただしアダプタが薄いので**差し替えが安い**。API の癖（D1-sensors §4 の 20 項目）はアダプタに集約 |

## 5. L1 — 観測層

### 構造

- **観測台帳**: append-only。センサーが吐いた事実をそのまま保存する
- **ベースライン基盤**: 統計は**明示的な更新ジョブ**でのみ書き換わる。読み取りは常に副作用なし
- **単一管轄**: 永続層はここだけ。第 2 SQLite は存在しない（A-09）

### retention は検証要件から逆算する

G-05 で判明したとおり、**現行の `sensor_observation_ts` は TTL 24h で、30 日 replay が物理的に不可能**。
S5 のパリティゲートは 30 日窓を要求するので、**信号台帳の retention はパリティ要件から導出される**:

| 台帳 | retention | 根拠 |
|---|---|---|
| 観測（信号レベル） | **60 日以上** | 30 日 replay 窓 × 2（比較のための前後窓）。S5-VERIF-018 |
| 結論台帳 | 365 日 | 較正の系列比較と事後検証（D3 §3-3） |
| ベースライン | 無期限（世代管理） | backfill 不能な 3 表（checkhost_hod / bgp_hod / gdelt_dow）を含む。D4 |

**この決定は容量に跳ねる**（S3 試算: 定常 6〜8 GB、現行 1.9 GB）。P2 で明示的にトレードオフを提示する。

## 6. L2 — 採点層

### 規律

1. **純関数**。入力は観測 + 閾値、出力はスコア。**副作用ゼロ**
2. **冪等**。同一入力は常に同一出力（F-05 の構造的解消 → replay パリティが成立する）
3. **式は 1 箇所**。velocity/slope/TL 導出の複製（A-02 / F-14 / G-09 の 4 複製）は定義上作れない
4. **閾値は `Threshold` 型経由のみ**。ハードコード 15 件（S1-scoring-core §3）は registry へ

### TL 導出の扱い

S1-SCORE-004 で確定した現行式を保存する（パリティの比較対象）。ただし
**ACCIDENTAL A6（TL1 がドメイン数を要求しない = TL2 より収斂要求が緩い）はオーナー裁定事項**であり、
裁定次第で v3 の式が変わる。P2 の cutover 条件はこの裁定を前提に確定する。

## 7. L3 — 結論層

### 結論不可を一級市民にする（R-D / NP5+8）

現行は 4 種の `UnavailableReason` のうち **3 種に生成経路が無く、全て `insufficient_data` に潰れている**（F-12）。
加えて**抑止の痕跡が残らない**（E-17: `rejection_reason` 列が無く、ガードが結論を止めても記録がゼロ）。

v3 の規範:

- 結論導出は `Conclusion | Unavailable` を返す。`Unavailable` は理由・不足しているもの・**解消条件**を持つ
- **ガードが結論を抑止したら、抑止自体が記録される**。「なぜ結論しなかったか」が NP6 の対象になる
- 各 `UnavailableReason` には**生成経路と、それを検証するテストが対で存在する**（S5 が生存を監視）

### provenance は構築時に埋まる

`Conclusion` は `Provenance` 無しに構築できない（K 層の制約）。
現行のように「結論を作ってから audit_trace を後付けで組み立てる」構造ではないため、
NP6 の欠落（E-08 の LLM プロンプト記録漏れなど）が起きない。

---

## 8. L4 — 較正層

### 単一経路の原則

現行は**ガード本体（`evaluate_for_country` / `is_truly_dormant`）が本番から一度も呼ばれず、
実際の判定は 4 ヘルパーを個別に呼ぶ再実装経路**を通っていた（E-03）。
つまり**テストされている式と、動いている式が違う**。

v3 では提案生成・適用・却下のすべてが単一のガード評価器を通る。迂回路を作れない構造にする。

### ラベルの系列管理（F-16 の解消）

recall baseline の `since` が null で、**帰属修正の前後を跨いで比較できてしまう**ことが実測で判明した。
v3 ではラベルと baseline が**系列 ID**を持ち、系列を跨いだ比較は機械的に拒否される。

### 較正の入力に認可をかける（G-01）

feedback ラベルは較正チェーンの入力である。現行は role ゲートが無い。
v3 では**較正に影響する書き込みはすべて analyst 以上**を要求する（S2-PROP-021）。

## 9. L5 — 自己検証層（新設・本リビルドの中核）

> **設計思想**: このツールの最悪の失敗は「間違った結論を出すこと」ではなく
> **「検知できなくなったことに気づかないこと」**である。それを検出する機構を、
> 検証対象から独立した層として持つ。

### 5 つの監視

| 監視 | 何を見るか | 由来した実際の欠陥 |
|---|---|---|
| **発火生存監視** | 各センサー・各判定フラグについて「最後に発火したのはいつか」。長期無発火を異常として提示 | **F-08**（gps_jamming が恒久無発火。実装当初から誰も気づかず） |
| **単位整合検査** | 閾値と被比較値のスケールが型的に整合しているか | **F-08**（比率 vs 百分率） |
| **窓健全性検査** | ベースラインの実効窓（サンプル数 × 取得周期）が宣言と一致するか | **F-06**（30 日のつもりで 7.5 時間） |
| **設定到達性検査** | registry のキーが実際に解決経路を通って読まれているか | **G-04**（registry 登録済みなのに getenv 直読み） |
| **ゲート生存検査** | 安全ゲート自体が機能しているか（存在しない関数を呼んで恒久 open になっていないか） | **G-07**（recall ゲートが恒久 open）、**G-02**（利用者別閾値が評価に効かない） |

### 系譜監査（D2 D-01 への回答）

較正インシデント #1〜#3 は**構造では直らない**（ラベル生成器のロジックバグ）。
L5 は代わりに**再発の検出条件**を持つ:

- 平穏期に FN が増加 → **ツールでなく生成器を疑うアラート**
- 閾値緩和が特定シナリオに偏る → 帰属汚染の兆候（#3 の signature）
- baseline のセルが構成上 recall=1.0 に固定 → blanket-TP の signature（**G-08 で現存が実測された**）

### L5 自身の生存

L5 が黙って死ぬと元の木阿弥なので、**L5 は自身のハートビートを出力し、AP3 チップに露出する**。
「自己評価が最後に走ったのはいつか」がアナリストから見える。

## 10. L6 — 公開層

- **読み取り API は射影**。採点・登録・emit などの副作用を持たない（A-01 の構造的解消）
- **指令 API は明示的**。状態を変えるものは POST/PUT/DELETE のみで、認可が宣言的に付く
- **契約は 1 系統**。v1/v2 の重複 10 対を統合し（S2-PROP-002〜011）、envelope も 1 形に統一（G-13）
- **NP7 disclaimer は envelope の必須フィールド**。欠ける形を作れない（現行は 4 形のうち欠ける形が存在）
- **語彙は country / scenario**。WS プロトコルの `theater` 系イベントは v3 で消える（C-01 の最深部）

---

## 11. L7 — 提示層

- **pure-core + 薄い DOM**。ロジックは DOM 非依存モジュールに置き、テスト可能にする
  （現行は radar.js 14,833 行がカバレッジ 0%）
- **既存の pure module 6 本は規範実装として keep**（triage_score / triage_display_mode /
  self_explanation / map_dim / wp_alarm / hud_v2_overlay）。この形が既に成功しているので全体に広げる
- **採点ロジックをフロントに置かない**。What-If の TL 再実装（G-09、しかもバックエンドと値が違う）は禁止
- **表示の生存も監視対象**。描画スキップ署名の欠落（G-10）は「データは来ているのに表示だけ死ぬ」型

## 12. 横断的関心

| 関心 | v3 の方針 | 解消する欠陥 |
|---|---|---|
| **スケジューリング** | **永続スケジュール**（次回実行時刻を DB に保持）。プロセス内カウンタは使わない | **F-01**（再起動で高オフセットのジョブが走らない）。S4-NF が規範化済 |
| **設定** | 宣言的レジストリ 1 系統。直読み禁止（K 層の `Threshold` 型） | A-13、G-04、F-15 |
| **認可** | エンドポイント定義に宣言的に付く。実装内の手続き呼び出しに依存しない | **G-01**（呼び忘れが起きる構造） |
| **テスト隔離** | 接続注入を強制。テストが本番 DB に触れる経路を構造的に作らない | **B-08**（tradecraft 全表がテスト残骸だった）。tier governor の `_block_live_db_access` が先例 |
| **i18n** | 日本語単一言語。全 UI 文字列が辞書経由（S4 に編入済） | C-06 |
| **CI** | 全ゲートを CI で強制（現行は pre-commit が secrets 走査のみ、workflows 不在） | **G-12** |

## 13. 設計が解消しない領域（正直な限界）

D2 §D の 3 欠陥は v3 でも残る。**L5 は検出を担うが、予防はしない**:

| 欠陥 | v3 での扱い |
|---|---|
| D-01 ラベル生成器のバグ | L5 の系譜監査で**検出**する。生成器自体の正しさは保証できない |
| D-02 外部 API の脆さ | L0 のアダプタ薄化で**差し替えを安く**する。壊れること自体は防げない |
| D-03 運用者の錬度依存 | K 層の型で**表現できるものは型へ**（TL 比較、単位、窓）。残りは検証ゲート |

またリビルド自体のリスクも残る: **v3 は新しい沈黙失敗を作りうる**。
これに対する唯一の防御が L5 と S5 のパリティゲートであり、それゆえ両者は
「後で足す」ものではなく**最初に作る**（P3 の作業順序に反映する）。

## 14. 現行構造との対応（参考情報 — 設計の根拠ではない）

ADR-V3-003 により本書の構造は目的から導出したが、実装計画のために対応を記しておく:

| v3 層 | 主に引き継ぐ挙動（port） | 主に捨てる実装（rewrite/discard） |
|---|---|---|
| K | — | 新規 |
| L0 | センサー 34 基の外部 API 知識（D1-sensors §4 の 20 項目） | base.py、各センサーの取得実装 |
| L1 | ベースライン数式、observation スキーマ | database.py（god-module）、第 2 SQLite |
| L2 | 収斂・TL 導出・dedup の全数式（S1-scoring-core 44 条項） | engine.py / scoring.py の重複実装 |
