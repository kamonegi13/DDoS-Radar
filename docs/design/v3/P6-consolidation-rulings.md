# P6 — 統合裁定（意味論的二重機構と導出未完領域の処遇）

**背景**: 2026-08-06 の設計再評価（4 視点の独立監査: スコアリング系仕様・入力系仕様・API 面・UI/UX）で、
共通する構造的弱点が確認された — **演繹の規律が P 文書の内側で止まっている**。P4 の 11 ステップ分解と
P5 の 155 件裁定はバックエンドの機械的複製には効いたが、(1) **意味論的な二重機構**（同じ問いに答える
別システム）が S1 仕様に CORE MUST として温存され、(2) **API と UI は「目的が要求するか」でなく
「消費者がいるか」で剪定**されており、(3) P3 の完了条件が S1 条項 ID に紐づくため、
**裁定なきまま実装すると二重機構が両方とも忠実に再建される**。

**位置づけ**: P5 §4（O-1〜O-13）の続番。**各裁定は推奨を実装既定とする** — 実装セッションは本書の
推奨に従い、オーナーが個別に覆した場合のみ変更する（覆した場合は ADR として記録）。

**判定の物差し**: ツール定義 4 文 + NP1-NP7 / AP1-AP4 + P4 §5（特に基準 2「隣接ステップの責務が
重ならない」を**仕様・API・UI にも適用する**）。

## O-14 — 採点パイプラインの一本化（影響最大）

| | |
|---|---|
| **対象** | engine 系（S1-SCORE-001〜006: cap 10、min-confidence ゲート収斂）と scenario 系（S1-SCORE-007〜018: `DOMAIN_CAP` 6.0、participant 数ゲート収斂）の 2 式族。S1-SCORE-018 の RationaleEntry→Signal 変換はこの 2 表現の橋渡しのためだけに存在 |
| **問題** | P4 §3 が v1 の病巣として名指しした「S5 の式重複」が、S 仕様では両系とも CORE MUST として清書され、一本化は scoring-core §7-1 の「未決」に退避。WP-2.4 の完了条件「S1-scoring-core の全条項が実装され」はこのままだと**二重実装を再建する** |
| **裁定（推奨=実装既定）** | v3 L2 は**単一の採点カーネル 1 本**のみ実装する。正とするのは**本番で実際に TL に到達している実効経路**（実装調査で確定し、除外条項リストを WP-2.4 成果物に含める）。実効経路に無い側の式族は移植しない |
| **パリティ** | 影響なしが要件。パリティ比較対象は「現行系の実効出力」であり、実効経路を写せば一致する。実効でない式族の除外はそもそも出力に現れない |
| **反映先** | WP-2.4（完了条件を「実効経路条項の実装 + 非実効条項の明示的除外リスト」に変更済） |

## O-15 — トレンドと severity スケールの単一化

| | |
|---|---|
| **対象** | (a) O-2 トレンドの 2 系統: S1-SCORE-036（TL 遷移数、4 語彙）と S1-CONC-015〜017（severity 平均差、5 語彙）。相互に言及なし。(b) 「severity」の同語二系統: 用語規約は `6−TL`、trend.py 内部は `5−TL`（S1-CONC-016 に 2026-08-06 注記済） |
| **裁定（推奨=実装既定）** | O-2 の計算主体は **CONC 系（TREND 結論）1 本**。SCORE-036 は v3 に移植しない。severity は **`6−TL` の 1 スケールに統一**し、K 層 `ThreatLevel.severity()` 以外の写像実装を禁止する |
| **パリティ** | trend は差分（delta）計算のため定数シフトは消える — **出力不変**。SCORE-036 の非移植は消費者調査（HUD のどのチップが読むか）を WP-2.4 で行い、消費者がいれば TREND 結論から供給する |
| **反映先** | WP-2.1（K 層）、WP-2.4、WP-3.1 |

## O-16 — TL 時系列の 1 ストリーム化

| | |
|---|---|
| **対象** | TL 時系列の 4 レーン（TL 観測系列 / TL 履歴 / conclusions 台帳の変化ゲート間引き行 / 結論不可継続性台帳）+ 補償機構 3 段重ね（間引きが慢性検知を壊す→継続性台帳、フラッピング取りこぼし→デューティ比） |
| **裁定（推奨=実装既定)** | L1 に**無間引きの TL 観測ストリーム 1 本**を持ち、トレンド・慢性検知・null-zone・replay・履歴 API は**すべて派生ビュー（クエリ）**として実装する。変化ゲート・継続性 run 状態機械・デューティ比補正は独立機構としては作らない |
| **パリティ** | 派生ビューが現行の各出力形を再現すること（間引き済み履歴も無間引きストリームから射影可能）。retention は ADR-V3-005 の 365 日（結論台帳）に従う |
| **反映先** | WP-2.2（L1 設計要件に追加済）、WP-3.1 |

## O-17 — 収斂機構の統合とインテルの位置づけ

| | |
|---|---|
| **対象** | 収斂判定 5〜6 機構（採点層ドメイン収斂 / convergence_tracker / intel 照合エンジン / 渡航勧告の多政府収斂 / シーケンス連鎖。climate は ADR-V3-008 で凍結済）、corroborator の 3 定義、dedup 約 10 系統、インテルキューの判定エンジン 4 併走（tier ラダー / auto-judge / 照合 / 起動時遡及）— 事実上の**第二の採点パイプライン** |
| **裁定（推奨=実装既定）** | (a) **収斂の数式は S5（L2 採点カーネル）の 1 箇所のみ**。convergence_tracker・照合エンジンの「複数ソースが同じ事象を見ているか」判定は S5 への入力（独立性メタデータ）に還元し、独立した収斂スコアラーとしては移植しない。(b) **LLM 抽出は S2 の一アダプタ**とし、intel item は観測として L1 に落とす。score_delta・独自減衰・独自 dedup は L2 の一元機構に吸収。(c) **人間レビューの状態機械（pending/confirmed/rejected/overridden）は I-2 として存続**（NP7）。ただし到達不能状態（review_needed 終端・shadow_dual）は移植しない（P5 DROP 済含む）。(d) dedup は「投入時の同一性判定（S2）」と「採点時の二重計上防止（S5）」の 2 責務のみに整理 |
| **パリティ** | 実効出力（結論系列・TL）の一致で検証。auto_confirm 挙動の変化は「予期された差分」として事前登録（P2 §5-C） |
| **反映先** | WP-2.5/2.7（アダプタ）、WP-2.4（S5）、WP-3.1。**規模が大きいため WP-2.7 着手時に詳細設計 1 枚を先行させる** |

## O-18 — 設定の二分（registry の適用範囲）

| | |
|---|---|
| **対象** | 各 S1 仕様の「v3 への示唆」が一様に「ハードコード閾値を全部 registry へ」と要求 → 実行すると登録面が 98 → 250〜350 キー規模へ**拡大**する。一方 D2 G-15 / S1-CONF-008 の実測は「95/98 キーが数ヶ月死んでいて誰も困らなかった」= **実行時可変であるべきキーはごく少数**という強い証拠 |
| **裁定（推奨=実装既定）** | NP6 が要求するのは**開示**であって**実行時可変性**ではない。閾値を 2 群に分ける: (a) **運用可変キー（目標 20〜30 個）**のみ 3 層 registry に登録 — アナリストが実際に触る蓋然性で選定し、選定理由を各キーの `why` に記す。(b) 残りは **K 層 `Threshold` 型の provenance 付き定数** — 式 ID・値・出典を開示し監査可能だが、変更はコード変更（= レビューと再較正を強制）。「全部 registry へ」の記述は本裁定で上書きする |
| **パリティ** | 影響なし（値は変えない。置き場所と可変性の宣言だけが変わる） |
| **反映先** | WP-2.1（K 層 `Threshold`）、WP-1.2（到達性検査の対象は (a) 群のみで足りる）、各 S1 仕様の「v3 への示唆」節 |

## O-19 — API / UI の導出文書（Phase 4 の前提・新 WP-4.0）

| | |
|---|---|
| **対象** | (a) **API**: O-1〜O-12 × endpoint の必要性マトリクスが存在せず、剪定基準が「消費者の有無」。既定軌道は 167 本中約 125 本（75%）温存。目的写像の無い約 35〜40 本（salute_report / weather_brief / ip_check / spof / compare / discovery 系 / deep_analytics 等）が無審査 keep。センサー健全性 4〜5 形・TL 履歴 3 形・異常イベント 3 形・監査台帳 3 面が未統合。O-9（AP1 順位）・O-10（決定論的説明）は API に半分しか存在せず、既存 narrate API は LLM 駆動で **P4 S7 の「テンプレート+スロット、LLM 不使用」と矛盾**。(b) **UI**: S1-frontend 72 条項の根拠欄は全て現行コード行番号（転写）。アナリスト一次ループ・情報階層の設計が 0 件。条項ゼロの宙吊りパネル群（連鎖 / 国詳細 / インテル / History / SPOF / Corr Heatmap 等）の生死が実装者の独断に委ねられる |
| **裁定（推奨=実装既定）** | **WP-4.0「API/UI 導出設計」を新設し、WP-4.1 / WP-4.2 の前提とする**。成果物: (1) O×endpoint 必要性マトリクス + threat_data 分解の目標形状 + 冗長 endpoint の統合裁定 + O-9/O-10 の台帳化 endpoint 新設案、(2) アナリスト一次ループ 1 枚（朝の状況確認 → トリアージ → ドリルダウン → フィードバック）+ O→画面要素の順方向トレーサビリティ表 + 宙吊りパネルの生死裁定 + AP3 表示の合成化（12 チップ並列 → 合成 1 + 内訳ドリルダウン）検討。**narrate の AP2 準拠化**（決定論テンプレート、LLM 不使用）を含む |
| **パリティ** | API/UI はパリティゲートの対象外（比較対象は結論系列）。ただし v1 API sunset は ADR-V3-009 に従う |
| **反映先** | P3 に WP-4.0 追加済。**設計セッション（Fable）で実施** — 実装 WP ではない |
