Intelligence Operations Guide — MDO C4ISR Strategic Radar

        
    

    


        

        
This platform is an MDO C4ISR Strategic OSINT Radar designed to detect precursor indicators of kinetic operations by correlating signals across three domains: Cyber, Physical, and Information. All data is sourced exclusively from open-source intelligence (OSINT). Sensors run on independent background schedules, and the convergence score is recalculated every SCORE_REFRESH_SEC=60 seconds from the latest cached data. The SYNC button forces an immediate fetch and score update across all active sensors.

        

        

        
本プラットフォームは MDO C4ISR 戦略OSINTレーダー です。サイバー・物理・情報の3ドメインにわたるシグナルを相関分析し、動態作戦の前兆指標を検出します。すべてのデータはオープンソースインテリジェンス（OSINT）のみから取得しています。各センサーは独立したバックグラウンドスケジュールで稼働し、収束スコアは最新キャッシュデータから SCORE_REFRESH_SEC=60 秒ごとに再計算されます。SYNC ボタンで全アクティブセンサーの即時取得とスコア更新を強制実行できます。

        


        

            
            
            
            
            
            
            
            
            
            
            
            
        


        

        

        
1. Multi-Domain Sensor Architecture (33 Sensors)


        
Cyber Domain (weight 0.50 default) — Highest-weighted domain. State-directed cyber operations typically precede kinetic action by 24–72 hours. Weights configurable via DOMAIN_WEIGHT_CYBER, DOMAIN_WEIGHT_PHYSICAL, DOMAIN_WEIGHT_INFO (must sum to 1.0).

        
    
            
  • Cloudflare Radar API [poll: 15 min]: Covers over 20% of global internet traffic. Provides L3 (volumetric) and L7 (application-layer) DDoS telemetry. Spike detection uses HOD (Hour-of-Day) Z-score normalization: the current spike ratio is compared against the historical distribution of the same UTC hour over the past 28 days, eliminating diurnal bias (daytime attack concentrations inflating flat-average baselines). Detects botnet overlap across allied theaters and identifies L7 vector shifts (HTTP flood transitions).
                
    HOD baseline is pre-fetched at startup in a background thread (~7 s per theater): (1) one L7 hourly timeseries call fetches 28 days × 24 h of attack intensity; (2) 28 daily origin-distribution calls provide per-day adversary share. Each HOD slot's spike estimate = daily_avg_spike × (hour_intensity / day_avg_intensity), giving real per-hour baselines immediately without waiting for accumulation. All 24 UTC-hour slots are filled at startup — no warmup period on any slot. Falls back to raw ratio thresholds (2×/4×/6×) only if timeseries is unavailable. Outliers capped at 25×. Sources with absolute share <1% excluded. Non-adversary floor: 3%; adversary floor (CN/RU/KP): 0.5% to retain low-volume state operations. HOD baseline (672 pts/theater) persisted across restarts.
            
    • 
            
  • ThreatFox (abuse.ch) API [poll: 1 hr]: Queries IoCs (Indicators of Compromise) with APT tags published in the past 24 hours. Matches against APT tag or target country name. A hit indicates known APT infrastructure is active in association with the monitored theater. Requires THREATFOX_API_KEY (Auth-Key header).
    • 
            
  • RIPE Stat BGP Routing [poll: 30 min]: Monitors BGP prefix announcement count for the core theater via RIPE NCC. When ≥7 same-UTC-hour samples exist (28-day HOD baseline), anomaly is detected via HOD Z-score: Z < –2.0σ → ANOMALY (+1). During HOD warmup, falls back to flat drop ratio >15% from the previous cycle — a known precursor to internet isolation operations (route withdrawal).
    • 
            
  • DDoS Acceleration Engine [no external poll — computed internally]: Calculates first-order (velocity) and second-order (acceleration) derivatives of the core theater threat score time series via linear regression over a DERIVATIVE_WINDOW=5-point rolling window. Declares an Ambush Pattern when acceleration Z-score (relative to its own rolling history) exceeds AMBUSH_ZSCORE_THRESHOLD=2.0 and both velocity and acceleration are positive — the mathematical signature of exponential escalation. Adds +2 to Cyber domain. Current rate of change is displayed in the VELOCITY meter.
    • 
            
  • GreyNoise Sensor [poll: 30 min] [v9 — Noise Suppressor]: Queries the GreyNoise GNQL Stats API to classify ongoing traffic toward the core theater as TARGETED, MIXED, or NOISE_DOMINANT (internet background scanners). When noise ratio exceeds 70%, all Cyber domain sensor scores are suppressed — preventing mass-scanner events from inflating threat levels during non-adversarial traffic surges. Operates passively (UNKNOWN) when no API key is configured. Requires GREYNOISE_API_KEY (Enterprise GNQL).
    • 
        


        
Physical/Logistics Domain (weight 0.30) — Covers infrastructure, airspace, maritime, and kinetic pre-strike indicators.

        
    
            
  • IODA API (CAIDA) [poll: 5 min]: Tracks BGP-based internet reachability and active probing (ping) success rates. Simultaneous degradation of BGP routing and probing success is classified as a critical infrastructure failure. Cross-validates with the BGP Routing sensor.
    • 
            
  • NASA EONET Wildfire API [poll: 1 hr]: Real-time wildfire and thermal event data from NASA's Earth Observing Natural Event Tracker. Flags events within ±10° of the theater center coordinates. Thermal anomalies near military infrastructure correlate with kinetic strikes, artillery fires, and pre-assault infrastructure destruction. No API key required.
    • 
            
  • OpenSky Network (Civil Airspace) [poll: 30 min]: Monitors civil aircraft count within airport bounding boxes for each theater. Builds a 20-cycle rolling baseline per airport. When ≥7 same-UTC-hour samples are available, severity is determined via HOD (Hour-of-Day) Z-score against the same-hour 28-day history — eliminating diurnal bias from peak/off-peak traffic patterns. HOD Z < –2.0σ → ANOMALY (+2); Z < –3.0σ → CLOSURE (+3). During HOD warmup (<7 same-hour samples), falls back to flat drop ratio: ≥40% → ANOMALY; <5% → CLOSURE. Score is automatically suppressed during severe weather based on OpenWeatherMap data.
                
    Anonymous API: 400 req/day. Set OPENSKY_CLIENT_ID/OPENSKY_CLIENT_SECRET (OAuth2 client credentials) to expand to 4,000 req/day.
    • 
            
  • PeeringDB / IXP Critical Nodes [poll: 4 hr]: Retrieves registration data for Internet Exchange Points (IXPs) associated with monitored theaters. Used as geographic context for interpreting BGP anomalies and physical infrastructure targeting. Displayed as yellow diamonds (◆) on the map.
    • 
            
  • ISR Hotspot Sensor (OpenSky Military ISR) [poll: 30 min]: Monitors 10 ISR_HOTSPOT zones within a 200 km radius — Taiwan Strait, East China Sea ADIZ, Spratly Islands, Korean Peninsula DMZ, Black Sea, Baltic Sea, and others. Aircraft are flagged as ISR patterns if they meet any of: (1) altitude >9,000 m and speed <160 m/s (high-altitude low-speed orbit), (2) squawk 7777 (government/military transponder), or (3) known ISR callsign prefixes (FORTE/JAKE/MYSTIC/RICO/TROLL, etc.). Detection of ≥3 aircraft simultaneously in the same hotspot triggers an ISR Surge, adding +2 to the Physical domain. Operates independently from the civil airspace sensor (targets straits and patrol corridors, not airports).
    • 
            
  • AIS Maritime Sensor (AISHub) [poll: 30 min]: Monitors vessels near 23 chokepoints — Taiwan Strait, Luzon Strait, Malacca Strait, Hormuz, Bab-el-Mandeb, Baltic Sea, Bosphorus, Suez, and others — using AISHub public position data. Detects two anomaly types: (1) AIS Dark Gap — a previously tracked vessel ceases AIS transmission for ≥AIS_DARK_GAP_THRESHOLD=3600 seconds (1 hour) near a chokepoint, consistent with intentional radio silence, submarine positioning, or covert survey vessels; (2) Stationary Anomaly — a non-commercial, non-fishing vessel (AIS type outside 60–89) drifting at <0.5 knots within 50 km of a chokepoint. Adds +1 to Physical domain. Dark Gap vessels appear on the map as red-halo anchor icons.
                
    A 2-second delay is inserted between each chokepoint request to comply with AISHub guest API rate limits.
    • 
            
  • Check-Host Survival Sensor [poll: 10 min] [v9]: Uses the check-host.net API to verify live reachability of critical national infrastructure URLs (government, parliament, central bank, energy grid) for each monitored theater from 5 geographically distributed global nodes (JP/US/DE/NL/FR). Two-phase API: POST check request → GET result (5 s delay). Status levels use HOD Z-score normalization (28-day same-hour baseline, ≥7 samples): HOD Z < –2.0σ AND success_rate < 80% → PARTIAL (+1); HOD Z < –3.0σ AND success_rate < 30% → BLACKOUT (+3). During HOD warmup, falls back to fixed thresholds: OK (≥80%) / PARTIAL (30–79%) → +1 / BLACKOUT (<30%) → +3. PARTIAL scores +1 (not +2) — Maskirovka policy: only confirmed BLACKOUT warrants a strong signal. High-latency responses above CHECKHOST_TIMEOUT_MS=3000 ms are penalized by 50%. Displayed as the SURVIVAL HUD indicator. Configure node list via CHECKHOST_NODES in config.env.
    • 
        


        
Information Domain (weight 0.20) — Propaganda and diplomatic tone analysis. The earliest leading indicator; typically shifts 48–96 hours before an operation.

        
    
            
  • GDELT TimelineTone API [poll: 30 min]: Retrieves media tone for the core theater from the Global Database of Events, Language, and Tone. Triggers an alert (+1) when the tone score falls below –15.0 OR when DoW (Day-of-Week) Z-score < –2.0σ versus the same-weekday 28-day baseline (≥3 same-weekday samples required). DoW normalization prevents false alerts from predictable weekly news cycles (e.g., Monday editorial tone is compared only against previous Mondays). Reference values: Russia→Ukraine pre-conflict period was –12 to –15; day of invasion was –18 to –25. –15.0 is the threshold for active military-tension rhetoric. Auto-suppressed during severe weather.
    • 
            
  • RSS Narrative Burst Sensor [poll: 30 min]: Scans adversary state-aligned RSS feeds selected dynamically by the active Threat Actor configuration (ADVERSARY_NARRATIVE_SOURCES). Sources are bloc-specific: RU → TASS + RIA Novosti; CN → Xinhua + Global Times; IR → Mehr News + Tasnim; KP → KCNA Watch; BY → TASS (RU proxy). Only sources relevant to the configured adversary bloc are polled — eliminating cross-bloc noise. Falls back to all sources when no adversary is configured. Matches theater-specific tactical keywords (e.g., for Taiwan: "military measures", "ultimatum", "median line crossing", "live-fire drills") against article titles and descriptions. Z-score analysis applied to normalized frequency (hit count ÷ total articles) using a 30-day rolling baseline. Alert thresholds: Z > NARRATIVE_ZSCORE_ALERT=2.0 → BURST (+1); Z > NARRATIVE_ZSCORE_CRITICAL=3.0 → CRITICAL_BURST (+2). Deduplication via normalized 60-character title key. Baseline activates after ≥7 days of data accumulation (cold-start guard).
    • 
            
  • Telegram Mirror Sensor [poll: 15 min] [v9]: Fetches public Telegram channel web previews (t.me/s/) for channels registered in THREAT_ACTOR_MAPPING (hacktivist groups mapped to theaters). No login or API token required. Only channels with public web preview enabled are accessible — private or restricted channels are automatically detected and skipped. Each unique channel is scraped once per cycle regardless of how many theaters it maps to (dedup). Content-hash dedup prevents the same unchanged post from re-appearing in the intercept log across poll cycles. Extracts attack intent keywords (target, ddos, http flood, under attack, op, etc.) and target URLs (.gov / .mil / bank / energy domains). Z-score analysis is applied to keyword frequency (hits per channel scraped) against a 30-day rolling baseline — the same thresholds as the RSS Narrative sensor. Detection levels: CRITICAL_BURST (Z ≥ 3.0, +2) / BURST (Z ≥ 2.0, +1) / INTENT_DETECTED (keyword match, +1) / TARGETS_FOUND (+1) / CLEAR. Baseline activates after ≥7 days of data. Confidence weighting: each channel has a confidence_weight (0.40–0.75) defined in TELEGRAM_CHANNEL_META in geo_data.json; when the mean channel confidence is below TELEGRAM_CLAIM_CONFIDENCE_THRESHOLD=0.5, the score is reduced by 1 to suppress unverified hacktivist claims. Detected channels and target URLs are displayed in the CHAIN panel. A NARRATIVE_BURST event is registered in the escalation chain on burst or intent detection. Configure keywords via TELEGRAM_ATTACK_KEYWORDS.
    • 
            
  • Hacktivist News Sensor [poll: 30 min] [v10]: Monitors security news RSS feeds (BleepingComputer, TheRecord, TheHackerNews, CyberScoop, DarkReading) for hacktivist campaign reporting. Implements the "observation of observers" OSINT principle — security journalists and researchers who monitor private Telegram channels publish their findings on public news sites, making this an indirect but OPSEC-safe intelligence source. Pre-filters articles by hacktivist/DDoS keywords (group names, attack types, campaign language), discards marketing/retrospective content, then submits to LLM for structured analysis: group name, target theater, attack type, urgency, confidence. Items are submitted to the intel queue as source_type="hacktivist", sharing the same pipeline as direct Telegram detections. Free, open, no authentication or API keys required. Configure poll interval via HACKTIVIST_NEWS_POLL_INTERVAL.

Noise Reduction & Human-in-the-Loop (HITL) Control

        
    
            
  • OpenWeatherMap (Weather Noise Filter) [poll: 30 min]: When a significant weather event (thunderstorm, blizzard, hurricane, etc.) is detected at the core theater, Physical domain alerts (IODA BGP failure, OpenSky airspace anomaly) and the Information domain alert (GDELT tone) are automatically marked SUPPRESSED and excluded from scoring. This prevents weather events from triggering false escalations.
    • 
            
  • GreyNoise (Automatic Noise Suppressor) [v9]: When GREYNOISE_API_KEY is configured and the GNQL Stats API classifies >70% of traffic toward the theater as internet background noise (scanners, crawlers, opportunistic probes), the suppress_confidence flag is raised. This automatically suppresses all Cyber domain sensor contributions, preventing scanner waves from being misread as targeted attack operations. Operates silently as UNKNOWN when no API key is set.
    • 
            
  • Analyst MUTE (HITL Override): Each sensor in the Evidence Panel has a [ MUTE ] button. Clicking it immediately excludes that sensor's score contribution and recalculates the convergence score. MUTE state is persisted to browser localStorage across sessions. Use this to suppress known false positives while preserving the underlying sensor record. When multiple sensors are muted, domain weights are correctly recalculated using only the remaining active sensors. All 33 sensors support MUTE.

1. マルチドメイン・センサー・アーキテクチャ（33センサー）


        
サイバードメイン（重み 0.50 デフォルト） — 最も重みが高いドメイン。国家指揮による サイバー作戦は、運動学的行動に24〜72時間先行するのが一般的。重みはDOMAIN_WEIGHT_CYBER、DOMAIN_WEIGHT_PHYSICAL、DOMAIN_WEIGHT_INFOで設定可能（合計1.0）。

        
    
            
  • Cloudflare Radar API [poll: 15 min]: グローバルインターネットトラフィックの20%以上をカバー。L3（ボリューメトリック）およびL7（アプリケーション層）の DDoS テレメトリを提供。スパイク検出にはHOD（時刻帯別）Z スコア正規化を採用：現在のスパイク比率を過去28日間の同じ UTC 時間帯の分布と比較し、昼夜の通信量変動による誤検知バイアスを排除する。同盟国シアター間のボットネット重複を検出し、L7ベクターシフト（HTTP フラッドの遷移）を識別する。
                
    HOD ベースラインは起動時にバックグラウンドスレッドで即時プリフェッチ（シアターあたり約7秒）：(1) L7 hourly timeseries 1回で28日 × 24時間の攻撃強度を取得、(2) 28回の日次オリジン分布コールで敵対国シェアを取得。各 HOD スロットのスパイク推定値 = 日次平均スパイク × (時間帯強度 ÷ 日平均強度) により、蓄積待ちなしで真の時間帯別ベースラインを即時構築。起動時に全24 UTC 時間帯スロットを補完——ウォームアップ期間なし。timeseries 取得不可時のみ生比率閾値（2×/4×/6×）にフォールバック。外れ値は25×に上限設定。絶対シェアが1%未満の送信元は除外。非敵対フロア: 3%; 敵対フロア（CN/RU/KP）: 0.5%。HOD ベースライン（672点/シアター）は再起動をまたいで保持。
            
    • 
            
  • ThreatFox (abuse.ch) API [poll: 1 hr]: 過去24時間に公開された APT タグ付きの IoC（侵害指標）を照会。APT タグまたは対象国名と照合。ヒットは既知の APT インフラが監視シアターに関連して活動中であることを示す。THREATFOX_API_KEY（Auth-Keyヘッダー）が必要。
    • 
            
  • RIPE Stat BGP Routing [poll: 30 min]: RIPE NCC 経由でコアシアターの BGP プレフィックス通知数を監視。同じUTC時間帯のサンプルが7件以上ある場合（28日間HODベースライン）、HOD Zスコアで異常を判定: Z < –2.0σ → ANOMALY (+1)。HODウォームアップ中は前サイクルから15%超のプレフィックス削減にフォールバック — インターネット隔離作戦（ルート撤回）の既知の前兆。
    • 
            
  • DDoS Acceleration Engine [no external poll — computed internally]: コアシアターの脅威スコア時系列に対し、DERIVATIVE_WINDOW=5点ローリングウィンドウで線形回帰による一次（速度）および二次（加速度）微分を算出。加速度Zスコア（独自ローリング履歴対比）が AMBUSH_ZSCORE_THRESHOLD=2.0 を超え、速度・加速度ともに正の場合にアンブッシュパターンを宣言 — 指数的エスカレーションの数学的特徴。サイバードメインに+2を加算。現在の変化率は VELOCITYメーターに表示。
    • 
            
  • GreyNoise Sensor [poll: 30 min] [v9 — Noise Suppressor]: GreyNoise GNQL Stats API を照会し、コアシアターへの継続的トラフィックを TARGETED、MIXED、NOISE_DOMINANT（インターネットバックグラウンドスキャナー）に分類。ノイズ比が70%を超えると、すべてのサイバードメインセンサースコアを抑制 — 非敵対的トラフィックサージ中にマスキャナーイベントが脅威レベルを誇張することを防止。API キー未設定時はパッシブ（UNKNOWN）として動作。GREYNOISE_API_KEY（Enterprise GNQL）が必要。

物理ドメイン（重み 0.30） — インフラ、領空、海上、および運動学的先制打撃指標をカバー。

3. Scoring Engine & Convergence Algorithm

        
The WeightedConvergenceEngine computes a raw threat score from all active, non-suppressed sensor signals, then adds domain convergence bonuses and a sequence bonus. The final score is capped at 15 pts to prevent bonus stacking from producing unrealistic values.


        
Raw Score Components

        
    
            
  • [Cyber]    cf_spike_core:       HOD Z-score vs same-UTC-hour 28d baseline: Z≥1.5σ(+1), Z≥2.5σ(+1), Z≥3.5σ(+1) — max +3. Warmup fallback: raw ratio >2×/4×/6×

Cross-Sensor Correlation Enrichment — When specific sensor pairs co-fire, the system enriches confidence and adds causal context:

        
    
            
  • DDoS-BGP causal link: CF spike + IODA BGP_OUTAGE co-fire → IODA reason enriched with "DDoS-BGP causal link" (attack likely caused the outage)
    • 
            
  • Multi-source physical outage: IHR disconnection + IODA BGP_OUTAGE → both entries set confidence=1.0 (independent confirmation)
    • 
            
  • Confirmed infrastructure degradation: RIPE Atlas + Check-Host both FIRED → Check-Host confidence=1.0. Atlas normal but Check-Host fires → "CDN-layer issue possible" annotation

  • Censorship chain: Tor relay_drop + IHR disconnection → Tor reason enriched with "Censorship chain" + confidence=1.0, registers CENSORSHIP_DETECTED

  • Multi-source censorship: OONI censoring + Tor relay_drop → OONI confidence=1.0, "Confirmed by Tor relay drop" [CAC]

  • Confirmed military activity: NOTAM surge + Airspace closure → NOTAM confidence=1.0, "Confirmed by concurrent airspace closure" [CAC]

Co-occurrence Sensitivity Boost [CAC Phase D] — Historical sensor pair co-firing rates (≥60% co-occurrence in past 72h) multiplicatively boost the raw score by up to 1.5×. Sensitivity only increases, never decreases (paranoid design).


        
Domain Convergence Bonus — Added when anomalies appear simultaneously across multiple domains (evidence of coordinated MDO activity rather than an isolated incident):

        
    
            
  • DUAL CONVERGENCE: Any 2 of 3 domains simultaneously active → +1 pt
    • 
            
  • FULL CONVERGENCE: Cyber + Physical + Info all active simultaneously → +2 pt
    • 
        

        
A domain is considered "active" when its weighted score contribution exceeds the domain threshold. FULL CONVERGENCE is the strongest pre-kinetic signal this system can generate.


        
Sequence Bonus — Applied on top of the convergence bonus when a logical escalation chain is confirmed within a 24-hour window. Acts as an anti-confirmation-bias mechanism (does not fire on dramatic signals in a single domain):

        
    
            
  • Chain definition (loose ordering — presence within 24 hr window, strict chronological order not required):
                
      [1] NARRATIVE_BURST  — Tactical keyword Z-score spike in state media or Telegram intent detection
                
      [2] ISR_SURGE        — Reconnaissance aircraft detected at strategic hotspot
                
      [3] SYNC_DDOS        — Coordinated DDoS from ≥2 theaters (high botnet overlap)
                
      [4] FIRMS_ANOMALY    — Thermal/kinetic event from NASA EONET
    • 
            
  • 4/4 confirmed (within 24 hr) → SEQUENCE_FULL_BONUS = +3 pt
    • 
            
  • 3/4 confirmed (within 24 hr) → SEQUENCE_PARTIAL_BONUS = +2 pt
    • 
            
  • <3 events → No bonus (insufficient pattern)
    • 
        


        
Temporal Coherence Bonus [v9] — Applied when first trigger events (SYNC_DDOS or NARRATIVE_BURST) across multiple theaters are temporally synchronized, indicating a single C2 node:

        
    
            
  • C2_SYNC_CONFIRMED  — ≥2 theaters trigger within 60 seconds of each other → +2 pt
    • 
            
  • C2_SYNC_PARTIAL    — ≥2 theaters trigger within 5 minutes of each other → +1 pt
    • 
            
  • Displayed in the HUD as C2-SYNC. Distinguishes nation-state coordinated operations (tight synchronization) from independent hacktivist campaigns (loose timing).
    • 
        


        
Blockade Index (HUD display) — A gauge to quantitatively distinguish "political signaling" DDoS from actual infrastructure neutralization:

        
    
            
  • Formula:  attack_weight = min(DDoS_spike, 10) × (1 + RIPE_drop_pct/100)
    • 
            
  •           infra_deg     = 1.0 − CheckHost_success_rate  (0 = OK, 1 = BLACKOUT)
    • 
            
  •           Blockade Index = min(attack_weight × (0.10 + 0.90 × infra_deg), 10)
    • 
            
  • 10% noise floor: attack is visible even when infra is healthy. 90% infra-weighted: real blockade requires actual connectivity loss. When CheckHost is unavailable (API error), treated conservatively as OK (rate=1.0).
    • 
            
  • NORMAL                        — Index < 1.5: DDoS present but infrastructure reachable. Typical signaling operation.
    • 
            
  • POLITICAL_NOISE               — 1.5–3.9: Significant cyber activity, infrastructure impact unconfirmed.
    • 
            
  • SEVERE_DISRUPTION             — 4.0–6.9: High DDoS + RIPE prefix reduction + partial Check-Host failure simultaneously.
    • 
            
  • INFRASTRUCTURE_NEUTRALIZATION — ≥ 7.0: Large-scale DDoS + BGP withdrawal + infrastructure blackout. Signature of a pre-invasion communications cutoff.
    • 
        


        
Triangulation Bonus [WM] — Applied when ALL three domains (Cyber, Physical, Info) independently confirm anomalous activity with score ≥ 1 AND confidence ≥ 0.5. This is the highest-confidence convergence signal — unlike the FULL CONVERGENCE bonus which triggers on domain threshold alone, Triangulation requires quality thresholds on both score and confidence:

        
    
            
  • Condition: All 3 domains score ≥ 1 AND confidence ≥ 0.5
    • 
            
  • Bonus: TRIANGULATION_BONUS (0.5) × average domain confidence
    • 
            
  • Displayed in the HUD as TRI: CONFIRMED (red). Hidden when inactive.
    • 
        


        
Silent Divergence Detection [WM] — Detects the reconnaissance/preparation phase pattern where Cyber AND Physical domains show anomalies but the Information domain is completely silent (score = 0). This absence of propaganda suggests adversary operational security rather than the typical pre-conflict media buildup:

        
    
            
  • Condition: cyber ≥ 1 AND physical ≥ 1 AND info == 0
    • 
            
  • Minimum fired sensors (cyber + physical combined) ≥ SILENT_DIVERGENCE_THRESHOLD (2)
    • 
            
  • Confidence: HIGH (combined ≥ 6) / MEDIUM (≥ 3) / LOW (< 3)
    • 
            
  • Score injection: +2 (HIGH) or +1 (MEDIUM/LOW) to cyber domain as “silent_divergence”
    • 
            
  • Displayed in the HUD as SILENT: HIGH/MED/LOW (orange). Hidden when inactive.
    • 
            
  • Anti-bias note: This pattern is also consistent with benign explanations (sensors offline, calm news cycle). The confidence tier system explicitly communicates uncertainty to the analyst.
    • 
        


        
Theater Baseline Z-Score [WM] — Provides per-theater historical context by computing how the current score compares to its own 30-day rolling average. The same raw score of 4.0 means very different things for a chronically active theater (TW) vs. a normally quiet one (Baltic):

        
    
            
  • Window: THEATER_BASELINE_WINDOW (30 days), minimum THEATER_BASELINE_MIN_SAMPLES (20) required
    • 
            
  • Formula: Z = (current_score − baseline_mean) / baseline_std
    • 
            
  • Anomalous: Z > 2.0 (current score is >2σ above this theater’s normal)
    • 
            
  • Displayed in the HUD as BASE-Z: ±X.XXσ — red (>2σ), yellow (>1σ), green (<−1σ), white (normal)
    • 
            
  • Theater baseline does NOT modify the score — it provides context only. The analyst decides whether an anomalous baseline deviation warrants action.

4. Threat Levels

        
Final Score = Raw Score + Convergence Bonus + Sequence Bonus. A 1-cycle hysteresis delay is applied on downgrade only (prevents threshold oscillation). Upgrades are immediate.

        
    
            
  • Level 1 — CRITICAL: Score ≥ 9 AND hard conditions met (core spike >5.0× AND BGP failure confirmed simultaneously). Combined signature of large-scale cyber surge and infrastructure collapse — coordinated pre-invasion blackout operation. Kinetic action probability is extremely high. Activate all emergency procedures.
    • 
            
  • Level 2 — SEVERE: Score ≥ 6 AND ≥ 2 active domains. Single-domain signals (e.g., Cyber-only) cannot reach TL2 regardless of score — multi-domain corroboration is mandatory. Multi-domain threat with direct adversary attribution or significant infrastructure degradation. Immediate commander notification required.
    • 
            
  • Level 3 — HIGH: Score ≥ 4. Significant coordinated anomalies spanning at least 2 sensors. Indicates preparation phase, probing operations, or initial escalation. Enhanced monitoring required.
    • 
            
  • Level 4 — ELEVATED: Score ≥ 2. Early indicators such as deteriorating media tone, isolated BGP events, or minor L7 vector shifts. Consistent with worsening diplomatic tensions or reconnaissance activity.
    • 
            
  • Level 5 — NORMAL: Score < 2. Background noise level. No significant anomalies across monitored domains.
    • 
        


        

        

        
4. 脅威レベル

        
最終スコア = 生スコア + 収束ボーナス + シーケンスボーナス。 ダウングレード時のみ1サイクルのヒステリシス遅延を適用（しきい値振動を防止）。アップグレードは即時。

        
    
            
  • レベル1 — 危機的: スコア ≥ 9 かつハード条件を満たす（コアスパイク >5.0× かつ BGP 障害が同時確認）。大規模サイバーサージとインフラ崩壊の複合特徴 — 協調的侵攻前ブラックアウト作戦。運動学的行動の確率が極めて高い。すべての緊急手順を発動すること。
    • 
            
  • レベル2 — 深刻: スコア ≥ 6 かつ 2ドメイン以上がアクティブ。単一ドメイン（例：サイバーのみ）はスコアに関わらずTL2に到達不可 — 複数ドメインの裏付けが必須条件。直接的な敵対帰属または重大なインフラ劣化を伴うマルチドメイン脅威。直ちに指揮官への通知が必要。
    • 
            
  • レベル3 — 高: スコア ≥ 4。少なくとも2つのセンサーにまたがる重大な協調異常。準備フェーズ、探査作戦、または初期エスカレーションを示す。監視強化が必要。
    • 
            
  • レベル4 — 上昇: スコア ≥ 2。メディアトーンの悪化、孤立した BGP イベント、または軽微な L7 ベクターシフトなどの早期指標。外交的緊張の悪化または偵察活動と整合。
    • 
            
  • レベル5 — 平常: スコア < 2。バックグラウンドノイズレベル。監視ドメイン全体で重大な異常なし。

  • Iran Internet Shutdown (2019): Near-complete BGP route withdrawal before domestic elections — a full isolation pattern. Corresponds to INFRASTRUCTURE_NEUTRALIZATION on the Blockade Index.

6. Analyst Workflow & Best Practices

        
    
            
  • Prioritize cross-domain corroboration. Do not escalate on single-domain indicators alone. Civilian botnets regularly produce 3–5× DDoS spikes without any military significance. The minimum standard for recommending a Level 2 escalation is FULL CONVERGENCE (Cyber + Physical + Info).
    • 
            
  • Suppress known false positives via HITL MUTE. When a non-adversarial source is confirmed (e.g., airspace anomaly from a major sporting event, BGP shift from legitimate CDN maintenance), mute that sensor in the Evidence Panel. MUTE state persists across reloads via localStorage.
    • 
            
  • Use SITREP for commander reporting. The SITREP button generates a structured situation report including domain breakdown, sensor evidence, and trend indicators.
    • 
            
  • Verify baseline sufficiency. Cloudflare HOD Z-score activates after ≥7 same-hour samples per UTC hour are accumulated. On first launch, a background prefill populates all 24 UTC-hour slots within ~7 s per theater using CF L7 timeseries (hourly intensity) combined with per-day origin distributions — no warmup period is expected under normal conditions. "HOD warmup N/7" in the Evidence Panel indicates the timeseries was unavailable and the slot is accumulating via live polling. RSS Narrative similarly requires ≥7 days of data. Check per-sensor baseline status in the Data Status panel.
    • 
            
  • Read the VELOCITY / AMBUSH meters. VELOCITY is the current rate of change of the threat score (pts per polling cycle ≈ 900 s). Positive (red ↑) = actively deteriorating. Negative (green ↓) = improving. ⚡ AMBUSH (red blink) = the rate of change itself is accelerating — a second-derivative spike. This is the most time-critical signal: it indicates a rapidly compressing attack window.
    • 
            
  • Read the escalation narrative in the CHAIN panel. The CHAIN button (HUD top-right) opens the evidence chain timeline. Displays timestamped [NARRATIVE_BURST → ISR_SURGE → SYNC_DDOS → FIRMS_ANOMALY] escalation events within the past 24 hours. FULL CHAIN (+3 pt) means all 4 event types appeared within 24 hours — a strong indicator of coordinated multi-domain preparation. v9 also registers TELEGRAM_INTENT, MASKIROVKA, C2_SYNC, and INFRA_BLACKOUT in the chain log.
    • 
            
  • Interpreting GDELT tone. –15.0 = threshold for active military-tension rhetoric (v9 calibration). –18 = active crisis framing. Below –20 = historically corresponds to kinetic action imminent or in progress. A 3–5 point drop within a single 30-minute polling cycle is more significant than a gradual decline to the same value.
    • 
            
  • Interpreting the Blockade Index. The index scales with both DDoS intensity and infrastructure degradation: high-volume DDoS that leaves Check-Host nodes reachable produces only the 10% noise floor contribution (Index ≈ 1.0). INFRASTRUCTURE_NEUTRALIZATION (Index ≥ 7.0) requires simultaneous DDoS surge, RIPE BGP withdrawal, AND Check-Host BLACKOUT from global nodes — the pattern observed 30–90 minutes before the Russian ground invasion in February 2022.
    • 
            
  • Interpreting the SURVIVAL HUD (v9). Shows real-time reachability of critical national infrastructure (government, central bank, energy grid) from global nodes. OK = infrastructure reachable. PARTIAL = some nodes report failure — possible DDoS effect or localized disruption. BLACKOUT = critical infrastructure unreachable from multiple global vantage points simultaneously. BLACKOUT + high Blockade Index = likely pre-invasion blackout scenario.
    • 
            
  • Interpreting C2-SYNC (v9). Displays whether attacks across multiple theaters started within 60 seconds (C2 SYNC CONFIRMED) or 5 minutes (PARTIAL). Tight temporal synchronization across geographically separated theaters is the hallmark of nation-state integrated C2 (command and control) rather than loosely coordinated hacktivist activity.
    • 
            
  • Maskirovka detection (v9). If physical outage is confirmed (IODA degraded or Check-Host BLACKOUT) while all narrative channels are simultaneously silent (no RSS burst, no Telegram intent), the system flags a potential Maskirovka (Russian military deception doctrine). PARTIAL Check-Host status alone does not trigger this — only full BLACKOUT, reducing false positives from localized node failures. Physical disruption without accompanying narrative amplification may indicate a genuine kinetic operation rather than a hacktivist campaign — hacktivist groups typically announce targets loudly before and during attacks.
    • 
            
  • Confirmed intel decays exponentially (ADR-023). When you confirm an LLM intel item, its contribution to the scenario score is no longer full-strength for 24h then zero — it enters at full weight and decays as exp(-age / τ) with τ=12h. Practical meaning: at age 12h the item contributes ~37%, at 24h ~14%, at 36h ~5%, fully removed at 48h. TL does not rise abruptly the moment you click CONFIRM; fresh confirms dominate the cap, stale items fade naturally. If you need a legacy binary-TTL comparison for calibration, set INTEL_AGE_DECAY_ENABLED=false in Config. Per-source τ override (e.g. fast-moving diplomatic signals) via INTEL_AGE_DECAY_TAU_HOURS_DIPLOMATIC=6. The Evidence Panel shows (age X.Xh, w=Y.YY) beside each confirmed item so you can see decayed vs. raw weight at a glance.

6. アナリストのワークフロー & ベストプラクティス

        
    
            
  • クロスドメインの裏付けを優先する。 単一ドメインの指標だけでエスカレーションしないこと。民間ボットネットは軍事的意義なしに定期的に3〜5倍の DDoS スパイクを生成する。レベル2のエスカレーションを推奨するための最低基準は FULL CONVERGENCE（サイバードメイン + 物理ドメイン + 情報ドメイン）である。
    • 
            
  • HITL MUTE で既知の誤検知を抑制する。 非敵対的な原因が確認された場合（例：大規模スポーツイベントによる領空異常、正規 CDN メンテナンスによる BGP シフト）、エビデンスパネルでそのセンサーをミュートする。MUTE 状態は localStorage によりリロードをまたいで保持される。
    • 
            
  • 指揮官報告には SITREP を使用する。 SITREP ボタンは、ドメイン内訳、センサーエビデンス、トレンド指標を含む構造化された状況報告書を生成する。
    • 
            
  • ベースラインの十分性を確認する。 Cloudflare の HOD Z スコアは UTC 時間帯ごとに同一時間帯サンプル ≥7 件で有効化される。初回起動時はバックグラウンドで全24 UTC 時間帯スロットをシアターあたり約7秒で補完：CF L7 hourly timeseries（時間帯別強度）と日次オリジン分布を組み合わせ、ウォームアップ期間なしで即時有効化される。エビデンスパネルに "HOD warmup N/7" が表示される場合は timeseries が取得できず、ライブポーリングで蓄積中であることを示す。RSS Narrative も同様に≥7日間のデータが必要。
    • 
            
  • VELOCITY / AMBUSH メーターを読む。 VELOCITY は脅威スコアの現在の変化率（ポーリングサイクルあたりのポイント ≈ 900秒）。正（赤↑）= アクティブに悪化中。負（緑↓）= 改善中。⚡ AMBUSH（赤点滅）= 変化率自体が加速中 — 二次微分スパイク。これは最も時間的に緊急なシグナルであり、急速に圧縮される攻撃ウィンドウを示す。
    • 
            
  • CHAIN パネルのエスカレーションナラティブを読む。 CHAIN ボタン（HUD 右上）はエビデンスチェーンタイムラインを開く。過去24時間以内のタイムスタンプ付き [NARRATIVE_BURST → ISR_SURGE → SYNC_DDOS → FIRMS_ANOMALY] エスカレーションイベントを表示。FULL CHAIN（+3 pt）は4種類のイベントタイプすべてが24時間以内に発生したことを意味 — 協調的マルチドメイン準備の強力な指標。v9 では TELEGRAM_INTENT、MASKIROVKA、C2_SYNC、INFRA_BLACKOUT もチェーンログに登録される。
    • 
            
  • GDELT トーンの解釈。 –15.0 = 活発な軍事緊張レトリックのしきい値（v9 キャリブレーション）。–18 = アクティブな危機フレーミング。–20以下 = 歴史的に運動学的行動が切迫または進行中に相当。30分間の単一ポーリングサイクル内での3〜5ポイントの急落は、同じ値への緩やかな下落より重要性が高い。
    • 
            
  • 封鎖インデックスの解釈。 インデックスは DDoS 強度とインフラ劣化の両方に連動してスケールする: Check-Host ノードへの到達可能性を維持したままの高ボリューム DDoS は10%ノイズフロアの貢献のみを生成（インデックス ≈ 1.0）。インフラ無力化（インデックス ≥ 7.0）には、DDoS サージ、RIPE BGP 撤退、そしてグローバルノードからの Check-Host BLACKOUT が同時に必要 — 2022年2月のロシア地上侵攻の30〜90分前に観察されたパターン。
    • 
            
  • SURVIVAL HUD の解釈（v9）。 グローバルノードからの重要な国家インフラ（政府、中央銀行、電力網）のリアルタイム到達可能性を表示。OK = インフラ到達可能。PARTIAL = 一部のノードが障害を報告 — DDoS 影響または局所的障害の可能性。BLACKOUT = 複数のグローバル拠点から同時に重要インフラへの到達不能。BLACKOUT + 高い封鎖インデックス = 侵攻前ブラックアウトシナリオの可能性が高い。
    • 
            
  • C2-SYNC の解釈（v9）。 複数シアターへの攻撃が60秒以内（C2 SYNC CONFIRMED）または5分以内（PARTIAL）に開始されたかどうかを表示。地理的に離れたシアター間での厳密な時間的同期は、緩やかに協調されたハクティビスト活動ではなく、国家が統合した C2（指揮統制）の特徴。
    • 
            
  • Maskirovka 検出（v9）。 物理的障害が確認され（IODA 劣化または Check-Host BLACKOUT）、すべてのナラティブチャンネルが同時に沈黙している場合（RSS バーストなし、Telegram 意図なし）、システムは潜在的な Maskirovka（ロシア軍事欺瞞ドクトリン）にフラグを立てる。Check-Host の PARTIAL 単独ではトリガーされない — ノードの局所的障害による誤検知を削減するため、BLACKOUT のみが対象。ナラティブ増幅を伴わない物理的障害は、ハクティビストキャンペーンではなく真の運動学的作戦を示す可能性がある — ハクティビストグループは通常、攻撃の前後に標的を大声で告知する。
    • 
            
  • confirm済みインテルは指数関数的に減衰（ADR-023）。 LLMインテルを confirm しても、シナリオスコアへの寄与は「24h フル強度 → 以降ゼロ」ではない。confirm 直後にフル重みで入り、exp(-age / τ)（τ=12h）で減衰する。実用値: age=12h で約37%、24h で約14%、36h で約5%、48h で完全除去。CONFIRM クリック直後に TL が急上昇することはない。 新鮮な confirm が容量上限（cap）を占有し、古いアイテムは自然にフェードアウト。キャリブレーション目的で従来の二値TTL挙動と比較したい場合は、Config 画面で INTEL_AGE_DECAY_ENABLED=false に設定。ソースタイプ別のτ上書き（例: 動きの速い外交シグナル）は INTEL_AGE_DECAY_TAU_HOURS_DIPLOMATIC=6 のように環境変数で指定。エビデンスパネルは各 confirm 済みアイテムの横に (age X.Xh, w=Y.YY) を表示し、減衰後の重みが一目で確認可能。

7. Config & Monitoring Management

        
Open the master settings modal via the Config button in the toolbar. It consists of six tabs.

        
    
            
  • Sensors: Enable or disable individual 33 sensors. A disabled sensor contributes zero to its domain score (graceful degradation). Sensor fleet: 12 original + 3 v9 (telegram_mirror, check_host, greynoise) + 1 Phase 2 (space_weather) + 3 Phase 4 (ihr, ripe_atlas, tor_metrics) + 7 CAC (notam, travel_advisory, ooni, usgs_seismic, mil_support_air, gps_jamming, ct_log) + 6 LLM Intel (hacktivist_intel, ground_osint, diplomatic, military_exercise, apt_intel, hacktivist_news) + 1 meta (convergence_tracker).
    • 
            
  • Fetch Log: Displays the last fetch result for each sensor (success / failure / cache age). Cache older than 3× the polling interval is flagged as STALE.
    • 
            
  • Upstreams (analyst+): Per-upstream-source health for sensors that aggregate multiple feeds. Currently surfaces CT Log's three sources — certstream (push, disabled by default since Calidog upstream is broken as of 2026-04-23), certspotter (pull), and crt.sh (fallback). Shows per-source last-message age, mode counters (e.g. ADR-024 untrusted-CA / wildcard-at-gov-TLD failure modes), watched-apex coverage (24h / 72h), and the 10 stalest watched apexes. Lets you answer "is the actual data feed alive?" without inferring it from sensor-level fetch logs.
    • 
            
  • Fleet Health (analyst+): Per-sensor detail view of fleet status — what the HUD's colored dots summarize, broken out per sensor. Shows health enum (OK / DEGRADED / STALE / ERROR / CIRCUIT_OPEN), circuit-breaker state (closed / half_open / open) and fail count, cache age, reliability over a selectable window (1h / 24h / 7d) — success rate, total fetches, average response time — poll interval, and last-error message. Domain filter (cyber / physical / info) narrows the list. Sensors that expose upstream_health() (currently CT Log) also show inline upstream source dots. Direct visualization of the /api/admin/sensor_health endpoint.
    • 
            
  • System (admin only): Edit config.env settings — server bind host/port, API keys, LLM/Ollama settings, intel queue thresholds, notification webhooks, cache & polling intervals, threat-scoring thresholds, DDoS acceleration parameters, JWT auth, plugin sensors. The Default Focus field sets the scenario that becomes focused on startup (defaults to taiwan_contingency).
    • 
            
  • Users: Manage operator accounts with roles admin (full access) / analyst (operational access) / viewer (read-only). Password reset via admin-initiated temporary token.
    • 
            
  • Scenarios (admin only): Create / edit / archive / restore / purge conflict scenarios. Each scenario defines its own participants (countries with role + coupling weight 0.0–1.0) and core_country (optional focus anchor). Exactly one scenario is focused at a time; all other enabled scenarios are scored in C-lite background mode (LLM intel + global signals only, no per-country sensors). See §8 for the scenario HUD and §9 for the scenario state machine.
    • 
        

        
Scope is scenario-driven, not tab-driven. The legacy Strategy / Threat Actors / Quick Pins tabs were removed when the system migrated from country-unit to scenario-unit scoring (see docs/design/scenario-refactor.md). All per-country lists — participants, adversaries, correlate targets — are now derived from the focused scenario's participants map, which is managed in the Scenarios tab.

Twenty visual components designed to engage analyst intuition and pattern-recognition (Recognition-Primed Decision) in parallel with numerical computation. Based on Naturalistic Decision Making (NDM) theory; intended for immediate situational awareness formation.

U. DDoSインテリジェンス強化 [データソースアップグレード]

V. ネットワーク到達性センサー [Phase 4] — 3つの新しいグラウンドトゥルースセンサー

  • 国家インテル: Country Intelモーダルに2つの新セクション: 「ネットワーク到達性」（IHR切断状態、RIPE Atlasプローブ数＆RTT）と「検閲/Tor」（Torリレー/ブリッジ数、ユーザー推定、検閲指標）。

H. Scenario Bar

        
    
            
  • Scenario cards appear as a horizontal strip below the HUD. Each registered scenario has a card showing its name, score, TL (for focused), and domain activity dots (C/P/I).
    • 
            
  • Focused scenario (cyan border, FOCUSED badge): receives signals from all 33 sensors — full scoring fidelity. TL1–5 threat level is computed.
    • 
            
  • Background scenarios (LITE badge): scored using LLM intel and global-only signals. TL is not computed. A BIAS tag is shown when the scenario is affected by C-lite sampling bias (ADR-008).
    • 
            
  • LITE-INS badge (in place of the TL number): shown when observable coverage is insufficient — only 0 or 1 of the 3 domains (Cyber/Physical/Information) has any data. The score exists but is not interpretable as a threat level. Treat the scenario as unobservable and switch focus if you need a real TL.
    • 
            
  • Coverage badge (background cards only): shows Coverage 33% or Coverage 66% when fewer than 2/3 domains have any signal in lite mode. Amber for 2/3 missing one domain (66%), red for ≤1/3 (33% or 0%). Hover the badge to see which domains are blind. Surfaces NP6 transparency: a low-coverage lite score is structurally biased and may understate or overstate actual risk — consider switching focus to this scenario for full sensor coverage.
    • 
            
  • TRIAGE filter & pulse: The LLM Intelligence panel opens to a TRIAGE view that ranks pending items by confidence × max_scenario_coupling × age_decay. When stale high-priority pending items accumulate (priority ≥ 0.50, age ≥ 4h by default), the LLM Intelligence menu item softly pulses amber and shows a count badge — non-disruptive and never auto-opens the panel. Tune via INTEL_PULSE_PRIORITY and INTEL_PULSE_MIN_AGE_HOURS.
    • 
            
  • Velocity trend arrow: Each card displays a directional arrow — ▲ rising (score increasing over recent observations), ▼ falling, or — stable. Velocity is computed via linear regression over the last 20 scenario_tl_observations. The velocity bonus (capped at ±1.5 pts) and acceleration bonus (0.5 max) are applied to the scenario score before TL derivation.
    • 
            
  • Pattern warning badges:
                
      
                    
    • SILENT DIV (pulsing) — Silent Divergence detected: cyber ≥ 1.0 AND physical ≥ 1.0 AND information = 0. This is a classic pre-conflict indicator — kinetic and cyber preparations are visible but media/information channels are silent, suggesting deliberate suppression. Adds +0.5 to scenario score.
      • 
                    
    • CTX ALIGN — Context Alignment: 3+ of 4 axes (temporal, spatial, target, direction) are converging, meaning signals are correlated rather than coincidental. Adds +0.5 to scenario score.
      • 
                
    
            
    • 
            
  • ETA indicator (focused only): When velocity is positive, shows estimated time to reach the next TL threshold (e.g., "ETA 2.3h"). Helps analysts anticipate escalation timing.
    • 
            
  • Click a scenario card to open the Scenario Detail Panel (below the scenario bar). Background cards also display a ◎ focus-switch button at the right edge — click it to promote that scenario to FOCUSED mode (full 33-sensor scoring). The focused card does not show this button.

  • Purpose (P4 traceability): Every rationale must be traceable back to the source evidence. The detail panel is the analyst's primary tool for verifying why a scenario score has its current value, down to the individual sensor contribution and LLM reasoning.
    • 
            
  • Switch Focus button: For background scenarios, a SWITCH FOCUS button appears in the detail panel header. Clicking it promotes this scenario to FOCUSED mode (full 33-sensor scoring). This button is not shown when viewing the already-focused scenario.
    • 
            
  • Bias warning banner: For background scenarios, an orange warning banner is shown at the top of the panel stating that the score is derived from LLM intel + global signals only, and that per-country sensor signals are not being sampled (ADR-008). Do not compare background scores directly with the focused scenario score.
    • 
            
  • Domain bars: Cyber / Physical / Information domain scores are shown as horizontal bars. The sum (capped per domain at DOMAIN_CAP=6.0) plus convergence bonus produces the scenario score.
    • 
            
  • Contribution table columns:
                
      
                    
    • Sensor — the sensor that produced the signal, with a colored tag indicating its domain.
      • 
                    
    • Country — ISO2 code of the country the signal is attributed to (or GLOBAL).
      • 
                    
    • Role — the country's role in the scenario (primary_target, forward_base, primary_ally, etc).
      • 
                    
    • Raw — raw sensor score before weighting.
      • 
                    
    • LLM w — LLM-assigned country weight (0.0–1.0), present only for LLM-analyzed signals.
      • 
                    
    • Part w — participant weight configured for the country within this scenario (0.0–1.0).
      • 
                    
    • Contrib — final contribution to domain score: raw × llm_w × part_w × global_discount.
      • 
                    
    • Evidence — clickable link to the source URL (opens in a new tab).
      • 
                    
    • What-if — toggle (focused scenarios only) to exclude this contribution from the recomputation.
      • 
                
    
            
    • 
            
  • Row expansion: Click any row to expand it and see: formula_trace (canonical calculation string — this is the authoritative explanation per P4), value_display (human-readable raw value), llm_reasoning (the LLM's stated reason for the country weighting), observed_at (UTC timestamp), and the evidence URL.
    • 
            
  • What-if recomputation (focused only): Click the what-if toggle on one or more rows to exclude those contributions. The panel header shows the recomputed domain scores, convergence bonus, total score, and derived TL (using the same rules as the server engine: TL1≥9+physical≥3, TL2≥6+active_domains≥2, TL3≥4, TL4≥2, TL5<2). Use this to sanity-check whether the score would still hold if a questionable signal were removed. Click Reset to clear all exclusions.
    • 
            
  • When to use: (a) before escalating an alert — verify formula_trace and evidence; (b) when an LLM-derived country weight looks suspicious — inspect llm_reasoning; (c) when you suspect a single noisy sensor is driving the score — use what-if to confirm.

H. シナリオバー

        
    
            
  • シナリオカードはHUD下部に水平バーとして表示されます。登録済みの各シナリオが名称、スコア、TL（フォーカス時）、ドメイン活動ドット(C/P/I)と共にカード表示されます。
    • 
            
  • フォーカスシナリオ（シアンの枠、FOCUSEDバッジ）: 全33センサーからの信号を受信し、完全なスコアリング精度でTL1–5の脅威レベルが算出されます。
    • 
            
  • バックグラウンドシナリオ（LITEバッジ）: LLMインテルとグローバル信号のみでスコアリングされます。TLは算出されません。C-liteサンプリングバイアスの影響を受けている場合はBIASタグが表示されます（ADR-008）。
    • 
            
  • LITE-INS（観測不足）バッジ（TL番号の代わりに表示）: 観測可能なカバレッジが不足している場合に表示されます — 3ドメイン（サイバー/物理/情報）のうち0〜1ドメインしかデータがない状態。スコアは存在しますが脅威レベルとしての解釈はできません。実質的に「観測不能」として扱い、TLが必要なら focus を切り替えてください。
    • 
            
  • カバレッジバッジ（バックグラウンドカードのみ）: LITE モードで 2/3 未満のドメインしか信号を持たない時に カバー 33% または カバー 66% を表示します。1ドメイン欠落（66%）は琥珀色、2ドメイン以上欠落（33% 以下）は赤。バッジにマウスを当てると欠落ドメイン名が表示されます。NP6 透明性原則: 低カバレッジの LITE スコアは構造的にバイアスがかかっており実リスクを過小/過大評価する可能性があるため、フル観測したい場合は focus 切り替えを検討してください。
    • 
            
  • TRIAGEフィルタ & パルス: LLMインテリジェンスパネルは confidence × max_scenario_coupling × age_decay でランク付けする TRIAGE ビューで開きます。高優先度の滞留審査待ち（既定: 優先度 ≥ 0.50 かつ経過 ≥ 4h）が溜まると、LLMインテリジェンスのメニュー項目が琥珀色に静かに点滅し件数バッジを表示します。非破壊的でパネルを自動展開しません。INTEL_PULSE_PRIORITY と INTEL_PULSE_MIN_AGE_HOURS で調整可能。
    • 
            
  • 速度トレンド矢印: 各カードに方向矢印が表示されます — ▲ 上昇（直近の観測でスコアが増加中）、▼ 下降、— 安定。速度は過去20回の scenario_tl_observation に対する線形回帰で算出されます。速度ボーナス（±1.5pt上限）と加速度ボーナス（0.5上限）がTL導出前にシナリオスコアに加算されます。
    • 
            
  • パターン警告バッジ:
                
      
                    
    • サイレント乖離（点滅表示）— サイレント乖離検出: サイバー ≥ 1.0 かつ 物理 ≥ 1.0 かつ 情報 = 0。典型的な開戦前兆パターン — 動的・サイバー面の準備は可視化されているが、メディア/情報チャネルは沈黙しており、意図的な抑制を示唆。スコアに+0.5加算。
      • 
                    
    • CTX ALIGN — コンテキスト整合: 4軸（時間・空間・対象・方向）中3軸以上が収斂。信号が偶然ではなく相関していることを示す。スコアに+0.5加算。
      • 
                
    
            
    • 
            
  • ETA表示（フォーカスシナリオのみ）: 速度が正の場合、次のTL閾値到達までの推定時間を表示（例: "ETA 2.3h"）。エスカレーションのタイミング予測に活用。
    • 
            
  • クリックでシナリオカードを開き、シナリオ詳細パネル（シナリオバー下部）が表示されます。バックグラウンドカードには右端に◎フォーカス切替ボタンが表示されます — クリックするとそのシナリオをFOCUSEDモード（全33センサースコアリング）に昇格します。フォーカス中のカードにはこのボタンは表示されません。
    • 
        


        
I. シナリオ詳細パネル / 根拠検証

        
    
            
  • 目的（P4: 追跡可能性）: 全ての根拠はソース証拠まで追跡可能でなければなりません。詳細パネルは、シナリオスコアが現在の値に至った理由を、個々のセンサー寄与度とLLM推論レベルまで検証するためのアナリストの主要ツールです。
    • 
            
  • フォーカス切替ボタン: バックグラウンドシナリオの場合、詳細パネルヘッダーにフォーカス切替ボタンが表示されます。クリックするとこのシナリオがFOCUSEDモード（全33センサースコアリング）に昇格します。既にフォーカス中のシナリオを閲覧中はこのボタンは表示されません。
    • 
            
  • バイアス警告バナー: バックグラウンドシナリオでは、パネル上部にオレンジ色の警告バナーが表示され、スコアはLLMインテル + グローバル信号のみから導出されており、国別センサー信号はサンプリングされていないこと（ADR-008）を明示します。バックグラウンドスコアをフォーカスシナリオのスコアと直接比較しないでください。
    • 
            
  • ドメインバー: Cyber / Physical / Information の各ドメインスコアが水平バーで表示されます。合計（ドメインごとに DOMAIN_CAP=6.0 でキャップ）+ 収斂ボーナスがシナリオスコアとなります。
    • 
            
  • 寄与度テーブル列:
                
      
                    
    • Sensor — 信号を発生させたセンサー。ドメインを示すカラータグ付き。
      • 
                    
    • Country — 信号が帰属する国のISO2コード（または GLOBAL）。
      • 
                    
    • Role — シナリオにおけるその国の役割（primary_target, forward_base, primary_ally 等）。
      • 
                    
    • Raw — 重み付け前の生センサースコア。
      • 
                    
    • LLM w — LLMが割り当てた国重み（0.0–1.0）。LLM解析済み信号のみに付与されます。
      • 
                    
    • Part w — このシナリオ内でその国に設定された参加者重み（0.0–1.0）。
      • 
                    
    • Contrib — ドメインスコアへの最終寄与: raw × llm_w × part_w × global_discount。
      • 
                    
    • Evidence — ソースURLへのクリック可能リンク（新しいタブで開きます）。
      • 
                    
    • What-if — 再計算からこの寄与を除外するトグル（フォーカスシナリオのみ）。
      • 
                
    
            
    • 
            
  • 行展開: 任意の行をクリックすると展開され、以下が表示されます: formula_trace（正準的な計算式文字列 — P4 に基づく唯一の権威ある説明）、value_display（人間可読の生値）、llm_reasoning（LLMが国重み付けの理由として提示したもの）、observed_at（UTCタイムスタンプ）、および証拠URL。
    • 
            
  • What-if 再計算（フォーカス時のみ）: 1つ以上の行でWhat-ifトグルをクリックすると、それらの寄与が除外されます。パネルヘッダには再計算されたドメインスコア、収斂ボーナス、合計スコア、導出TLが表示されます（サーバーエンジンと同じルール: TL1≥9+physical≥3, TL2≥6+active_domains≥2, TL3≥4, TL4≥2, TL5<2）。疑わしい信号を除去してもスコアが維持されるかのサニティチェックに使用します。Reset で全除外をクリア。
    • 
            
  • 使用タイミング: (a) アラートをエスカレーションする前 — formula_trace と証拠を検証する; (b) LLM導出の国重みが疑わしい場合 — llm_reasoning を確認する; (c) 単一のノイジーなセンサーがスコアを牽引している疑いがある場合 — What-if で確認する。

    • 
        

        
LLMインテル経時減衰フィールド [ADR-023]

        
    
            
  • rationale_matrix[].score — スコアリングに使用される実効（減衰済み）寄与値: score_raw × age_weight。
    • 
            
  • rationale_matrix[].score_raw — 経時減衰適用前の生スコア。アナリストが元のLLM評価強度を監査できるよう保持。
    • 
            
  • rationale_matrix[].age_hours — confirm済みインテルの経過時間（時間単位）。confirmed_at（自動confirmの場合は初回検出時刻）からの経過。
    • 
            
  • rationale_matrix[].age_weight — 適用された減衰係数: exp(-age_sec / (τ · 3600))。age=τ（既定 12h）で重み=1/e≈0.37、2·τで≈0.14、3·τで≈0.05。
    • 
            
  • rationale_matrix[].detail — 減衰が有効な場合、(age X.Xh, w=Y.YY) の接尾辞が付与され、エビデンスパネルで減衰後の寄与値が一目で確認可能。
    • 
        

        
これらのフィールドは INTEL_AGE_DECAY_ENABLED=true（既定）の場合のみ出力。false にすると二値TTL挙動に戻す（回帰試験用）。ソースタイプ別にτを上書きする場合は環境変数 INTEL_AGE_DECAY_TAU_HOURS_<SOURCE_TYPE> を使用（例: INTEL_AGE_DECAY_TAU_HOURS_DIPLOMATIC=6）。

        

        

        

        

        
10. Administration & Extended Features

        
Features added for production deployment: user authentication, alert notifications, plugin sensors, and historical analysis.


        
A. User Management — TOOLS ▾ → User Management

        
    
            
  • Authentication: JWT-based login with access tokens (default: 1h expiry) and refresh tokens (24h). On first startup, a default admin user is created with the password set in DEFAULT_ADMIN_PASSWORD (default: "admin"). Change this immediately in production.
    • 
            
  • Roles: Three roles control access — admin (full access, user management), analyst (operational access), viewer (read-only). Only admins can add/delete users and change roles.
    • 
            
  • User Management Panel: Login with admin credentials → view all users with role/created/last-login. Inline role selector for instant role changes. PW button to reset passwords. DEL button to delete users (with confirmation). Self-deletion and self-role-change are blocked for safety.
    • 
            
  • Per-User Settings: Each user stores their own theater configuration (core, pins, correlates, adversaries, muted sensors, language) via PUT /api/auth/settings.
    • 
        


        
B. Alert Notifications

        
    
            
  • Channels: Slack (Incoming Webhook), Microsoft Teams (MessageCard), and generic HTTP POST webhook. Configure URLs in Config → Advanced Settings → Alert Notifications.
    • 
            
  • Events: Threat Level changes (escalation/de-escalation), Ambush pattern detection, Sequence chain completion (FULL_CHAIN/PARTIAL), and persistent sensor failure.
    • 
            
  • Debounce: Same-type alerts are suppressed for NOTIFY_DEBOUNCE_SEC seconds (default: 300) to prevent notification storms.
    • 
            
  • Safety: All dispatches run in background daemon threads. Set NOTIFY_ENABLED=false to disable all notifications globally.
    • 
        


        
C. Plugin Sensors

        
    
            
  • Dynamic Loading: Place a Python file containing a BaseSensor subclass in the plugins/ directory. The plugin loader automatically discovers, imports, and registers it at startup.
    • 
            
  • Configuration: PLUGIN_DIR (directory path), PLUGIN_ENABLED (* for all, or comma-separated filenames), PLUGIN_DISABLED (explicit exclusion list).
    • 
            
  • Duplicate Protection: If a plugin sensor name conflicts with a built-in sensor, the plugin is skipped with a warning.
    • 
        


        
D. History Analysis — TOOLS ▾ → History Analysis

        
    
            
  • Theater Selector: Dynamically populated from all configured theaters (pins + correlates + core) and any theaters with recorded data. Fetched via /api/history/theaters.
    • 
            
  • Time Range: 24h / 3 days / 7 days / 14 days / 28 days. Data is retained up to 28 days (8064 data points at 5-minute intervals).
    • 
            
  • Threat Score Trend: Canvas line chart with a fixed Y-axis (0–25) and severity zone backgrounds: Normal (0–2, green), Elevated (2–5), Warning (5–10, amber), Severe (10–18, orange), Critical (18–25, red). This fixed scale ensures that a score of 7 is always visually contextualized as "Warning zone" regardless of the current data range.
    • 
            
  • Hour-of-Day Baseline: Bar chart of CF Spike averages by hour (0–23), colored by intensity. Useful for identifying temporal attack patterns.
    • 
            
  • Sequence Events: Escalation chain events grouped by date with type summary badges (e.g., BURST×3 SURGE×1). Event types: NARRATIVE_BURST, ISR_SURGE, SYNC_DDOS, FIRMS_ANOMALY, AIS_DARK_GAP, etc.
    • 
            
  • Recent Alerts: Displays threat level transitions instead of raw alert entries. Each row shows: time → TL badge → duration at that level → peak score. Consecutive same-TL alerts are collapsed into a single transition entry, making it easy to see how long each threat level persisted. Grouped by date.
    • 
            
  • Export: Download all historical data as JSON via the Export button or GET /api/history/export?theater=TW (admin only).
    • 
        


        
E. Database Backend (SQLite)

        
    
            
  • All persistent state is stored in SQLite with WAL mode for concurrent read/write performance. The database file is at persistence/radar.db.
    • 
            
  • On first startup after migration, existing state.json data is automatically migrated to SQLite and the JSON file is renamed to state.json.migrated as backup.
    • 
            
  • Per-sensor caches remain in memory for performance; all other state (baselines, HOD data, sequence events, alerts, threat levels) is persisted to SQLite.
    • 
        


        
F. Sensor Health & Rate Limiting

        
    
            
  • Health States: Each sensor reports one of 5 states: OK (green), STALE (orange — no fresh data for 3× poll interval), ERROR (red — last fetch failed), INITIALIZING (grey — no data fetched yet), DISABLED (grey — manually muted). The HUD SENSORS indicator shows a dot per sensor colored by state.
    • 
            
  • Error Propagation: When a sensor fetch fails (HTTP error, timeout, etc.), the error is immediately reflected in the health state. Any failed log_fetch() call automatically sets the sensor to ERROR, even when no specific error message is provided. Successful fetches clear the error state.
    • 
            
  • OpenSky Rate Limiting: Three sensors (OpenSky airspace, ISR Hotspot, Military Support Air) share the OpenSky Network API. A shared rate limiter enforces minimum 10-second intervals between API calls. At startup, sensors are staggered (0s, +120s, +240s) to prevent 429 rate-limit cascades. If a 429 response is received, the sensor waits for the Retry-After period before retrying once.
    • 
            
  • Cache-on-Success: Sensors only update their cache when at least one successful response is received. On complete failure, the previous cached data is returned to prevent data loss during transient outages.
    • 
        


        
G. Scenario Manager — Config → Scenarios tab (Admin only)

        
    
            
  • Scenario Architecture: DDoS-Radar scores threats per scenario (e.g., "Taiwan Contingency"), not per country. Each scenario defines participants (countries) with coupling weights (0.0–1.0) and roles (primary_target, adversary, primary_ally, etc.).
    • 
            
  • 3-Layer Design: Layer 1 = presets from geo_data.json (read-only). Layer 2 = admin customizations stored in SQLite (overrides presets). Layer 3 = session overrides (see H).
    • 
            
  • Create: New custom scenarios with unique ID (lowercase, 3–30 chars), bilingual names, core country, and participant table.
    • 
            
  • Edit: Modify names, descriptions, core country, and participant weights/roles. Changes are written to Layer 2 (DB), preserving the original preset.
    • 
            
  • State Management: Active → Paused → Archived lifecycle. Only active+enabled scenarios are scored. Paused scenarios retain data but don't contribute to scores.
    • 
            
  • Reset: For preset-based scenarios, removes all Layer 2 overrides and reverts to geo_data.json defaults.
    • 
            
  • Purge: Permanently deletes a custom (DB-only) scenario and all associated data. Requires confirmation dialog.
    • 
            
  • Change Log: All modifications are recorded in scenario_change_log with timestamps and diff.
    • 
        


        
H. Layer 3 Session Overlay — Scenario detail panel → "Weights" button (Analyst & Admin only)

        
    
            
  • Purpose: Stateless, session-only participant weight overrides for hypothesis testing. Lets analysts ask "what if Japan's coupling to this scenario were 0.8 instead of 0.5?" without touching Layer 2 (DB) or Layer 1 (geo_data.json).
    • 
            
  • Scope: Applies only to the currently focused scenario. Background scenarios always use their stored (Layer 1 + Layer 2) weights.
    • 
            
  • Persistence: Stored in sessionStorage — cleared when the browser tab closes. Deliberately non-persistent per ADR-003 to prevent accidental long-term biasing of the scoring model.
    • 
            
  • Transport: The UI sends the overlay to the backend as JSON in the X-Scenario-Overlay HTTP header on /api/threat_data requests. The backend validates role and weight range, then applies it through apply_session_overlay() before scoring.
    • 
            
  • Validation: Values outside [0.0, 1.0] are silently dropped. Unknown country codes are ignored. Viewers cannot apply overlays (the header is discarded server-side).
    • 
            
  • UI Cues: The overlay section shows an ACTIVE badge when any override is in effect, and each modified row has an amber border. The baseline weight is displayed in parentheses next to the slider for comparison.
    • 
        


        
I. C-lite Evaluation — Config → Scenarios tab → "Load C-lite Evaluation" button

        
    
            
  • Purpose: Determines whether the current C-lite mode (focused scenario = full sensors, background = LLM + global only) is adequate, or whether upgrading to C-medium (background scenarios also receive per-country sensor data at reduced frequency) should be considered.
    • 
            
  • Data Source: Aggregates focus_switch_log entries over a configurable window (default 28 days). Each focus switch records old/new scenario IDs, TL at switch time, and score delta.
    • 
            
  • Key Metrics:
                
      
                    
    • Switches: Total focus switches in the evaluation period.
      • 
                    
    • Misses: Switches where the background scenario's score had risen significantly (delta > threshold) before the analyst noticed and switched — indicating a missed escalation while the scenario was in LITE mode.
      • 
                    
    • Miss Rate: misses / switches. The primary decision metric.
      • 
                    
    • Avg Delta: Average score delta at time of switch. Higher values indicate larger blind spots in LITE mode.
      • 
                    
    • Max Delta: Worst-case score delta observed.
      • 
                
    
            
    • 
            
  • Recommendation:
                
      
                    
    • LITE_SUFFICIENT — Miss rate ≤ 15%. Background scenarios are adequately covered by LLM + global signals.
      • 
                    
    • CONSIDER_C_MEDIUM — Miss rate > 15%. Background scenarios have significant blind spots; consider upgrading to C-medium for more comprehensive coverage.
      • 
                    
    • INSUFFICIENT_DATA — Fewer than 3 focus switches recorded. Cannot draw conclusions yet.
      • 
                
    
            
    • 
            
  • Per-Scenario Breakdown: Table showing switches, misses, and avg_delta for each scenario that was the target of a focus switch. Identifies which specific scenarios are most affected by LITE mode limitations.
    •

A. ユーザー管理 — TOOLS ▾ → User Management

        
    
            
  • 認証: JWT ベースのログイン。アクセストークン（デフォルト: 1時間有効）とリフレッシュトークン（24時間）を使用。初回起動時に DEFAULT_ADMIN_PASSWORD（デフォルト: "admin"）で admin ユーザーが自動作成される。本番環境では即時変更すること。

B. アラート通知

        
    
            
  • チャネル: Slack（Incoming Webhook）、Microsoft Teams（MessageCard）、汎用 HTTP POST Webhook。URL は Config → 詳細設定 → アラート通知で設定。
    • 
            
  • イベント: 脅威レベル変化（エスカレーション/デエスカレーション）、アンブッシュパターン検出、シーケンスチェーン完了（FULL_CHAIN/PARTIAL）、センサーの持続的障害。
    • 
            
  • デバウンス: 同一タイプのアラートは NOTIFY_DEBOUNCE_SEC 秒間（デフォルト: 300）抑制され、通知の嵐を防止。

  • 安全性: すべてのディスパッチはバックグラウンドのデーモンスレッドで実行。NOTIFY_ENABLED=false で全通知をグローバルに無効化可能。
    • 
        


        
C. プラグインセンサー

        
    
            
  • 動的ロード: BaseSensor サブクラスを含む Python ファイルを plugins/ ディレクトリに配置。プラグインローダーが起動時に自動的に検出、インポート、登録。
    • 
            
  • 設定: PLUGIN_DIR（ディレクトリパス）、PLUGIN_ENABLED（* で全プラグイン、またはカンマ区切りのファイル名）、PLUGIN_DISABLED（明示的除外リスト）。

  • 重複保護: プラグインセンサー名が組み込みセンサーと競合する場合、警告とともにスキップ。
    • 
        


        
D. 履歴分析 — TOOLS ▾ → History Analysis

        
    
            
  • シアターセレクター: 設定済みの全シアター（ピン + 相関国 + コア）およびデータ記録のあるシアターから動的に生成。/api/history/theaters から取得。
    • 
            
  • 時間範囲: 24時間 / 3日間 / 7日間 / 14日間 / 28日間。データは最大28日間保持（5分間隔で8064データポイント）。
    • 
            
  • 脅威スコア推移: 固定Y軸（0〜25）と重要度ゾーン背景色を持つ Canvas 折れ線グラフ: 正常（0〜2, 緑）、警戒（2〜5）、警告（5〜10, 琥珀）、深刻（10〜18, オレンジ）、危機的（18〜25, 赤）。この固定スケールにより、例えばスコア7は現在のデータ範囲に関係なく常に「警告ゾーン」として視覚的に文脈化される。
    • 
            
  • 時間帯別ベースライン: CF スパイク平均を時間帯（0〜23時）ごとに棒グラフで表示、強度で色分け。時間的な攻撃パターンの特定に有用。
    • 
            
  • シーケンスイベント: 日付別にグループ化されたエスカレーションチェーンイベント。タイプ別サマリーバッジ付き（例: BURST×3 SURGE×1）。イベントタイプ: NARRATIVE_BURST、ISR_SURGE、SYNC_DDOS、FIRMS_ANOMALY、AIS_DARK_GAP 等。
    • 
            
  • 最近のアラート: 生のアラートエントリではなく、脅威レベルの遷移を表示。各行: 時刻 → TLバッジ → そのレベルでの滞在時間 → ピークスコア。連続する同一TLアラートは1つの遷移エントリに圧縮され、各脅威レベルの持続時間が一目で把握可能。日付別グループ化。
    • 
            
  • エクスポート: Export ボタンまたは GET /api/history/export?theater=TW で全履歴データを JSON としてダウンロード（admin のみ）。
    • 
        


        
E. データベースバックエンド（SQLite）

        
    
            
  • すべての永続状態は WAL モードの SQLite に保存され、並行読み書き性能を確保。データベースファイルは persistence/radar.db に配置。
    • 
            
  • マイグレーション後の初回起動時に、既存の state.json データが自動的に SQLite にマイグレーションされ、JSON ファイルはバックアップとして state.json.migrated にリネーム。
    • 
            
  • センサーごとのキャッシュはパフォーマンスのためメモリに保持。その他すべての状態（ベースライン、HOD データ、シーケンスイベント、アラート、脅威レベル）は SQLite に永続化。
    • 
        


        
F. センサーヘルス & レート制限

        
    
            
  • ヘルス状態: 各センサーは5つの状態のいずれかを報告: OK（緑）、STALE（橙 — ポーリング間隔の3倍以上データ更新なし）、ERROR（赤 — 最終フェッチ失敗）、INITIALIZING（灰 — 初回データ未取得）、DISABLED（灰 — 手動ミュート中）。HUD の SENSORS インジケーターはセンサーごとに状態色のドットを表示。
    • 
            
  • エラー伝搬: センサーフェッチが失敗した場合（HTTP エラー、タイムアウト等）、エラーは即座にヘルス状態に反映。log_fetch() の失敗呼び出しは、特定のエラーメッセージがなくても自動的にセンサーを ERROR に設定。成功したフェッチはエラー状態をクリア。
    • 
            
  • OpenSky レート制限: 3つのセンサー（OpenSky 空域、ISR ホットスポット、軍事支援航空機）は OpenSky Network API を共有。共有レートリミッターが API コール間に最低10秒の間隔を強制。起動時にセンサーは段階的に起動（0秒、+120秒、+240秒）し、429 レート制限の連鎖を防止。429 レスポンスを受信した場合、Retry-After 期間待機後に1回リトライ。
    • 
            
  • 成功時のみキャッシュ: センサーは少なくとも1つの成功レスポンスを受信した場合のみキャッシュを更新。完全な失敗時は前回のキャッシュデータを返し、一時的な障害中のデータ損失を防止。
    • 
        


        
G. シナリオマネージャー — Config → Scenarios タブ（Admin のみ）

        
    
            
  • シナリオアーキテクチャ: DDoS-Radar は国単位ではなくシナリオ単位（例: 「台湾有事」）で脅威をスコアリング。各シナリオは参加国（participants）をカップリングウェイト（0.0–1.0）とロール（primary_target、adversary、primary_ally 等）で定義。
    • 
            
  • 3層設計: Layer 1 = geo_data.json のプリセット（読み取り専用）。Layer 2 = SQLite に保存された管理者カスタマイズ（プリセットを上書き）。Layer 3 = セッションオーバーライド（下記 H 参照）。
    • 
            
  • 作成: 一意の ID（小文字、3–30文字）、日英バイリンガル名、コア国、参加国テーブルを指定してカスタムシナリオを新規作成。
    • 
            
  • 編集: 名前、説明、コア国、参加国のウェイト/ロールを変更可能。変更は Layer 2（DB）に書き込まれ、元のプリセットは保持。
    • 
            
  • 状態管理: Active → Paused → Archived のライフサイクル。スコアリング対象は active かつ enabled のシナリオのみ。Paused シナリオはデータを保持するがスコアに寄与しない。
    • 
            
  • リセット: プリセットベースのシナリオについて、Layer 2 のすべてのオーバーライドを削除し、geo_data.json のデフォルトに復帰。
    • 
            
  • パージ: カスタム（DB のみ）シナリオと関連データを完全削除。確認ダイアログが必要。
    • 
            
  • 変更ログ: すべての変更は scenario_change_log にタイムスタンプと差分とともに記録。
    • 
        


        
H. Layer 3 セッションオーバーライド — シナリオ詳細パネル → 「重み調整」ボタン（Analyst および Admin のみ）

        
    
            
  • 目的: 仮説検証用のセッション限定な参加国重み上書き。「もし日本のカップリングが 0.5 ではなく 0.8 だったら？」という問いを、Layer 2（DB）や Layer 1（geo_data.json）に触れずに試せる。
    • 
            
  • スコープ: 現在フォーカス中のシナリオのみに適用。バックグラウンドシナリオは常に保存済みの（Layer 1 + Layer 2）重みを使用。
    • 
            
  • 永続化: sessionStorage に保存 — タブを閉じるとクリア。ADR-003 に従い、スコアリングモデルの意図しない長期的バイアスを防ぐため意図的に非永続化されている。
    • 
            
  • 通信: UI は /api/threat_data リクエストの X-Scenario-Overlay HTTP ヘッダに JSON でオーバーレイを送信。バックエンドはロールと重み範囲を検証後、apply_session_overlay() 経由でスコアリング前に適用する。
    • 
            
  • バリデーション: [0.0, 1.0] の範囲外の値は黙って破棄。未知の国コードは無視。Viewer はオーバーレイを適用できない（ヘッダはサーバ側で破棄される）。
    • 
            
  • UI 表示: オーバーレイが有効なときはセクションに 適用中 バッジが表示され、変更された行にはアンバーのボーダーがつく。スライダーの横に基準値（括弧内）が表示され、比較しやすい。
    • 
        


        
I. C-lite 評価 — Config → Scenarios タブ → 「C-lite評価を読み込む」ボタン

        
    
            
  • 目的: 現在の C-lite モード（フォーカスシナリオ＝全センサー、バックグラウンド＝LLM + グローバルのみ）が適切か、C-medium（バックグラウンドシナリオも低頻度で国別センサーデータを受信）へのアップグレードを検討すべきかを判定。
    • 
            
  • データソース: 設定可能な期間（デフォルト28日間）の focus_switch_log エントリを集約。各フォーカス切替は旧/新シナリオID、切替時のTL、スコアデルタを記録。
    • 
            
  • 主要メトリクス:
                
      
                    
    • 切替回数: 評価期間中の総フォーカス切替回数。
      • 
                    
    • ミス: バックグラウンドシナリオのスコアがアナリストが気づいて切り替える前に大幅に上昇していた（デルタ＞閾値）切替 — LITE モードでのエスカレーション見逃しを示す。
      • 
                    
    • ミス率: ミス / 切替回数。主要な判断指標。
      • 
                    
    • 平均Δ: 切替時の平均スコアデルタ。高い値はLITEモードのブラインドスポットが大きいことを示す。
      • 
                    
    • 最大Δ: 観測された最悪ケースのスコアデルタ。
      • 
                
    
            
    • 
            
  • 推奨:
                
      
                    
    • LITE_SUFFICIENT — ミス率 ≤ 15%。バックグラウンドシナリオはLLM + グローバル信号で十分にカバー。
      • 
                    
    • CONSIDER_C_MEDIUM — ミス率 > 15%。バックグラウンドシナリオに重大なブラインドスポットあり。より包括的なカバレッジのためC-mediumへのアップグレードを検討。
      • 
                    
    • INSUFFICIENT_DATA — フォーカス切替記録が3回未満。結論を出すにはデータ不足。
      • 
                
    
            
    • 
            
  • シナリオ別内訳: フォーカス切替の対象となった各シナリオの切替回数、ミス、平均Δを表示するテーブル。LITEモードの制約により最も影響を受けているシナリオを特定。

11. System Limitations & Monitoring Directionality


        
This chapter is required reading for all operators. Understanding the system's inherent limitations is critical to avoiding over-reliance on automated assessments and maintaining human-in-the-loop (HITL) judgment.


        
11.1 Sensor Coverage Gaps

        
    
            
  • English-language bias: GDELT and RSS narrative sensors primarily index English-language media. Mandarin, Russian, Farsi, and Korean-language sources are under-represented. The system applies median-delta subtraction to mitigate global English-media trends, but local-language narratives may be missed entirely.
    • 
            
  • Western advisory bias: Travel advisory data comes from US, UK, and Canada — all Western Five Eyes nations. These governments may issue advisories based on shared intelligence or political alignment rather than independent assessment. Convergence detection mitigates but does not eliminate this.
    • 
            
  • ADS-B coverage: ISR and military support air monitoring depends on ADS-B transponder data. Military aircraft frequently operate with transponders off (EMCON). Detection of ISR sorties via ADS-B represents a lower bound — absence of ADS-B tracks does NOT mean absence of ISR activity.
    • 
            
  • AIS dark gaps: Maritime monitoring relies on AIS transponder signals. State actors deliberately disable AIS during sensitive operations. Detection of "dark gaps" is itself the signal, but requires prior AIS history.
    • 
            
  • Telegram coverage: Telegram monitoring uses public web previews (t.me/s/). Only channels with public web preview enabled are visible — private or restricted channels cannot be monitored. Coverage is supplemented by security news RSS feeds that report on hacktivist campaigns.
    • 
        


        
11.2 Baseline & Cold-Start Limitations

        
    
            
  • Cold-start period: Z-score based detection (Cloudflare HOD, BGP, CT Log, shipping, narrative) requires historical baselines. During the first 4–7 days of operation, anomaly detection sensitivity is reduced and severity is capped at level 1 (WATCH). The baseline_maturity indicator in the HUD shows current baseline completeness.
    • 
            
  • Seasonal/cyclical blindness: Shipping route analysis uses weekday+time-bucket baselines (14-day window). Annual patterns (holidays, monsoon seasons, political cycles) may still cause false positives.
    • 
            
  • Forex USD-factor noise: The system subtracts median z-score across all monitored currencies to filter global USD movements. This works for gradual Fed policy shifts but may over-correct during genuine crisis-driven capital flight if the flight is globally correlated.
    • 
        


        
11.3 Directionality & Attribution

        
    
            
  • Correlation ≠ causation: Multi-domain convergence scoring identifies statistical co-occurrence of signals across cyber, physical, and info domains. It cannot determine intent, command relationships, or causal chains. A high convergence score means "multiple indicators are active simultaneously" — not "an attack is imminent."
    • 
            
  • Attribution limitations: The system maps threat actors to theaters using THREAT_ACTOR_MAPPING (Telegram channels, ASN ownership, APT tags). These mappings are heuristic and may be incorrect due to false-flag operations, shared infrastructure, or proxy actors.
    • 
            
  • Monitoring directionality: This system is designed to detect precursors to attacks on monitored theaters. It is NOT designed to detect friendly-force offensive operations, defensive preparations by adversaries, or internal civil unrest. Signals are interpreted through the lens of "is this theater about to be attacked?" which introduces confirmation bias when applied to ambiguous situations.
    • 
            
  • Ambush pattern caveat: The 2nd-derivative acceleration detector ("ambush pattern") identifies sudden changes in the rate of change. This can trigger on legitimate events (e.g., a scheduled military exercise suddenly ramping up) as well as genuine surprise attacks.
    • 
        


        
11.4 Signal Deduplication & Double-Counting

        
    
            
  • BGP signal grouping: IODA, RIPE BGP, and IHR disconnection sensors all measure BGP routing anomalies. The engine groups these by signal_source="bgp" and takes max() instead of sum to prevent triple-counting the same physical event.
    • 
            
  • Remaining overlaps: Certificate Transparency anomalies (untrusted CA issuance, gov-TLD wildcards) may correlate with BGP hijacking events (DNS+BGP attacks often co-occur). These are NOT currently deduplicated because the underlying phenomena are distinct even if tactically coordinated.
    • 
        


        
11.5 Operator Responsibilities

        
    
            
  • HITL override is mandatory: All automated assessments must be validated by a human analyst before action is taken. The MUTE function exists specifically for this purpose.
    • 
            
  • Domain weight bias: Default weights (cyber=0.50, physical=0.30, info=0.20) reflect a cyber-first monitoring posture. Operators should adjust DOMAIN_WEIGHT_* variables based on the operational context (e.g., increase physical weight during kinetic conflict).
    • 
            
  • Threat level interpretation: Severity levels (NORMAL→WATCH→ELEVATED→CRITICAL) are relative to baseline, NOT absolute assessments of danger. A "CRITICAL" rating means "significantly above historical normal" — it does not inherently mean an attack is imminent.
    • 
        

        


        

        
11. システムの限界と監視方向性


        
本章はすべてのオペレーターの必読事項です。自動評価への過度な依存を避け、HITL（Human-in-the-Loop）判断を維持するため、システムの固有の限界を理解することが不可欠です。


        
11.1 センサーカバレッジのギャップ

        
    
            
  • 英語バイアス：GDELTおよびRSSナラティブセンサーは主に英語メディアをインデックスしています。中国語、ロシア語、ペルシャ語、韓国語のソースは過小表現されています。システムはグローバルな英語メディアトレンドを緩和するためにmedian-delta減算を適用していますが、現地語のナラティブは完全に見逃される可能性があります。
    • 
            
  • 西側諸国アドバイザリーバイアス：渡航勧告データは米国、英国、カナダ（すべてファイブアイズ加盟国）から取得。これらの政府は独立した評価ではなく、共有情報や政治的同盟に基づいて勧告を発行する場合があります。収束検出により緩和されますが、完全には排除されません。
    • 
            
  • ADS-Bカバレッジ：ISRおよび軍事支援航空機の監視はADS-Bトランスポンダデータに依存します。軍用機はEMCON（電波管制）時にトランスポンダをオフにすることが多く、ADS-BによるISRソーティの検出は下限値を示します。ADS-Bトラックの不在はISR活動の不在を意味しません。
    • 
            
  • AISダークギャップ：海上監視はAISトランスポンダ信号に依存します。国家行為者は機密作戦中にAISを意図的に無効化します。「ダークギャップ」の検出自体がシグナルですが、事前のAIS履歴が必要です。
    • 
            
  • Telegramカバレッジ：Telegram監視は公開Webプレビュー（t.me/s/）を使用します。Webプレビューが有効な公開チャネルのみが対象で、非公開・制限付きチャネルは監視できません。セキュリティニュースRSSフィードによるハクティビストキャンペー���報道で補完しています。
    • 
        


        
11.2 ベースラインとコールドスタートの制限

        
    
            
  • コールドスタート期間：Zスコアベースの検出（Cloudflare HOD、BGP、CT Log、海運、ナラティブ）には履歴ベースラインが必要です。運用開始から最初の4〜7日間は異常検出感度が低下し、重大度はレベル1（WATCH）に制限されます。HUDのbaseline_maturityインジケーターが現在のベースライン完成度を表示します。
    • 
            
  • 季節/周期的盲点：海運ルート分析は曜日+時間バケットベースライン（14日間ウィンドウ）を使用します。年間パターン（祝日、モンスーン季節、政治サイクル）は依然として偽陽性を引き起こす可能性があります。
    • 
            
  • 為替USDファクターノイズ：システムは全監視通貨のZスコア中央値を減算してグローバルなUSD変動をフィルタリングします。これは緩やかなFRB政策変更には有効ですが、危機に起因する資本逃避がグローバルに相関している場合は過剰補正する可能性があります。
    • 
        


        
11.3 方向性と帰属

        
    
            
  • 相関 ≠ 因果関係：マルチドメイン収束スコアリングは、サイバー・物理・情報ドメイン間のシグナルの統計的共起を識別します。意図、指揮関係、因果連鎖を判定することはできません。高い収束スコアは「複数の指標が同時にアクティブである」ことを意味し、「攻撃が差し迫っている」ことを意味しません。
    • 
            
  • 帰属の限界：システムはTHREAT_ACTOR_MAPPING（Telegramチャネル、ASN所有権、APTタグ）を使用して脅威アクターをシアターにマッピングします。これらのマッピングはヒューリスティックであり、偽旗作戦、共有インフラ、プロキシアクターにより不正確な場合があります。
    • 
            
  • 監視方向性：本システムは監視対象シアターに対する攻撃の前兆を検出するように設計されています。味方の攻撃作戦、敵対者の防衛準備、または国内の市民不安の検出を目的としていません。シグナルは「このシアターが攻撃されようとしているか？」というレンズを通じて解釈されるため、曖昧な状況に適用すると確認バイアスが生じます。
    • 
            
  • 待ち伏せパターンの注意：二次微分加速度検出器（「待ち伏せパターン」）は変化率の急激な変化を識別します。これは正当なイベント（例：予定された軍事演習の突然のランプアップ）と本物の奇襲攻撃の両方でトリガーされる可能性があります。
    • 
        


        
11.4 信号重複排除と二重カウント

        
    
            
  • BGP信号グルーピング：IODA、RIPE BGP、IHR切断センサーはすべてBGPルーティング異常を測定します。エンジンはこれらをsignal_source="bgp"でグループ化し、同一の物理イベントの三重カウントを防ぐためにsum()ではなくmax()を取ります。
    • 
            
  • 残存する重複：証明書透過性のサージはBGPハイジャックイベントと相関する場合があります（DNS+BGP攻撃は共起することが多い）。基盤となる現象が異なるため、現時点ではこれらは重複排除されていません。
    • 
        


        
11.5 オペレーターの責任

        
    
            
  • HITLオーバーライドは必須：すべての自動評価は、アクションを取る前に人間のアナリストによって検証されなければなりません。MUTE機能はまさにこの目的のために存在します。
    • 
            
  • ドメイン重みバイアス：デフォルトの重み（cyber=0.50、physical=0.30、info=0.20）はサイバーファーストの監視姿勢を反映しています。オペレーターは運用コンテキストに基づいてDOMAIN_WEIGHT_*変数を調整する必要があります（例：動的紛争中はphysical重みを増加）。
    • 
            
  • 脅威レベルの解釈：重大度レベル（NORMAL→WATCH→ELEVATED→CRITICAL）はベースラインに対する相対値であり、危険の絶対的評価ではありません。「CRITICAL」レーティングは「過去の正常値を大幅に上回っている」ことを意味し、攻撃が差し迫っていることを本質的に意味するものではありません。
    • 
        

        

        


        

        

        
12. Analyst Tradecraft


        
The Analyst Tradecraft panel (TOOLS → TRADECRAFT → Analyst Tradecraft) bundles 10 structured-analytic-technique (SAT) surfaces that supplement the automated scoring with deliberate cognitive checks. The panel is scoped to the current focused scenario — switching the focused scenario refreshes the active tab.


        
Why this exists. The convergence engine is good at fusing signals; it is bad at telling you when its own picture is wrong. These tabs deliberately surface the failure modes of the upstream pipeline: hidden negative evidence, single-source dominance, plausible alternative hypotheses, and analyst assumptions that quietly become load-bearing.


        
12.1 Three failure modes the panel is designed to catch

        
    
            
  • False positive (FP) — convergence fires on coincidental signals. Tabs: Hidden Signals, Coverage Gaps, Disconfirming.
    • 
            
  • False negative (FN) — real escalation is missed because filters/floors discarded it. Tabs: Hidden Signals (noise/discard log), Coverage Gaps (broken sensors).
    • 
            
  • Cognitive bias — anchoring on the first plausible story. Tabs: Compare, ACH Matrix, Dissent, Assumptions, Pre-Mortem.
    • 
        


        
12.2 Tab reference

        

        
TabPurposeUse when…

        
        
Hidden SignalsLists items the pipeline filtered out (mute, noise exclusion, confidence floor, dedup).Scenario looks oddly quiet, or you suspect the floor is too high.

        
Coverage GapsPer-scenario sensor coverage (active / muted / circuit-broken / disabled).Before drawing a conclusion — confirms which sensors actually contributed.

        
DisconfirmingSurfaces evidence that contradicts the current scenario thesis (de-escalation cues, contrary diplomatic signals).Always before raising TL conclusions — counters confirmation bias.

        
CompareSide-by-side scenario comparison (TL, top contributors, recent rationale).Same signal could fit multiple scenarios — pick the better-fit one.

12.3 When to use which technique

        
    
            
  • Routine watch → Coverage Gaps + Disconfirming. Cheap habit checks before signing off on a TL.
    • 
            
  • Anomaly spike → Hidden Signals (was it really an anomaly, or did the floor change?) + Compare (does another scenario fit better?).
    • 
            
  • High-stakes call (TL≤2, public assessment) → ACH Matrix + Pre-Mortem + Assumptions lock. The three-step CIA Tradecraft Primer minimum.
    • 
            
  • Disagreement with team → Dissent (record the view) + ACH (show the matrix that supports it).
    • 
            
  • Threshold tuning request → What-If first (does the change actually move TL?) + Decisions log (what changed, why).
    • 
        


        
12.4 Permission model

        
    
            
  • Read: any logged-in analyst.
    • 
            
  • Write (create/edit/resolve cards, score ACH, lock assumptions): analyst or admin role.
    • 
            
  • Admin lock: certain assumptions can be marked locked by an admin; analysts can still log invalidations against them but cannot delete the row. The full edit history is in the per-row change log.
    • 
            
  • Decision ledger entries are append-only — they cannot be deleted, only superseded.
    • 
        


        
12.5 Session boundary (F14)

        
Every write from this panel is stamped with a session_id. The session is per browser tab: opening a new tab gets a fresh UUID, closing the tab clears it (sessionStorage). Reloading the same tab preserves the id.

        
This lets the decision ledger group "everything one analyst did in one sitting" without conflating it with parallel work in other tabs by the same user.


        
12.6 Relationship to scoring

        
The Tradecraft surface is read-mostly with respect to the scoring engine. None of these tabs change live TL output. The exceptions:

        
    
            
  • What-If returns a simulated TL/score, but it is rendered as a side-panel comparison and does NOT overwrite the live scenario state.
    • 
            
  • Pre-Mortem & Assumptions can be elevated by admin to influence threshold tuning via the Admin panel — that path is explicit and audited, not automatic.
    • 
            
  • Hidden Signals / Coverage Gaps read from existing pipeline logs (noise exclusion, mute, circuit breaker state); they do not gate scoring themselves.
    • 
        


        
12.7 Auto-logged tradecraft actions in the Decision Ledger

        
Every tradecraft write (disconf / ACH / assumptions / pre-mortem / dissent — and their resolve/lock variants) is automatically appended to the Decision Ledger (F14) with a detail.auto = true marker. That means the ledger is a single, complete audit trail for the panel — you do not need to remember to log each action manually.

        
Auto-logged rows display an auto badge next to the decision type. The Decisions tab has a Show auto-logged tradecraft actions checkbox at the top: uncheck it to see only manually-entered decisions (threshold changes, weight overrides, intel actions, report publishes, etc.). Manual ledger entries posted directly to the Decisions form are not marked auto.

        
Auto rows carry the same session_id as the originating tab, so filtering the ledger by a session still groups every action (manual + auto) that one analyst performed in one sitting.


        
Methodological background: Heuer R.J., Psychology of Intelligence Analysis (1999, ACH Ch.8); CIA Tradecraft Primer (2009, KAC + ACH + Pre-Mortem); Klein G., Performing a Project Premortem (HBR 2007). The names "Key Assumptions Check" and "Devil's Advocacy" are used in the standard SAT sense from the Primer.

        


        

        
12. アナリスト・トレードクラフト


        
アナリスト・トレードクラフトパネル（TOOLS → TRADECRAFT → Analyst Tradecraft）は、自動スコアリングを補完する10種類の構造化分析技法（SAT: Structured Analytic Techniques）の作業面をまとめたものです。パネルは現在 focus 中のシナリオにスコープされており、focus シナリオを切り替えるとアクティブタブが再描画されます。


        
このパネルが存在する理由。収斂エンジンはシグナルの融合は得意ですが、自分自身の出した像が間違っているときにそれを教えてくれません。これらのタブは、上流パイプラインの失敗モード — 隠れた反証、単一ソース依存、もっともらしい代替仮説、いつのまにか前提となっているアナリストの思い込み — を意図的に表に出します。


        
12.1 パネルが捕捉する3つの失敗モード

        
    
            
  • 偽陽性（FP） — 偶然のシグナルで収斂が発火する。タブ：隠れシグナル / カバレッジ / 反証証拠。
    • 
            
  • 偽陰性（FN） — フィルタ・閾値で実際のエスカレーションが捨てられている。タブ：隠れシグナル（ノイズ/破棄ログ）/ カバレッジ（壊れたセンサー）。
    • 
            
  • 認知バイアス — 最初に思いついたストーリーへのアンカリング。タブ：シナリオ比較 / ACH / 少数意見 / 前提条件 / プリモーテム。
    • 
        


        
12.2 タブリファレンス

        

        
タブ目的使うタイミング

        
        
隠れシグナルパイプラインがフィルタアウトした項目を一覧（mute、ノイズ除外、信頼度フロア、重複排除）。シナリオが妙に静かに見えるとき、フロアが高すぎる疑いがあるとき。

        
カバレッジシナリオごとのセンサーカバレッジ（active / muted / circuit-broken / disabled）。結論を出す前に — どのセンサーが実際に寄与したかを確認する。

        
反証証拠現在のシナリオ仮説に反する証拠を提示（デエスカレーション兆候、対立する外交シグナル）。TL の引き上げ判断を出す前に必ず — 確証バイアス対策。

        
シナリオ比較シナリオの横並び比較（TL、トップ寄与、最近の根拠）。同じシグナルが複数のシナリオに当てはまり得るとき — フィットの良い方を選ぶ。

        
ACHHeuer の競合仮説分析。各証拠を各仮説に対して -2 〜 +2 で採点し、診断性で重み付け。帰属・意図が問われる重要評価のとき。お気に入りの仮説だけでなく代替仮説に対しても証拠を量る作業を強制する。

        
少数意見Devil's Advocate ログ：公表された評価に対する反対意見を記録する。コンセンサス判断に反対のとき — 失わないために記録する。

        
前提条件Key Assumptions Check（KAC）。暗黙の前提を顕在化し、要となる前提を lock し、崩れたら invalidate する。シナリオ監視の開始時、および状況が変わった都度。

        
プリモーテムKlein 2007 のプリモーテム：評価が間違っていると仮定して、その理由を列挙。重大度：低 / 中 / 高。高い確信度の評価を発出する前に。

        
決定台帳何が変更されたか（閾値、重み、分類、インテル裁定）を、誰が、どの根拠で行ったかの台帳。監査証跡。タブ session_id 自動付与。

        
What-Ifスライダによる participant 結合重みの調整→再採点。スナップショット再生 — センサー再実行はなし。感度分析：「日本の結合が 0.8 ではなく 0.5 だったら TL は出るか？」

        
        


        
12.3 どの技法をいつ使うか

        
    
            
  • 日常監視 → カバレッジ + 反証証拠。TL を確定する前の安価な習慣的チェック。
    • 
            
  • 異常スパイク → 隠れシグナル（本当に異常か、フロアが変わっただけか？）+ シナリオ比較（別のシナリオの方がフィットするか？）。
    • 
            
  • 重要判断（TL≤2、対外公表評価）→ ACH + プリモーテム + 前提条件 lock。CIA Tradecraft Primer の最低3点セット。
    • 
            
  • チームと意見が割れたとき → 少数意見（記録）+ ACH（その立場を支える行列を提示）。
    • 
            
  • 閾値調整リクエスト → まず What-If（変更で TL は本当に動くか？）+ 決定台帳（何を、なぜ変更したか）。
    • 
        


        
12.4 権限モデル

        
    
            
  • 読み取り：ログイン中の任意のアナリスト。
    • 
            
  • 書き込み（カードの作成・編集・解決、ACH 採点、前提の lock）：analyst または admin ロール。
    • 
            
  • Admin lock：特定の前提は admin が locked マークでき、analyst は invalidate ログは追加できますが行の削除はできません。編集履歴は行ごとの change log に残ります。
    • 
            
  • 決定台帳のエントリは append-only — 削除不可、後続エントリで上書き（supersede）するのみ。
    • 
        


        
12.5 セッション境界（F14）

        
このパネルからの全書き込みには session_id が付与されます。セッションはブラウザタブ単位です：新しいタブを開くと新しい UUID が発行され、タブを閉じるとクリアされます（sessionStorage）。同一タブのリロードでは id は維持されます。

        
これにより決定台帳は「1人のアナリストが1セッションで行ったこと」を、同一ユーザーが別タブで並行して行った作業と混同せずグループ化できます。


        
12.6 スコアリングとの関係

        
トレードクラフト面はスコアリングエンジンに対して基本的に読み取り専用です。ライブ TL 出力を変更するタブはありません。例外：

        
    
            
  • What-If はシミュレートされた TL/スコアを返しますが、サイドパネル比較として描画されるのみで、ライブのシナリオ状態には書き戻しません。
    • 
            
  • プリモーテム/前提条件は admin の判断で Admin パネル経由の閾値チューニングに昇格できますが、その経路は明示的かつ監査対象であり、自動ではありません。
    • 
            
  • 隠れシグナル/カバレッジは既存のパイプラインログ（ノイズ除外、mute、サーキットブレーカー状態）から読み出すだけで、それ自体が採点をゲートすることはありません。
    • 
        


        
12.7 決定台帳への自動記録

        
トレードクラフトパネルでの書き込み操作（反証 / ACH / 前提条件 / プリモーテム / 反対意見 ― およびその解決・ロック系の操作）はすべて、決定台帳(F14) に detail.auto = true マーカー付きで自動的に追記されます。これにより、台帳はパネル全体の完全な監査証跡となり、各操作を手動でログに残す必要はありません。

        
自動記録された行は決定タイプの隣に auto バッジを表示します。決定タブ上部の 自動記録されたトレードクラフト操作を表示 チェックボックスをオフにすると、手動で入力された決定（閾値変更、重みオーバーライド、インテル操作、レポート発行など）のみが表示されます。決定フォームから直接投稿された手動の台帳エントリには auto マークは付きません。

        
自動記録行は発行元タブと同じ session_id を引き継ぐため、セッションで台帳をフィルタすれば、1人のアナリストが1セッションで行った操作（手動 + 自動）をすべてグループ化できます。
