インテリジェンス運用ガイド — Noroshi 戦略 MDO レーダー

        ✕
    

    


        

        
本プラットフォームは Noroshi（烽火）、MDO C4ISR 戦略 OSINT レーダーです。サイバー・物理・情報の3ドメインにわたるシグナルを相関分析し、動態作戦の前兆指標を検出します。すべてのデータはオープンソースインテリジェンス（OSINT）のみから取得しています。各センサーは独立したバックグラウンドスケジュールで稼働し、収束スコアは最新キャッシュデータから SCORE_REFRESH_SEC=60 秒ごとに再計算されます。SYNC ボタンで全アクティブセンサーの即時取得とスコア更新を強制実行できます。

        
本ツールの結論であり、最終判断は組織のプロセスによって行われます。本レーダーは、組織的なインテリジェンス判断プロセスにおける一つのノードとして機能します。出力（脅威レベル、トレンド、ドメイン別ステータス、異常事象、推定攻撃モード）はすべて、透明な計算式と一次ソースから導出された ツールの結論 です。最終的な状況判断は、本ツールの出力を他の情報源（HUMINT、SIGINT 等）と統合した上で組織が行います。ページ上部に常時表示される disclaimer バナーが正式な注意書きであり、v2 conclusions API は各結論の完全な導出経路（formula 参照、閾値、ソース URL、LLM プロンプトハッシュ）を公開してアナリストの検証を支援します。

        


        

            
            
            
            
            
            
            
            
            
            
            
            
            
            

        

        


        

        
1. ツールの境界と運用者責任


        
本章はすべてのオペレーターの必読事項です。本ツールは OSINT のみという制約下で技術的に実行可能な最大の評価結論を出力し、その導出に用いた式・閾値・一次ソース・LLM プロンプトをすべて開示します。以下の固有の限界を理解することで、本ツールの出力を組織の意思決定プロセスにおける一つのノードとして、HUMINT・SIGINT 等の本ツールが見ることのできない他情報源と統合して活用できます。


        
11.1 センサーカバレッジのギャップ

        
    
            
  • 英語バイアス：GDELTおよびRSSナラティブセンサーは主に英語メディアをインデックスしています。中国語、ロシア語、ペルシャ語、韓国語のソースは過小表現されています。システムはグローバルな英語メディアトレンドを緩和するためにmedian-delta減算を適用していますが、現地語のナラティブは完全に見逃される可能性があります。
    • 
            
  • 西側諸国アドバイザリーバイアス：渡航勧告データは米国、英国、カナダ（すべてファイブアイズ加盟国）から取得。これらの政府は独立した評価ではなく、共有情報や政治的同盟に基づいて勧告を発行する場合があります。収束検出により緩和されますが、完全には排除されません。
    • 
            
  • ADS-Bカバレッジ：ISRおよび軍事支援航空機の監視はADS-Bトランスポンダデータに依存します。軍用機はEMCON（電波管制）時にトランスポンダをオフにすることが多く、ADS-BによるISRソーティの検出は下限値を示します。ADS-Bトラックの不在はISR活動の不在を意味しません。
    • 
            
  • AISダークギャップ：海上監視はAISトランスポンダ信号に依存します。国家行為者は機密作戦中にAISを意図的に無効化します。「ダークギャップ」の検出自体がシグナルですが、事前のAIS履歴が必要です。
    • 
            
  • Telegramカバレッジ：Telegram監視は公開Webプレビュー（t.me/s/）を使用します。Webプレビューが有効な公開チャネルのみが対象で、非公開・制限付きチャネルは監視できません。セキュリティニュースRSSフィードによるハクティビストキャンペー���報道で補完しています。
    • 
        


        
11.2 ベースラインとコールドスタートの制限

        
    
            
  • コールドスタート期間：Zスコアベースの検出（Cloudflare HOD、BGP、CT Log、海運、ナラティブ）には履歴ベースラインが必要です。運用開始から最初の4〜7日間は異常検出感度が低下し、重大度はレベル1（WATCH）に制限されます。HUDのbaseline_maturityインジケーターが現在のベースライン完成度を表示します。
    • 
            
  • 季節/周期的盲点：海運ルート分析は曜日+時間バケットベースライン（14日間ウィンドウ）を使用します。年間パターン（祝日、モンスーン季節、政治サイクル）は依然として偽陽性を引き起こす可能性があります。
    • 
            
  • 為替USDファクターノイズ：システムは全監視通貨のZスコア中央値を減算してグローバルなUSD変動をフィルタリングします。これは緩やかなFRB政策変更には有効ですが、危機に起因する資本逃避がグローバルに相関している場合は過剰補正する可能性があります。
    • 
        


        
11.3 方向性と帰属

        
    
            
  • 相関 ≠ 因果関係：マルチドメイン収束スコアリングは、サイバー・物理・情報ドメイン間のシグナルの統計的共起を識別します。意図、指揮関係、因果連鎖を判定することはできません。高い収束スコアは「複数の指標が同時にアクティブである」ことを意味し、「攻撃が差し迫っている」ことを意味しません。
    • 
            
  • 帰属の限界：システムはTHREAT_ACTOR_MAPPING（Telegramチャネル、ASN所有権、APTタグ）を使用して脅威アクターを国にマッピングします。これらのマッピングはヒューリスティックであり、偽旗作戦、共有インフラ、プロキシアクターにより不正確な場合があります。
    • 
            
  • 監視方向性：本システムは監視対象国に対する攻撃の前兆を検出するように設計されています。味方の攻撃作戦、敵対者の防衛準備、または国内の市民不安の検出を目的としていません。シグナルは「この国が攻撃されようとしているか？」というレンズを通じて解釈されるため、曖昧な状況に適用すると確認バイアスが生じます。
    • 
            
  • 待ち伏せパターンの注意：二次微分加速度検出器（「待ち伏せパターン」）は変化率の急激な変化を識別します。これは正当なイベント（例：予定された軍事演習の突然のランプアップ）と本物の奇襲攻撃の両方でトリガーされる可能性があります。
    • 
        


        
11.4 信号重複排除と二重カウント

        
    
            
  • BGP信号グルーピング：IODA、RIPE BGP、IHR切断センサーはすべてBGPルーティング異常を測定します。エンジンはこれらをsignal_source="bgp"でグループ化し、同一の物理イベントの三重カウントを防ぐためにsum()ではなくmax()を取ります。
    • 
            
  • 残存する重複：証明書透過性のサージはBGPハイジャックイベントと相関する場合があります（DNS+BGP攻撃は共起することが多い）。基盤となる現象が異なるため、現時点ではこれらは重複排除されていません。
    • 
        


        
11.5 オペレーター実践指針

        
    
            
  • ツール出力は判定そのものではなく組織内の一ノード：本ツールは式とデータが許す限り最大の結論を、完全な導出トレースと共に出力します。組織はこの出力を HUMINT・SIGINT 等と統合し、運用上の判断を導きます。MUTE 機能は誤検知が裏取りされたセンサーの寄与を取り除くためのものであり、これはツールの根拠入力を再構成する操作です（ツール推論を信用するか否かの票決ではありません）。
    • 
            
  • ドメイン重みバイアス：デフォルトの重み（cyber=0.50、physical=0.30、info=0.20）はサイバーファーストの監視姿勢を反映しています。オペレーターは運用コンテキストに基づいてDOMAIN_WEIGHT_*変数を調整する必要があります（例：動的紛争中はphysical重みを増加）。
    • 
            
  • 脅威レベルの解釈：重大度レベル（NORMAL→WATCH→ELEVATED→CRITICAL）はベースラインに対する相対値であり、危険の絶対的評価ではありません。「CRITICAL」レーティングは「過去の正常値を大幅に上回っている」ことを意味し、攻撃が差し迫っていることを本質的に意味するものではありません。
    • 
        

        

        

        

        

        
2. 結論の読み方


        
2.1 脅威レベル定義

        
最終スコア = 生スコア + 収束ボーナス + シーケンスボーナス。 ダウングレード時のみ1サイクルのヒステリシス遅延を適用（しきい値振動を防止）。アップグレードは即時。

        
    
            
  • レベル1 — 危機的: スコア ≥ 9 かつハード条件を満たす（コアスパイク >5.0× かつ BGP 障害が同時確認）。大規模サイバーサージとインフラ崩壊の複合特徴 — 協調的侵攻前ブラックアウト作戦。運動学的行動の確率が極めて高い。すべての緊急手順を発動すること。
    • 
            
  • レベル2 — 深刻: スコア ≥ 6 かつ 2ドメイン以上がアクティブ。単一ドメイン（例：サイバーのみ）はスコアに関わらずTL2に到達不可 — 複数ドメインの裏付けが必須条件。直接的な敵対帰属または重大なインフラ劣化を伴うマルチドメイン脅威。直ちに指揮官への通知が必要。
    • 
            
  • レベル3 — 高: スコア ≥ 4。少なくとも2つのセンサーにまたがる重大な協調異常。準備フェーズ、探査作戦、または初期エスカレーションを示す。監視強化が必要。
    • 
            
  • レベル4 — 上昇: スコア ≥ 2。メディアトーンの悪化、孤立した BGP イベント、または軽微な L7 ベクターシフトなどの早期指標。外交的緊張の悪化または偵察活動と整合。
    • 
            
  • レベル5 — 平常: スコア < 2。バックグラウンドノイズレベル。監視ドメイン全体で重大な異常なし。
    • 
        


        
2.2 結論カード

        
    
            
  • レイヤ 1 — Conclusion Cards: HUD 直下に focus シナリオの 5 結論カードを常時表示。ConclusionType バケット別: THREAT_LEVEL（1〜5 + ラベル）、TREND（上昇 / 横ばい / 下降）、PER_DOMAIN（cyber / physical / info の状態組み合わせ）、ANOMALY（センサー外れ値の上位）、ATTACK_MODE（ルールベース攻撃パターン推定または INSUFFICIENT_DATA）。各カードには見出し結論と確信度ドットを表示。10 秒ごとのスコアリングポーリングで更新され、Switch Focus（◎ボタンまたはシナリオパネル）後は <100 ms で再描画される（v1 同期完了を待たない）。
    • 
        


        
2.3 ドリルダウン監査トレース

        
    
            
  • レイヤ 2 — Drill-down Modal: カードクリックで監査トレースモーダルを開く。各結論は以下を露出: (a) 採用した 計算式参照 と閾値、(b) 結果を生んだ 数値入力、(c) キャリブレーションメタ（サンプル N、最終キャリブレーション時刻；信頼に足る N 未満の場合は low-N 警告）、(d) 参照した 一次ソース（重複排除済の http(s) URL のみ、XSS 安全）、(e) LLM ステップが寄与した場合の LLM プロンプトハッシュ。ESC・[✕]・背景クリックで閉じる。閉じると元のカードへフォーカス復帰。読み込み中に他カードへ切替えた場合は AbortController で古い fetch をキャンセル。
    • 
        


        
2.4 センサーウォッチペイン — TOOLS ▾ → Sensor Watchpane

        
    
            
  • レイヤ 3 — Sensor Watchpane — TOOLS ▾ → Sensor Watchpane: アナリストが任意のセンサーをピン留めできる持続型フローティングパネル。+ Add sensor でカタログを ID / ラベル / ドメインで絞り込み（検索ボックス、大文字小文字を無視する部分一致）、選択して追加。各行はセンサーラベル、スコープ、ステータスピル（FIRED / NORMAL / SUPPRESSED）、sensor_observation_ts テーブル（24h TTL、scoring tick 毎に append）由来のスパークライン、現在の数値スコアを表示。更新は 10 秒スコアリングポーリングに相乗り（パネル表示中のみ）。ピン留めしたセンサーとパネル位置・表示状態は localStorage でブラウザリロードを跨いで永続化。黄色の history shallow タグは観測点が 2 点未満（fresh DB / 再起動直後の初サイクル）の時のみ表示され、系列が蓄積されると消える。アラームモード: 各行に 🔔 ボタンを設置。条件（score > 5、delta > 2、status == FIRED 等）を設定すると、条件成立中は行が赤化し ⚠ バッジを表示。任意で false→true 遷移時に Web Notification を 1 回発射（連続 active 中は抑制）— 結論層が suppress した signal をアナリストが直接監視するための経路。条件はセンサーリストと同じ localStorage に永続化。
    • 
        


        
2.5 ディスクレーマバナー

        
    
            
  • ディスクレーマバナー: HUD 直下に「ツールの結論であり、最終判断は組織のプロセスによって行われます」と v2 API サーフェス通知を常時表示する帯。アナリストが結論カードを最終判断と誤認することを構造的に防止。

4. HUD・パネル・状況認識画面

        
数値計算と並行してアナリストの直感とパターン認識（識別先行意思決定）を活性化するために設計された20のビジュアルコンポーネント。自然主義的意思決定（NDM）理論に基づく；即時の状況認識形成を目的とする。


        

            
アクセス方法

            
TOOLS ▾ ドロップダウン（HUD 右上）でパネルを個別に有効化。CORE: Target Visibility / Attack Origin Feed / Evidence Chain / Telegram SIGINT / Sensor Watchpane。ANALYTICS: Strategic Climate / Weather Brief / GreyNoise / History Analysis / LLM Intelligence。SIMULATION: What-If Sim / SPOF Analysis。ADMIN: Sensor Heatmap / Sensor Manager / Admin Panel（シアンドット = アクティブ）。各パネルは ✕ で個別に閉じる。常時表示コンポーネント（Ambient Atmosphere / Radio Silence / Threat Terrain / Conclusion Cards）はインタラクションなしに自動動作。レポートボタングループ（HUD右上、TOOLS横）: SITREP / EVIDENCE / SALUTE — 3つの主要出力モーダルへのワンクリックアクセス。SALUTEエクスポートはEvidence Modalフッターからもアクセス可能。マップインタラクション: 国マーカークリックでCountry Intelモーダルを開く。HUDの脅威レベル表示クリックでEvidenceパネルを開く（EVIDENCEボタンと同一）。

        


        
4.1 アンビエントアトモスフィア

        
    
            
  • 常時アクティブ。 脅威レベルに応じて画面全体の背景色を微妙に変化させる（レベル3 → 緑色調 / レベル2 → 赤橙色調 / レベル1 → 深紅色調、2〜5秒のアニメーションサイクル）。長時間監視セッション中に「何かがおかしい」ことをシグナリングするために周辺視野を活用し、注意の集中化を防止。
    • 
        


        
4.1 無線沈黙インジケーター

        
    
            
  • 下部 HUD に常時表示。 脅威スコアが有意（≥3 ポイント）であるが速度がゼロに近い状態を検出 — QUIET としてフラグ。
    
            QUIET の含意: (1) 運動学的行動前の通信ブラックアウト（EMCON）、(2) センサー抑制（敵対者によるジャミング/スプーフィング）、(3) 戦術的作戦停止。真の沈黙は平和を意味しない — 沈黙自体が「何も起きていない」という誤った認識を防ぐための異常として扱われる。
    • 
        


        
4.1 脅威テレイン オーバーレイ

        
    
            
  • マップレイヤーコントロール（右上）→ Threat Terrain。 DDoS スパイク強度（avg_spike）にスケールした半透明コロプレス型サークルを監視国の上にレンダリング。BGP 確認済み障害 = 赤；スパイク ≥4× = オレンジ；それ未満 = 黄色。半径はスパイク強度に比例（最大 ≈620 km）。脅威圧力の分布を地理的に一目で把握可能。通常スパイクレベル以下の国はレンダリングされず、ノイズを最小化。
    •

4.2 Telegram SIGINT — CHAIN パネル → Telegram Mirror 行の SIGINT↗ ボタン

    • 
            
  • 国別活動グリッド: アクティブ国ごとに1タイル。各タイルに国コード、総ヒット数、最高検出レベルバッジを表示。空状態テキストはコンテキスト対応: 最初のサイクル前は「センサー未ポーリング」；ヒットなしでポーリング完了後は「チャンネル活動未検出」。タイルをクリックすると、その国のみに傍受ログをフィルタリング。

  • チャンネルリスト: THREAT_ACTOR_MAPPING に設定されたすべてのチャンネルを、関連する国とミラー URL とともに一覧表示。チャンネルカバレッジの確認と監視への新規チャンネル追加の参照として使用。

  • 誤検知抑制: センサーは部分文字列衝突を避けるため、単語境界正規表現マッチング（\b）を適用（例: "target" が "targeting" に一致しないよう）。2文字以下のキーワードは完全にスキップ。複数単語キーワードとハッシュタグは完全部分文字列マッチングを使用。

  • 国ノイズ分類: 国ごとの GreyNoise 分類を表示 — TARGETED（トラフィックが指向性を持ち、バックグラウンドスキャナーではない）、MIXED、または NOISE_DOMINANT（≥70%インターネットバックグラウンドスキャントラフィック、サイバードメイン抑制）。GREYNOISE_API_KEY（Enterprise GNQL）が必要。Enterprise キーなしの場合、分類は UNKNOWN を表示。

  • 調査ログ: 直近20件の IP 照会のセッション履歴をブラウザの localStorage に保持。攻撃送信元フィードパネルで浮上した疑わしい送信元 IP のトリアージにこのパネルを使用。

4.3 戦略的環境気候フィード — TOOLS ▾ → Strategic Climate / HUD Climate バッジ

        
    
            
  • 目的: 「ペンタゴンピザ指数」の概念に着想を得た間接的環境インテリジェンス指標。脅威を直接測定するのではなく、観測可能な行動の副産物から早期警戒を提供。脅威レベルスコアリングとは独立した分析軸として機能。
    • 
            
  • 環境気候ゲージ: 5段階の環境気圧計: FROZEN（全指標静穏）→ COOL（微弱シグナル）→ WARMING（複数指標上昇）→ HOT（広範な環境変化）→ FLASHPOINT（歴史的パターン合致）。HUDではコンパクトバッジ、パネルではプログレスバーで表示。
    • 
            
  • 環境気候フィード: 生の事実を最小限の解釈で提示するスクロール可能なイベントログ。各イベントはタイムスタンプ、軸タグ、ヘッドライン、詳細を表示。アナリストがフィードを直接読み、自ら統合判断する。
    • 
            
  • 軸フィルター: イベントは3つの分析軸+コンテキストでタグ付け:
                
      
                    
    • 時間 (⏱) — T2: 国営メディア発信テンポ異常（急増または沈黙）、T4: 対象国でのGoogle Trends危機キーワードスパイク
      • 
                    
    • 空間 (📍) — S1: 民間航空路の暗黙回避（航空会社の自主迂回）、S2: 商船のAISダークギャップ（EMCON/迂回）、S3: 通貨ストレスと相関崩壊
      • 
                    
    • 対象 (🎯) — O1: 監視対象政府ドメインに対する未信頼CA発行 / 政府TLDレベルのワイルドカード証明書（アイデンティティ一致型）、O3: ナラティブ標的の移動（国営メディアの敵対対象変化）
      • 
                    
    • 暦 (📅) — 歴史的記念日の一致（±2日）、外交デッドラインの収束
      • 
                
    
            
    • 
            
  • 季節ベースライン: 指標T2（メディアテンポ）、S1（航空）、S3（為替）はSeasonalBaselineエンジンを使用し、同じ曜日・6時間帯バケットと比較。これにより定期的な周期パターン（週末のメディア沈黙、夜間の航空減少、為替市場の閉鎖）からの誤検出を防止。3段階フォールバック: 完全一致（曜日＋時間帯）→ 同時間帯の全曜日集約 → 全履歴平均。ベースラインレベルはイベント詳細に exact、hour、all として表示。
    • 
            
  • 設計原則: 環境気候フィードは脅威レベルを補完するが、決して変更しない。TLが低いのにClimateがWARMINGの場合、その乖離そのものがシグナル — 直接チャネルではまだ見えないが何かが準備されている可能性。
    • 
            
  • API: GET /api/climate（全体状態）/ GET /api/climate/feed?axis=time&limit=50（フィルタ済みフィード）。

4.4 What-Ifシミュレーション — TOOLS ▾ → What-If Sim

4.4 SPOF分析 — TOOLS ▾ → SPOF Analysis

  • ドメイン健全性カード: ドメインごと（Cyber / Physical / Info）に1枚のカード。アクティブ/合計センサー数、冗長性ステータス、重大SPOFの数を表示。

  • センサー健全性: SPOFリスト内の各センサーのリアルタイム健全性ステータス、キャッシュ経過時間、最終エラーを表示。

4.5 分析根拠（エビデンスモーダル） — HUD EVIDENCE ボタン / HUDの脅威レベル表示をクリック

        
    
            
  • 目的: どのセンサーがどの信頼度レベルで発火し、なぜ発火したかを示す透明な分析内訳 — 収斂エンジンのコア説明責任レイヤー。すべての脅威評価が監査・理解可能であることを保証。収束スコア内訳、システム評価、センサー根拠マトリクスの3つのラベル付きセクションで構成。
    • 
            
  • アクセス方法: HUDレポートグループ（SITREP / SALUTE横）のEVIDENCEボタンで専用ワンクリックアクセス。HUDの脅威レベル表示をクリックしても同じモーダルが開く（パワーユーザー向けショートカット）。
    • 
            
  • セクション1 — 収束スコア内訳: ドメイン別寄与度（Cyber / Physical / Information）— スコアポイント × 重み = 加重寄与度。収斂スコア合計サマリー。
    • 
            
  • 文脈整合度（CAC）: スコア（1〜4スケール）と各軸の整合状態:
                
      
                    
    • 地理的整合 — 地理的に一貫したエリアでセンサーが発火
      • 
                    
    • 時間的整合 — ドメイン間のタイミングパターンが整合
      • 
                    
    • 戦略的整合 — ターゲットが既知の戦略目標と一致
      • 
                    
    • 作戦的整合 — 攻撃ベクターが作戦的に一貫
      • 
                
    
            
    • 
            
  • 方向性サマリー: 主要脅威方向 — ADVERSARY_OFFENSIVE（敵対的攻勢）/ FRIENDLY_DEFENSIVE（友軍防衛）/ TARGET_IMPACT（標的影響）— 明瞭度パーセンテージ付き。
    • 
            
  • セクション2 — システム評価: エンジンが生成した自由形式の文脈的推論。現在の脅威態勢、主要シグナル、注目すべきパターンのナラティブ説明を提供。
    • 
            
  • セクション3 — センサー根拠マトリクス: センサーごとに1行 — 列: センサー | ドメイン | ステータス（FIRED / HOLDING / SUPPRESSED）| 観測値 | スコア | 信頼度（0–100%）| 方向（敵対的攻勢 / 友軍防衛 / 標的影響）| 発火理由/注記。ドメイン色分け行（Cyber = シアン、Physical = オレンジ、Info = パープル）。各センサー行にはアナリストによる制御抑制用のミュートボタンとシグナルトリアージ用のノイズ分類ボタンを含む。
    • 
            
  • 寄与度ウォーターフォール: 各センサーの総収斂スコアに対するパーセンテージ寄与を可視化する水平積み上げバー。セグメントはドメイン別に色分け（Cyber = シアン、Physical = オレンジ、Info = パープル）、ボーナス寄与（収斂ボーナス、CAC整合）は緑で別表示。各セグメントにホバーでセンサー名と正確なパーセンテージを表示。どのセンサーが現在の脅威評価を主導しているかを一目で把握可能。
    • 
            
  • カウンターシグナルとインテリジェンスギャップ: 確証バイアス防止セクション。2つのカテゴリーを強調表示:
                
      
                    
    • カウンターシグナル（緑チップ）— 積極的にチェックし異常なしと判定したセンサー。脅威評価を抑制すべき安心材料を表す。
      • 
                    
    • インテリジェンスギャップ（琥珀チップ）— オフライン、サーキットオープン、またはデータ陳腐化（データ未受信）のセンサー。脅威が未検知のまま存在しうる盲点を表す。各チップに最終データ受信からの経過時間を表示。
      • 
                
    
            
    • 
            
  • ノイズフィルター適用: このサイクルでスコアを低減したアクティブノイズ抑制器（宇宙天気、GreyNoise、地震、PeeringDB）のフッターリスト。
    • 
            
  • エクスポートアクション（フッター）: SALUTEレポート出力ボタンでエビデンス確認ワークフローから直接SALUTEモーダルを開く。SITREPを表示ボタンでエグゼクティブサマリーを開く。いずれもHUDに戻ることなく、分析→報告の自然なフローを提供。
    •

4.6 協調指数 — コンステレーション・フィールド

        
    
            
  • 目的: 国家間の協調関係をマップ上に可視化。複数の国が希少な攻撃元インフラを共有している場合、IDF 重み付き overlap (0〜~5) と spike 相関、C2-SYNC、adversary strike を統合した協調指数を算出。
    • 
            
  • スコア式: 各国の攻撃元 ASN 分布の pairwise histogram intersection を IDF (Inverse Document Frequency) で重み付けし、Cloudflare/AWS/Google など世界共通の ASN は ~ゼロ寄与、希少な ASN 共起のみがスコアに乗る。地図は既定で strategic_alert.correlations_idf_l3（3 日 baseline、安定性のため）を参照、L3 が未温まりの場合は per-tick の correlations_idf に自動 fallback。
    • 
            
  • コンステレーションリンク: 二層の直線（太いグロートラック＋細いパルスコア）が相関国を接続。曲線の DDoS 攻撃アークとは視覚的に明確に区別。両端にダイヤモンド ◆ マーカー。
    • 
            
  • 色スケール (IDF): シアン (≤1.0) → イエロー (1.0–2.0) → オレンジ (>2.0) → レッド (C2-SYNC 確認 かつ ≥1.5)。パルス速度は協調レベルに応じて加速。
    • 
            
  • ツールチップ: リンクにホバーで内訳表示 — IDF overlap 値、L3/L7 分割、両方高負荷、C2-SYNC、adversary strike 指標。すべて IDF スケール表示。
    • 
            
  • レイヤー切替: レイヤーコントロールの「Coordination」で表示/非表示。
    • 
            
  • 表示モード (HUD): Cyber サブメトリクス行の Coord 線 ボタンで OFF → STRONG → ALL を切替。現状の既定は raw モード時代の名残で OFF、IDF で saturation が解消されたため STRONG 復帰検討中（観察期間後に判断）。STRONG は coordIdx ≥ 1.5 (≈P95 — analyst が動くべき上位 5%) のみ描画。ALL は noise floor 0.5 超の全ペア（全体像）。選択は端末ごとに永続化。tier 別アニメ (low 静止、mid/high のみ脈動) は ALL モードでの視覚ノイズも抑制。
    • 
            
  • raw overlap でなく IDF を使う理由: raw histogram intersection は多国構成シナリオで全ペアが mean 53/max 91 となり、平時にもかかわらず「全国が 70% 相関」となって信号性ゼロだった。IDF はその構造的ベースライン (mean 0.4 / P50 0.0) を抑制するため、可視化された線は実質的なインフラ共有のみを示す。
    • 
        


        
4.7 信頼度伝播 & TL近接度

        
    
            
  • センサー信頼度 (0–100%): 各センサーがヘルス状態（OK=100%, STALE=50%, ERROR/DISABLED=0%）、サンプル充足度（閾値到達まで30%→100%で漸増）、ベースラインカバレッジに基づく信頼度係数を報告。証拠パネルの「信頼度」列に色分けバッジ（緑/橙/赤）で表示。
    • 
            
  • 信頼度加重スコアリング: ドメインスコアが スコア × 信頼度 で計算。低信頼度センサーの寄与は比例的に低減。全センサーが正常でデータ十分な場合、従来エンジンと同一の動作。
    • 
            
  • 収束ボーナスゲーティング: マルチドメイン収束ボーナス（+1/+2）に min(アクティブドメイン信頼度) を乗算。ノイズの多いまたは劣化したセンサーによるFULL_CONVERGENCE経由のスコア膨張を防止。
    • 
            
  • TL近接度インジケーター: HUDの脅威レベル横に現在スコアの次のTL境界までの距離を表示。▲ 赤 = エスカレーション近接、▼ 緑 = デエスカレーション近接。安定時（境界から1.5pt以上）は非表示。
    • 
        


        
4.7 DDoSコア強化

        
    
            
  • 封鎖指数 → スコア反映: 封鎖指数（BI）が7.0/10以上に達した場合（有効なインフラ封鎖を示す）、サイバードメインの脅威スコアに+1pt寄与。従来は表示のみ。
    •

4.x v3 影画面の表示状態（表示モード・遮蔽・ライブチップ）

        
v3 影画面は浮遊パネルを持たない（P8 §7 でパネル蓄積を廃止）。代わりに、画面の状態を語る 3 つの小さな表示がある。いずれも判断は純モジュールが行い、DOM は書くだけである。

        
    
            
  • 表示モード chip（注目レーン横、3 値: 待機表示 / 常設表示 / 最重要バナー）。サーバが重大標識（critical / recall_reducing / kill_switch）を付けた行、または CRITICAL 帯の行があれば無条件で最重要バナーへ移る（S1-UI-031、NP1）。確認済・一時保留・却下はバナーを消せない（S1-UI-032）。chip の tooltip には選んだ理由が必ず平文で入る（NP6）。
    
            v1 の 4 つのスコア帯（0.40/0.50/0.85/0.78）は移植していない。スコアはサーバが決める量であり、ブラウザがそれを自前の境界と比較すればバックエンドから見えない閾値を持つことになるため。ヒステリシスは連続静穏回数で表現する（重い側へは 1 回で入り、軽い側へは複数回連続で静かなときだけ降りる）。表示下限（min_score）はサーバが R6 の時点で適用済である。
    • 
            
  • focus 切替の遮蔽（DIMMED → REFRESHING → ENDED、代替終端 STALE）。結論の到着で遮蔽を解除し、シナリオ台帳の到着で更新標識を終える。遮蔽が時間切れになっても遮蔽は維持する（S1-UI-049）— 解除すると「前のシナリオの数値を新しいシナリオの名前で」見せることになり、欠測より悪い。時間切れ時は「同期未完了 — 最後に取得した状態を表示中」と再取得導線を出し、任意のキーで解除できる。Replay 中は遮蔽しない。
    • 
            
  • ライブチップ（状況確認ヘッダ）。S1-UI-011 の 3 値（connected / degraded / disconnected）に加えて unmounted を持つ。「切断」はチャネルが在って乗れていないという主張であり、そもそもチャネルを合成していない配備にそれを言うのは誤警報になるため。切断中もポーリングは継続し、加速もしない。

5. 日常監視のワークフロー

        
    
            
  • クロスドメインの裏付けを優先する。 単一ドメインの指標だけでエスカレーションしないこと。民間ボットネットは軍事的意義なしに定期的に3〜5倍の DDoS スパイクを生成する。レベル2のエスカレーションを推奨するための最低基準は FULL CONVERGENCE（サイバードメイン + 物理ドメイン + 情報ドメイン）である。
    • 
            
  • HITL MUTE で既知の誤検知を抑制する。 非敵対的な原因が確認された場合（例：大規模スポーツイベントによる領空異常、正規 CDN メンテナンスによる BGP シフト）、エビデンスパネルでそのセンサーをミュートする。MUTE 状態は localStorage によりリロードをまたいで保持される。
    • 
            
  • 指揮官報告には SITREP を使用する。 SITREP ボタンは、ドメイン内訳、センサーエビデンス、トレンド指標を含む構造化された状況報告書を生成する。
    • 
            
  • ベースラインの十分性を確認する。 Cloudflare の HOD Z スコアは UTC 時間帯ごとに同一時間帯サンプル ≥7 件で有効化される。初回起動時はバックグラウンドで全24 UTC 時間帯スロットを国あたり約7秒で補完：CF L7 hourly timeseries（時間帯別強度）と日次オリジン分布を組み合わせ、ウォームアップ期間なしで即時有効化される。エビデンスパネルに "HOD warmup N/7" が表示される場合は timeseries が取得できず、ライブポーリングで蓄積中であることを示す。RSS Narrative も同様に≥7日間のデータが必要。
    • 
            
  • VELOCITY / AMBUSH メーターを読む。 VELOCITY は脅威スコアの現在の変化率（ポーリングサイクルあたりのポイント ≈ 900秒）。正（赤↑）= アクティブに悪化中。負（緑↓）= 改善中。⚡ AMBUSH（赤点滅）= 変化率自体が加速中 — 二次微分スパイク。これは最も時間的に緊急なシグナルであり、急速に圧縮される攻撃ウィンドウを示す。
    • 
            
  • CHAIN パネルのエスカレーションナラティブを読む。 CHAIN ボタン（HUD 右上）はエビデンスチェーンタイムラインを開く。過去24時間以内のタイムスタンプ付き [NARRATIVE_BURST → ISR_SURGE → SYNC_DDOS → FIRMS_ANOMALY] エスカレーションイベントを表示。FULL CHAIN（+3 pt）は4種類のイベントタイプすべてが24時間以内に発生したことを意味 — 協調的マルチドメイン準備の強力な指標。v9 では TELEGRAM_INTENT、MASKIROVKA、C2_SYNC、INFRA_BLACKOUT もチェーンログに登録される。
    • 
            
  • GDELT トーンの解釈。 –15.0 = 活発な軍事緊張レトリックのしきい値（v9 キャリブレーション）。–18 = アクティブな危機フレーミング。–20以下 = 歴史的に運動学的行動が切迫または進行中に相当。30分間の単一ポーリングサイクル内での3〜5ポイントの急落は、同じ値への緩やかな下落より重要性が高い。
    • 
            
  • 封鎖インデックスの解釈。 インデックスは DDoS 強度とインフラ劣化の両方に連動してスケールする: Check-Host ノードへの到達可能性を維持したままの高ボリューム DDoS は10%ノイズフロアの貢献のみを生成（インデックス ≈ 1.0）。インフラ無力化（インデックス ≥ 7.0）には、DDoS サージ、RIPE BGP 撤退、そしてグローバルノードからの Check-Host BLACKOUT が同時に必要 — 2022年2月のロシア地上侵攻の30〜90分前に観察されたパターン。
    • 
            
  • SURVIVAL HUD の解釈（v9）。 グローバルノードからの重要な国家インフラ（政府、中央銀行、電力網）のリアルタイム到達可能性を表示。OK = インフラ到達可能。PARTIAL = 一部のノードが障害を報告 — DDoS 影響または局所的障害の可能性。BLACKOUT = 複数のグローバル拠点から同時に重要インフラへの到達不能。BLACKOUT + 高い封鎖インデックス = 侵攻前ブラックアウトシナリオの可能性が高い。
    • 
            
  • C2-SYNC の解釈（v9）。 複数国への攻撃が60秒以内（C2 SYNC CONFIRMED）または5分以内（PARTIAL）に開始されたかどうかを表示。地理的に離れた国家間での厳密な時間的同期は、緩やかに協調されたハクティビスト活動ではなく、国家が統合した C2（指揮統制）の特徴。
    • 
            
  • Maskirovka 検出（v9）。 物理的障害が確認され（IODA 劣化または Check-Host BLACKOUT）、すべてのナラティブチャンネルが同時に沈黙している場合（RSS バーストなし、Telegram 意図なし）、システムは潜在的な Maskirovka（ロシア軍事欺瞞ドクトリン）にフラグを立てる。Check-Host の PARTIAL 単独ではトリガーされない — ノードの局所的障害による誤検知を削減するため、BLACKOUT のみが対象。ナラティブ増幅を伴わない物理的障害は、ハクティビストキャンペーンではなく真の運動学的作戦を示す可能性がある — ハクティビストグループは通常、攻撃の前後に標的を大声で告知する。

  • confirm済みインテルは指数関数的に減衰。 LLMインテルを confirm しても、シナリオスコアへの寄与は「24h フル強度 → 以降ゼロ」ではない。confirm 直後にフル重みで入り、exp(-age / τ)（τ=12h）で減衰する。実用値: age=12h で約37%、24h で約14%、36h で約5%、48h で完全除去。CONFIRM クリック直後に TL が急上昇することはない。 新鮮な confirm が容量上限（cap）を占有し、古いアイテムは自然にフェードアウト。キャリブレーション目的で従来の二値TTL挙動と比較したい場合は、Config 画面で INTEL_AGE_DECAY_ENABLED=false に設定。ソースタイプ別のτ上書き（例: 動きの速い外交シグナル）は INTEL_AGE_DECAY_TAU_HOURS_DIPLOMATIC=6 のように環境変数で指定。エビデンスパネルは各 confirm 済みアイテムの横に (age X.Xh, w=Y.YY) を表示し、減衰後の重みが一目で確認可能。

9. アナリスト・トレードクラフト


        
アナリスト・トレードクラフトパネル（TOOLS → TRADECRAFT → Analyst Tradecraft）は、自動スコアリングを補完する10種類の構造化分析技法（SAT: Structured Analytic Techniques）の作業面をまとめたものです。パネルは現在 focus 中のシナリオにスコープされており、focus シナリオを切り替えるとアクティブタブが再描画されます。


        
このパネルが存在する理由。収斂エンジンはシグナルの融合は得意ですが、自分自身の出した像が間違っているときにそれを教えてくれません。これらのタブは、上流パイプラインの失敗モード — 隠れた反証、単一ソース依存、もっともらしい代替仮説、いつのまにか前提となっているアナリストの思い込み — を意図的に表に出します。


        
12.1 パネルが捕捉する3つの失敗モード

        
    
            
  • 偽陽性（FP） — 偶然のシグナルで収斂が発火する。タブ：隠れシグナル / カバレッジ / 反証証拠。
    • 
            
  • 偽陰性（FN） — フィルタ・閾値で実際のエスカレーションが捨てられている。タブ：隠れシグナル（ノイズ/破棄ログ）/ カバレッジ（壊れたセンサー）。
    • 
            
  • 認知バイアス — 最初に思いついたストーリーへのアンカリング。タブ：シナリオ比較 / ACH / 少数意見 / 前提条件 / プリモーテム。
    • 
        


        
12.2 タブリファレンス

        

        
タブ目的使うタイミング

        
        
隠れシグナルパイプラインがフィルタアウトした項目を一覧（mute、ノイズ除外、信頼度フロア、重複排除）。シナリオが妙に静かに見えるとき、フロアが高すぎる疑いがあるとき。

        
カバレッジシナリオごとのセンサーカバレッジ（active / muted / circuit-broken / disabled）。結論を出す前に — どのセンサーが実際に寄与したかを確認する。

        
反証証拠現在のシナリオ仮説に反する証拠を提示（デエスカレーション兆候、対立する外交シグナル）。TL の引き上げ判断を出す前に必ず — 確証バイアス対策。

        
シナリオ比較シナリオの横並び比較（TL、トップ寄与、最近の根拠）。同じシグナルが複数のシナリオに当てはまり得るとき — フィットの良い方を選ぶ。

        
ACHHeuer の競合仮説分析。各証拠を各仮説に対して -2 〜 +2 で採点し、診断性で重み付け。帰属・意図が問われる重要評価のとき。お気に入りの仮説だけでなく代替仮説に対しても証拠を量る作業を強制する。

        
少数意見Devil's Advocate ログ：公表された評価に対する反対意見を記録する。コンセンサス判断に反対のとき — 失わないために記録する。

        
前提条件Key Assumptions Check（KAC）。暗黙の前提を顕在化し、要となる前提を lock し、崩れたら invalidate する。シナリオ監視の開始時、および状況が変わった都度。

        
プリモーテムKlein 2007 のプリモーテム：評価が間違っていると仮定して、その理由を列挙。重大度：低 / 中 / 高。高い確信度の評価を発出する前に。

        
決定台帳何が変更されたか（閾値、重み、分類、インテル裁定）を、誰が、どの根拠で行ったかの台帳。監査証跡。タブ session_id 自動付与。

        
What-Ifスライダによる participant 結合重みの調整→再採点。スナップショット再生 — センサー再実行はなし。感度分析：「日本の結合が 0.8 ではなく 0.5 だったら TL は出るか？」

        
        


        
12.3 どの技法をいつ使うか

        
    
            
  • 日常監視 → カバレッジ + 反証証拠。TL を確定する前の安価な習慣的チェック。
    • 
            
  • 異常スパイク → 隠れシグナル（本当に異常か、フロアが変わっただけか？）+ シナリオ比較（別のシナリオの方がフィットするか？）。
    • 
            
  • 重要判断（TL≤2、対外公表評価）→ ACH + プリモーテム + 前提条件 lock。CIA Tradecraft Primer の最低3点セット。
    • 
            
  • チームと意見が割れたとき → 少数意見（記録）+ ACH（その立場を支える行列を提示）。
    • 
            
  • 閾値調整リクエスト → まず What-If（変更で TL は本当に動くか？）+ 決定台帳（何を、なぜ変更したか）。
    • 
        


        
12.4 権限モデル

        
    
            
  • 読み取り：ログイン中の任意のアナリスト。
    • 
            
  • 書き込み（カードの作成・編集・解決、ACH 採点、前提の lock）：analyst または admin ロール。
    • 
            
  • Admin lock：特定の前提は admin が locked マークでき、analyst は invalidate ログは追加できますが行の削除はできません。編集履歴は行ごとの change log に残ります。
    • 
            
  • 決定台帳のエントリは append-only — 削除不可、後続エントリで上書き（supersede）するのみ。
    • 
        


        
12.5 セッション境界

        
このパネルからの全書き込みには session_id が付与されます。セッションはブラウザタブ単位です：新しいタブを開くと新しい UUID が発行され、タブを閉じるとクリアされます（sessionStorage）。同一タブのリロードでは id は維持されます。

        
これにより決定台帳は「1人のアナリストが1セッションで行ったこと」を、同一ユーザーが別タブで並行して行った作業と混同せずグループ化できます。


        
12.6 スコアリングとの関係

        
トレードクラフト面はスコアリングエンジンに対して基本的に読み取り専用です。ライブ TL 出力を変更するタブはありません。例外：

        
    
            
  • What-If はシミュレートされた TL/スコアを返しますが、サイドパネル比較として描画されるのみで、ライブのシナリオ状態には書き戻しません。
    • 
            
  • プリモーテム/前提条件は admin の判断で Admin パネル経由の閾値チューニングに昇格できますが、その経路は明示的かつ監査対象であり、自動ではありません。
    • 
            
  • 隠れシグナル/カバレッジは既存のパイプラインログ（ノイズ除外、mute、サーキットブレーカー状態）から読み出すだけで、それ自体が採点をゲートすることはありません。
    • 
        


        
12.7 決定台帳への自動記録

        
トレードクラフトパネルでの書き込み操作（反証 / ACH / 前提条件 / プリモーテム / 反対意見 ― およびその解決・ロック系の操作）はすべて、決定台帳に detail.auto = true マーカー付きで自動的に追記されます。これにより、台帳はパネル全体の完全な監査証跡となり、各操作を手動でログに残す必要はありません。

        
自動記録された行は決定タイプの隣に auto バッジを表示します。決定タブ上部の 自動記録されたトレードクラフト操作を表示 チェックボックスをオフにすると、手動で入力された決定（閾値変更、重みオーバーライド、インテル操作、レポート発行など）のみが表示されます。決定フォームから直接投稿された手動の台帳エントリには auto マークは付きません。

        
自動記録行は発行元タブと同じ session_id を引き継ぐため、セッションで台帳をフィルタすれば、1人のアナリストが1セッションで行った操作（手動 + 自動）をすべてグループ化できます。


        
方法論的背景: Heuer R.J., Psychology of Intelligence Analysis（1999, ACH 第8章）; CIA Tradecraft Primer（2009, KAC + ACH + プリモーテム）; Klein G., Performing a Project Premortem（HBR 2007）。「Key Assumptions Check」「Devil's Advocacy」の名称はいずれも Primer の SAT 標準の意味で用いています。

        

        


        

        

        
10. フィードバックと感度計測

        
HUD 右下の RECALL チップ（Row 3 右端）は analyst_feedback 台帳から計算されます。ラベル付きの行がゼロの間チップは — のままです。値を点灯させるには 2 通りあります：


        
A. 手動ラベリング（OPSEC コストゼロ、最初の選択肢として推奨）

        
    
            
  1. 結論の drill-down を開く（HUD の脅威レベル数値クリック、または Triage Lane の drill ▶ ボタン）。
    2. 
            
  2. Analyst Feedback セクションまでスクロール。
    3. 
            
  3. 4 つのラベルから 1 つ選択：
                
      
                    
    • TRUE_POSITIVE — 結論が正しく、実際にイベントが発生した。
      • 
                    
    • FALSE_POSITIVE — 結論は発火したが、イベントは発生しなかった。
      • 
                    
    • TRUE_NEGATIVE — 静かな結論が正しく、イベントは無かった。
      • 
                    
    • FALSE_NEGATIVE — 実際のイベントが発生したのにツールが静かなままだった（感度クリティカル）。
      • 
                
    
            
    4. 
            
  4. 必要に応じて検証 URL やメモを添付して送信。
    5. 
        

        
複数シナリオで合計 30〜50 件のラベル付き行があると、RECALL チップは概ね安定した数値を表示し始めます。


        
B. ground-truth ETL による自動ラベリング

        
scripts/run_ground_truth_etl.py が公開情報から結論を自動ラベリングします。ACLED は任意 — ACLED API キー登録（メール+用途を運用組織に紐付ける OPSEC リスクあり）を避けたい場合、ランナーは自動的に GDELT 単独モードへフォールバックします：

        
    
            
  • config.env で V2_GROUND_TRUTH_ETL_ENABLED=true を設定。
    • 
            
  • ACLED_API_KEY / ACLED_API_EMAIL を空のままにすると、警告とともに GDELT 単独モードで動作。--no-acled で警告を抑止可能。
    • 
            
  • ホスト cron またはリモート routine で定期実行: docker exec noroshi python scripts/run_ground_truth_etl.py を 1 時間に 1 回で十分。
    • 
            
  • 自動行は analyst_id="auto:gdelt"（ACLED 有効時は "auto:acled" も）を持ちます。CI baseline は scripts/report_recall_metrics.py --exclude-auto で人手ラベルのみから計算するのが推奨。
    • 
        

        
GDELT 単独で TRUE_POSITIVE / FALSE_POSITIVE / TRUE_NEGATIVE のルールは動作します。感度クリティカルな FALSE_NEGATIVE コーナーの主要な自動ソースは §C の RSS 相関（段階的過小評価検知、API キー不要）です。ACLED はその上に死者数経路を追加します。手動 + 自動の併用でカバレッジ最良。


        
C. RSS / ニュースワイヤー相関 — FALSE_NEGATIVE の供給源 (B1)

        
RSS はツール唯一の大容量な外部（センサー非依存）ground-truth ストリームであり、ツールが自身の盲点を検知できる根拠です。公開 RSS フィードから動態事象の言及を抽出します。抽出器は LLM 無しでも degrade gracefully に動作 — 決定論的なキーワード + 正規表現ベースラインだけで行を生成します。ローカル Ollama が到達可能なら抽出品質を補強できますが、LLM 依存は必須ではありません。RSS 自動行は analyst_id="auto:rss" を持ちます。

        
段階的過小評価検知（2026-05-29 改修）。各動態事象を「本来あるべき最低脅威レベル」にマッピングし（大量死傷 ⇒ TL≥4、武力衝突 ⇒ TL≥3、エスカレーション兆候 ⇒ TL≥2）、そのシナリオの同時刻の THREAT_LEVEL（事象がその forward window に入る結論）と突き合わせます。ツールの TL が本来の下限を下回っていれば FALSE_NEGATIVE、満たすか上回れば TRUE_POSITIVE。これは「国が一致する全結論を無差別に TRUE_POSITIVE と刻印し recall を 1.0 に固定、見逃しを永遠に検知できなかった」旧経路を置換したものです。分類器は意図的に外部証拠のみを用います — ツール自身の内部信号（LLM intel、sequence event）では「ツールが見落としたもの」を明らかにできない（循環論法）からです。


        
F. Calibration status と DRIFT チップ（ground-truth 由来）

        
各結論は calibration_status スナップショットを持ちます（drill-down の Calibration タブで可視）。2026-05-29 以降、これはそのシナリオの ground-truth 混同行列（30 日窓）から計算されます — recall、precision、TP/FP/TN/FN 件数、そして status: INSUFFICIENT_DATA（観測陽性が 5 件未満）、DEGRADED（recall < 0.70 — ツールが明白にエスカレーションを見逃している）、OK。HUD DRIFT チップはこれをシナリオ横断の平均見逃し率 (1 − recall) として集約し（緑 ≤0.05、アンバー ≤0.10、赤 >0.10）、tooltip に最悪シナリオを表示します。

        
これは退役したshadow sampler（lite-vs-full スコア乖離を測定）を置換したものです。Phase-9 のスコア経路統合でこの delta が ≡ 0 になり、旧 DRIFT チップは現実と無関係に全結論で「ドリフトなし / OK」を報告していました（NP5+8 の縮退キャリブレーション失敗）。新しい信号はツールが実際に見逃し始めると動きます。


        
D. Background Observer と OBS チップ — シナリオ別観測健全性

        
「C-lite」機構（focused = 全 sensor、background = LLM intel + global signal のみ）は配線上は正しく動いていますが、実際の信号供給は地理的に偏っています：Taiwan / Korea / South China Sea シナリオは過去 24h で LLM intel ≈0 件、lite-mode スコアは cf_botnet_overlap のような global noise のみで動かされている状態です。

        
これに対する 2 つの surface:

        
    
            
  • OBS チップ（scenario-bar）: 各シナリオカードに OBS N を表示。N は過去 24h の per-country signal イベント数。色バンド: 赤 0 (恒常的盲点 — 設計失敗)、アンバー 1-9 (観測不足)、緑 ≥10 (健全)。tooltip は distinct 国数、最終 signal までの分数、top 寄与国を表示。
    • 
            
  • Background Observer（BG_OBSERVER_ENABLED=true で opt-in）: 非 focus シナリオとその participant 国を round-robin で巡回し、公開 RSS を anonymous HTTP GET でフェッチ（API key 不要、登録不要、LLM 不要）、対象国に scope した正規表現抽出を実行、findings を ephemeral signal として発行し、30 分 TTL 内のすべての scoring tick から可視（保持バッファ、再観測でスライド。2026-07-04 修正）。デフォルト 5 分サイクル。durable record は OBS チップを駆動する scenario_contribution_log 行。
    • 
        

        
有効化: config.env で BG_OBSERVER_ENABLED=true 設定 + 再起動。Asia-Pacific シナリオのカバレッジ向上には BG_OBSERVER_FEEDS を地域ソース（Kyodo News、Korea Herald、Taipei Times 等）で上書き推奨。


        
E. FAULT チップ — silent failure

        
FAULT チップ（Row 3、DRIFT と OBS-BG の間）は監査で特定された silent failure カテゴリの累計件数を表示します。これらは元々 except Exception: pass で耐障害性を理由に例外を握りつぶしていたパスですが、実際は感度優先に違反する signal drop を隠蔽していました。各パスはカテゴリ・タグ付きで失敗を記録するよう修正済で、エンジンが silent に劣化していることがチップで可視化されます。

        
    
            
  • focused_scoring — scoring 外側 except。以前は phantom TL5 行を threat_history に永続化していましたが、現在はレスポンスに scoring_error: true を載せ、履歴は触りません。
    • 
            
  • llm_intel_signals — confirmed LLM intel 信号の tick あたり drop。
    • 
            
  • bg_observer_drain — bg_observer キュー drain 失敗。握り潰された例外は queued signal を永久に失っていました。
    • 
            
  • auto_judge_override_trail — auto-judge 上書き時の台帳 DB write 失敗。
    • 
            
  • attention_collection_errors — attention メトリック収集器の bare-except サイト。1 つの collector を壊す DB スキーマ変更が、ルールを silent に無効化する代わりにカウンタを増やします。
    • 
        

        
チップのバンド（プロセス起動以来の累計）:

        
    
            
  • 緑 0 — silent failure なし。
    • 
            
  • アンバー ≥1 — 1 つ以上のパスで劣化発生。チップにホバーするとカテゴリ別ブレークダウン表示（/api/v2/self_eval.silent_failures.by_category）。
    • 
            
  • 赤 ≥10 — 即調査。持続的な感度優先級失敗はエンジンが自身の出力を信頼できない状態。
    • 
        

        
カウンタはプロセスローカルでコンテナ再起動でリセット。ブレークダウンの last_failure_kind が最新の例外クラスを示すので、コンテナログから該当スタックトレースを grep できます。


        
recall が HUD に届く経路

        
/api/v2/self_eval エンドポイントがラベル付き行を集計し recall = TP / (TP + FN) を計算。窓は per-conclusion の calibration_status と同じ 30 日に統一（2026-07-04 — それ以前は全期間集計で、同じ「recall」の名で別の数値だった）。recall_meta が window_days と labels_auto / labels_human の内訳を返す: labels_human = 0 のとき recall は auto-label ETL による完全な自己採点であり、独立した検証点を持たない。HUD チップは 5 分ごとにポーリング：

        
    
            
  • recall ≥ 0.80 で緑（calibration 目標内）
    • 
            
  • 0.60 ≤ recall < 0.80 でアンバー（ドリフト形成中）
    • 
            
  • recall < 0.60 で赤（感度退行 — 即調査）
    • 
            
  • ラベルゼロの間は —（赤ではなく中立の灰色）
    • 
        

        
同じ分子/分母が CI ベースライン ゲート（scripts/check_recall_baseline.py）も駆動するため、チップとゲートが食い違うことはありません。

        

        

        

        

        
11. シナリオと設定

        
ツールバーの Config ボタンからマスター設定モーダルを開く。6つのタブで構成される。

        
    
            
  • センサー: 個別センサーを有効/無効切替。無効化されたセンサーのドメインスコア貢献はゼロ（グレースフルデグラデーション）。センサーは Cyber / Physical / Information の各ドメインに加え、ノイズ抑制器と 1 つのバックグラウンド対象センサーで構成される。
    • 
            
  • フェッチログ: 各センサーの最終フェッチ結果（成功 / 失敗 / キャッシュ経過時間）を表示。ポーリング間隔の3倍より古いキャッシュは STALE としてフラグ。
    • 
            
  • 上流ソース（analyst 以上）: 複数のフィードを集約するセンサーについて、上流ソース単位の稼働状況を表示。現時点では CT Log の3ソース — certstream（push、Calidog 上流が 2026-04-23 時点で停止しているため既定で無効）、certspotter（pull）、crt.sh（フォールバック）— を表示する。ソース別の最終メッセージ経過時間、モード別カウンタ（untrusted-CA / wildcard-at-gov-TLD などの失敗モードを含む）、監視 apex カバレッジ（24h / 72h）、最古の監視 apex 上位10件を表示。センサー全体のフェッチログから推測することなく「実際のデータフィードが生きているか」を直接確認できる。
    • 
            
  • フリート稼働（analyst 以上）: HUD のセンサードットが要約しているフリート全体の状態を、センサー毎に詳細表示。ヘルス（OK/DEGRADED/STALE/ERROR/CIRCUIT_OPEN）、サーキットブレーカ状態（closed/half_open/open）と失敗カウント、キャッシュ齢、選択窓（1h/24h/7d）における信頼性（成功率・総フェッチ数・平均応答時間）、ポーリング間隔、最終エラーメッセージを表示。ドメインフィルタ（cyber/physical/info）でセンサー群を絞り込み可能。upstream_health() を公開しているセンサー（現状 CT Log）は上流ソース別ドットも併記。/api/admin/sensor_health エンドポイントを直接的に可視化する。
    • 
            
  • System（admin のみ）: config.env を編集 — サーバー Listen ホスト/ポート、API キー、LLM/Ollama 設定、インテルキュー閾値、通知 Webhook、キャッシュ & ポーリング間隔、脅威スコアリング閾値、DDoS アクセラレーションパラメータ、JWT 認証、プラグインセンサー。Default Focus 欄は起動時に focused になるシナリオを指定（既定は taiwan_contingency）。
    • 
            
  • ユーザー: オペレータアカウントの管理。ロールは admin（完全アクセス）/ analyst（運用アクセス）/ viewer（閲覧のみ）。管理者発行の一時トークンによるパスワードリセットに対応。
    • 
            
  • Scenarios（admin のみ）: 紛争シナリオの作成 / 編集 / アーカイブ / 復元 / 完全削除。各シナリオは独自の participants（役割と結合重み 0.0–1.0 を持つ国）と core_country（任意のフォーカス基準）を定義。常に1つのシナリオだけが focused、他の有効なシナリオは C-lite バックグラウンドモードで採点される（LLM インテル + グローバル信号のみ、per-country センサーは走らない）。シナリオ HUD は §4、シナリオの状態機械については §13 を参照。
    •

11.x v3 影画面の SETTINGS（3 段テストを通過したキーのみ）

        
v3 の設定画面には「読まれることが検証されたキー」しか出ない。本番の設定 registry は 98 キーを並べていたが、うち 95 キーは DB override 層に届いておらず、画面は送った値をそのまま表示していたため、誰も読まない値を変更し続けられた（G-15）。v3 はこれを構造で禁じる。

        
    
            
  • 3 段テスト（tests/test_config_registry.py、CI ゲート）: (1) 宣言された読み手（module:callable）が実在しインポートできる、(2) 読み手の関数本体を AST 走査してキー名の文字列が現れる、(3) override を入れると読み手の出力が実際に変わる。通過するのは現在 9 キーで、すべて読み手は v3.scoring.settings:resolve_settings。画面はこの件数と、対する固定定数の件数（R10 が開示）を常に併記する。少ないことは欠落ではなく事実である。
    • 
            
  • 3 層解決: override（command_record 台帳の fold）→ env → default。どの層が勝ったかは行ごとにバッジで出る。専用の override テーブルは作らない（誰が・いつ・なぜ・前は何だったかはすべて指令台帳の列で答えられる）。
    • 
            
  • バッジは 4 系統だが、すべてサーバの申告に由来する: 出所（override/env/default）・env 層の有無・読み手・可変性。v1 の TIMING / IMPACT バッジは出さない — R14 がどちらも申告しておらず、ブラウザで算出したバッジはバックエンドがしていない主張になるため。IMPACT の唯一の機構的役割（高影響キーに理由を強制する）は、v3 がすべての設定変更に理由を必須としている（requires_reason=True）ことで、より強く満たされている。
    • 
            
  • 差分確認 → 理由入力 → 送信 → 読み戻し: 差分が無ければ送信せず「変更なし」と返す。保存後に表示するのはサーバが 3 層チェーンで再解決した値（effect）であり、送った値ではない。台帳には記録されたが実効値が動かなかった場合はそのことを明示する — その組み合わせが G-15 の指紋そのものだからである。
    • 
            
  • 同じ画面に ground truth 一覧（読み取り専用）が同居する。抑制規則（noise exclusion）の面は指令 API (C8) が未実装のため、未実装であることを明示して置いていない。

  • GET /api/v3/scenarios — [v3 R1] シナリオ台帳 + focus + TL サマリ。各行は scenario_id / display_name_ja / display_name_source / participants / adversaries / roles / chain_country / threat_level / threat_level_24h_ago / severity_delta_24h / score / scoring_mode / in_null_zone / never_observed。display_name_ja は geo_data.json のシナリオ定義から供給され、宣言が無い場合は scenario_id にフォールバックする（display_name_source が display_name_ja | name_ja | scenario_id のどれで解決したかを開示するので、「宣言された名前がたまたま id と同じ」と「名前が宣言されていない」を取り違えない）。envelope はさらに board_summary{text, template_ref, inputs} を持つ — 状況ビュー冒頭の日本語 1〜2 文（P9 §5 / R-A）で、LLM ではなく決定論テンプレート（P7 §4 の同一エンジン）で合成される。inputs は 24 時間の変化数（変化 / 変化なし / 比較不能の 3 分類）、最優先の注目対象（R6 と同一射影から）、AP3 自己評価バンド（R7 と同一 ops fold から）を根拠付きで開示し、供給できなかった構成要素は inputs.unsupplied に名前で残る（黙って落とすと「注目対象なし」と読めるため）。テンプレート本体は同 envelope の board_summary_templates が id・version・slot 付きで開示する（NP6）。結論が 1 件も無い配備は board.summary.cold 側の文になり、「変化 0 件」とは言わない。
    • 
            
  • GET /api/v3/scenarios/<scenario_id>/evidence?window=&domain=&sensor=&at= — [v3 R5] 兆候マトリクスと個別異常事象。行は sensor / signal_source / domain / country / status / raw_score / confidence / observed_at / suppressed / suppress_reason / evidence_url / flags。抑制済み行は理由付きで返る（E-17: 「発火して除外」と「発火せず」を同じ OK に潰さない）。v3 画面の地理面の唯一の供給源。座標は含まれない（Ch.3 の v3 節を参照）。
    • 
            
  • GET /api/v3/config — [v3 R14] 運用可変キーのみ。キーごとに value / source（override|env|default）/ unit / default / why / consumer / override{value,actor_id,reason,at} / env_present、加えて variable_keys / layers / environment_layer_keys / pinned_note。固定定数は R10 が開示する。
    • 
            
  • POST /api/v3/config/<key> — [v3 C7s] ボディ {"value": ..., "reason": "..."}。reason は必須。応答の effect.config は追記後に同じ 3 層チェーンで読み戻した値であり、送信値のエコーではない。changed が false なら「台帳に載ったが実効値は動いていない」。固定キー・未知キー・単位違反は 400。
    • 
            
  • DELETE /api/v3/config/<key> — [v3 C7d] override の解除。削除ではなく追記で、誰がいつ既定へ戻したかが判断台帳に残る（AP4）。reason 必須。
    • 
            
  • GET /api/v3/ground_truth?scenario_id= — [v3 C9g] {scenario_id: [行]} 形式。C9p（教師信号の投稿）の効果が実在する先。設定画面に読み取り専用で同居。
    • 
            
  • GET /api/v3/app_config — [v3 R15c] 配備の自己申告。mode / authoritative / ledger / tick_interval_sec / scenario_ids / adapters_enabled / session_surface、および websocket{mounted, reason, unpublished}。ライブチップはこれを読んでから接続する（未マウントなら一切ダイヤルせず、「切断」ではなく「未マウント」と表示する）。

WebSocket 面: v3 の発行語彙は conclusion_update / attention_update / sensor_status の 3 つ（notification_result は発行者が存在しないため構築自体が拒否される）。購読は subscribe_scenario / unsubscribe_scenario でシナリオ単位。push は envelope ではない（NP7 注意文も鮮度スタンプも持たない）ため、v3 クライアントは push を表示値としてマージせず、該当射影の再取得の合図として扱う。廃止済イベント名（threat_update 等）の受信はサーバ側の版ずれとして報告し、黙って捨てない。

13.1 ユーザー管理 — TOOLS ▾ → User Management

        
    
            
  • 認証: JWT ベースのログイン。アクセストークン（デフォルト: 1時間有効）とリフレッシュトークン（24時間）を使用。初回起動時に DEFAULT_ADMIN_PASSWORD（デフォルト: "admin"）で admin ユーザーが自動作成される。本番環境では即時変更すること。

  • ユーザー管理パネル: admin 認証情報でログイン → 全ユーザーのロール/作成日/最終ログインを表示。インラインのロール選択で即時変更。PW ボタンでパスワードリセット。DEL ボタンでユーザー削除（確認ダイアログ付き）。安全のため自分自身の削除とロール変更はブロック。
    • 
            
  • ユーザー別設定: 各ユーザーは独自の国設定（コア、ピン、相関国、敵対者、ミュートセンサー、言語）を PUT /api/auth/settings で保存可能。

13.2 シナリオマネージャー — Config → Scenarios タブ（Admin のみ）

        
    
            
  • シナリオアーキテクチャ: Noroshi は国単位ではなくシナリオ単位（例: 「台湾有事」）で脅威をスコアリング。各シナリオは参加国（participants）をカップリングウェイト（0.0–1.0）とロール（primary_target、adversary、primary_ally 等）で定義。
    • 
            
  • 3層設計: Layer 1 = geo_data.json のプリセット（読み取り専用）。Layer 2 = SQLite に保存された管理者カスタマイズ（プリセットを上書き）。Layer 3 = セッションオーバーライド（下記 H 参照）。
    • 
            
  • 作成: 一意の ID（小文字、3–30文字）、日英バイリンガル名、コア国、参加国テーブルを指定してカスタムシナリオを新規作成。
    • 
            
  • 編集: 名前、説明、コア国、参加国のウェイト/ロールを変更可能。変更は Layer 2（DB）に書き込まれ、元のプリセットは保持。
    • 
            
  • 状態管理: Active → Paused → Archived のライフサイクル。スコアリング対象は active かつ enabled のシナリオのみ。Paused シナリオはデータを保持するがスコアに寄与しない。
    • 
            
  • リセット: プリセットベースのシナリオについて、Layer 2 のすべてのオーバーライドを削除し、geo_data.json のデフォルトに復帰。
    • 
            
  • パージ: カスタム（DB のみ）シナリオと関連データを完全削除。確認ダイアログが必要。
    • 
            
  • 変更ログ: すべての変更は scenario_change_log にタイムスタンプと差分とともに記録。
    • 
        


        
13.3 Layer 3 セッションオーバーライド — シナリオ詳細パネル → 「重み調整」ボタン（Analyst および Admin のみ）

        
    
            
  • 目的: 仮説検証用のセッション限定な参加国重み上書き。「もし日本のカップリングが 0.5 ではなく 0.8 だったら？」という問いを、Layer 2（DB）や Layer 1（geo_data.json）に触れずに試せる。
    • 
            
  • スコープ: 現在フォーカス中のシナリオのみに適用。バックグラウンドシナリオは常に保存済みの（Layer 1 + Layer 2）重みを使用。
    • 
            
  • 永続化: sessionStorage に保存 — タブを閉じるとクリア。スコアリングモデルの意図しない長期的バイアスを防ぐため意図的に非永続化されている。

13.4 LITE / MEDIUM モード評価 — Config → Scenarios タブ → 「C-lite評価を読み込む」ボタン

        
    
            
  • 目的: 現在の C-lite モード（フォーカスシナリオ＝全センサー、バックグラウンド＝LLM + グローバルのみ）が適切か、C-medium（バックグラウンドシナリオも低頻度で国別センサーデータを受信）へのアップグレードを検討すべきかを判定。
    • 
            
  • データソース: 設定可能な期間（デフォルト28日間）の focus_switch_log エントリを集約。各フォーカス切替は旧/新シナリオID、切替時のTL、スコアデルタを記録。
    • 
            
  • 主要メトリクス:
                
      
                    
    • 切替回数: 評価期間中の総フォーカス切替回数。
      • 
                    
    • ミス: バックグラウンドシナリオのスコアがアナリストが気づいて切り替える前に大幅に上昇していた（デルタ＞閾値）切替 — LITE モードでのエスカレーション見逃しを示す。

      •

      • 
                
    
            
    •

    • LITE_SUFFICIENT — ミス率 ≤ 15%。バックグラウンドシナリオはLLM + グローバル信号で十分にカバー。
      • 
                    
    • CONSIDER_C_MEDIUM — ミス率 > 15%。バックグラウンドシナリオに重大なブラインドスポットあり。より包括的なカバレッジのためC-mediumへのアップグレードを検討。
      • 
                    
    • INSUFFICIENT_DATA — フォーカス切替記録が3回未満。結論を出すにはデータ不足。
      • 
                
    
            
    • 
            
  • シナリオ別内訳: フォーカス切替の対象となった各シナリオの切替回数、ミス、平均Δを表示するテーブル。LITEモードの制約により最も影響を受けているシナリオを特定。

13.7 Falsification 説明 — 「現結論を変える条件」narrative

        
    
            
  • 目的: 透明性の拡張。THREAT_LEVEL の conclusion に metadata.falsification ブロックが付与され、narrative が「What would change this:」セクションで描画。既存の rationale_matrix + 閾値ラダー上の純粋算術であり、LLM 不使用 / 学習重み不使用 / scenario 個別チューニング不使用。
    • 
            
  • 閾値距離: 隣接 TL rung までの距離を双方向で提示。重大化方向 (低 TL 番号): "Rise to TL2 if score ≥ 6.0 (currently 4.5, gap +1.5) AND active domains ≥ 2 (currently 1, gap +1)". 緩和方向 (高 TL 番号): "Drop to TL4 if score < 4.0 (currently 4.5, margin 0.5)".
    • 
            
  • シグナル sensitivity: 寄与上位 3 シグナルを 0 化したケースをシミュレート、仮想 TL を報告。"If ct_log (cyber contrib 1.4) drops to 0, TL would fall to TL4"。suppressed と GLOBAL 行は除外し、actionable な per-country 寄与のみ surface。
    • 
            
  • 境界ケース: 最重要 rung では "Already at TL1 (no higher severity defined)"、TL5 では "Drop to..." 行なし。INSUFFICIENT_DATA はセクション全体省略 (metadata.falsification が空)。
    •

13.8 自動キャリブレーション・ティアガバナー — HUD AUTO-CAL chip / SETTINGS Operate > Auto-Calibration / /api/v2/calibration/tier_governor

        
    
            
  • 目的: per-proposal の安全規則の上に乗る自己昇格的な信頼レイヤー。「自動 apply 機構全体としてどこまで信用できる段階に達しているか」をシステム自身が観測ベースで判定し調整する。Tier 0（proposal-only — 提案は記録するが apply はしない）から始まり、持続的な安定指標が満たされたときだけ Tier 3（LOW/MED/HIGH 全面 auto-apply）へと自動的に昇格する。
    • 
            
  • Tier モデル:
                
      
                    
    • T0 — proposal-only: すべての calibration は ledger に書かれるが downstream consumer は無視。auto-feedback 行が 100 以上で T1 へ昇格。
      • 
                    
    • T1 — LOW: シナリオ単位 tl_thresholds.* の auto-apply。T1 で 7 日以上滞在しかつ revert_rate_7d ≤ 5% なら T2 へ昇格。
      • 
                    
    • T2 — LOW + MED: センサー単位の LLM confidence floor も追加。14 日以上の滞在に加え diff_log_match_rate ≥ 0.99 と revert_rate_14d ≤ 5% を満たすと T3 へ昇格。
      • 
                    
    • T3 — FULL: HIGH-impact キー（domain weight、hysteresis、convergence）も auto-apply の対象。ただし HIGH 1 件 commit のたびに LOW/MED は 24h cool-down がかかり、未検証の HIGH の上に下位の連鎖変更が積み重ならないようにする。
      • 
                
    
            
    • 
            
  • 3 つの常時稼働セーフティネット:
                
      
                    
    • Kill switch: 環境変数 AUTO_CALIBRATION_TIER_CAP で天井を制限。0 にすればシステム全体の auto-apply を停止できる（ガバナー自体は観測を継続）。
      • 
                    
    • サーキットブレーカー: ガバナー評価が 3 回連続で失敗するとメトリクス如何にかかわらず Tier 0 に強制降格。失敗マーカーは ledger に記録される。
      • 
                    
    • HIGH cool-down: T3 で HIGH-impact 書き込みが成功するたび、LOW と MED の auto-apply を AUTO_APPLY_HIGH_COOLDOWN_HOURS（既定 24h）一時停止。
      • 
                
    
            
    • 
            
  • Tier 滞在時刻マーカー（Phase 2 ハードニング）: 現在 tier の滞在時間は audit ledger が誤って truncate されても保持される。別テーブルの 1 行スカラーとして保管し、operator の DB クリーンアップやテストの初期化対象から外れている。ledger が空になった場合、次の参照時に metrics.recovery=true を付けた recovery init 行が自動で書き戻され、追跡可能性は維持される。
    • 
            
  • 観測サーフェス（Phase 3 ハードニング）:
                
      
                    
    • HUD AUTO-CAL chip: Row 3 self-eval 行。ラベルは T{n}（接尾辞は次昇格条件全達成で ↑、kill switch 発動で !、連続失敗中で …）。tooltip にライブの昇格ゲート（各ゲートの ✓/✗）、有効な cooldown、直近の transition を表示。クリックでこの SETTINGS ページを開く。
      • 
                    
    • SETTINGS Operate > Auto-Calibration: 設定キーの上にライブステータスブロックを表示。現在 tier バッジ + raw / cap、滞在時間、昇格ゲートのチェックリスト、有効な cooldown、直近 5 件の transition。
      • 
                    
    • エンドポイント: GET /api/v2/calibration/tier_governor（analyst 以上）。HUD chip と SETTINGS ブロックが共有する単一の読み取り専用スナップショット。
      • 
                
    
            
    • 
            
  • 監査証跡: tier の遷移（init / promote / demote / circuit_breaker / kill_switch_engaged）はすべて auto_apply_tier_state に行追加され、判定根拠の metrics_json も保存される。エンドポイントは直近 10 件を露出し、それより古い履歴は管理者が直接 DB を参照する形（SQL 監査）でアクセスできる。
    • 
        


        
13.9 恒常的結論不可検知 — HUD CHRONIC chip / /api/v2/observability/chronic_inconclusive

        
    
            
  • 契約: CLAUDE.md は「過渡的結論不可は許容、データ蓄積後の恒常的結論不可は設計失敗」と明記している。本検知器がこの契約を直接強制する: (シナリオ, conclusion_type) ペアの UNAVAILABLE 開始から CHRONIC_INCONCLUSIVE_THRESHOLD_DAYS（既定 7d、最小 3d）を超過したものを chronic として flag する。
    • 
            
  • duty-cycle 判定 (2026-07-04): 連続 run 方式はフラッピングに盲目（例: attack_mode が数ヶ月間 tick の 20-30% で UNAVAILABLE なのに、各 run は数時間で閉じるため chronic_count は 0 のまま）。第 2 の判定として rolling window 内の不可時間を合算: duty_cycle = unavailable_sec / window_sec が CHRONIC_DUTY_THRESHOLD（既定 0.20、最小 0.05）以上（窓は CHRONIC_DUTY_WINDOW_DAYS、既定 14d、最小 7d）なら chronic。レスポンスに duty セクションが追加され、マージ後の chronic エントリは criterion: "duty_cycle" | "consecutive_days" を持つ。
    • 
            
  • データソース: inconclusive_continuity_log — 結論保存ごとに _record_continuity が記録（open / extend / close の遷移イベント）。検知器はペアごとに最新行を取り、is_available=0 なら「first_seen_at から不可状態が継続中」と解釈する。
    • 
            
  • 日次 scheduler hook: _cycle % 24 == 9 でスナップショットを取り、chronic 1 件ごとに record_failure("inconclusive_chronic", ...) を発火。重要な点は、inconclusive_chronic は FAULT chip の感度優先カテゴリ集合には含めないこと — 恒常的結論不可専用サーフェス（CHRONIC chip）として独立に表示する。
    • 
            
  • HUD CHRONIC chip: row 3、AUTO-CAL の隣。ラベルは chronic 件数。バンド: 0 → 緑、1-2 → 琥珀、≥3 → 赤。tooltip に上位 5 件の offending ペアと滞在日数を表示。クリックで Operate > Auto-Calibration SETTINGS を開く（閾値ノブの所在）。
    • 
            
  • チューニング: 閾値を下げるのは false-positive 率を 30 日以上観察した後のみ。3d 未満には決して下げない（routine sensor outages が支配的になる）。CHRONIC が正当に発火した場合、答えはほぼ「閾値を上げる」ではなく「上流 sensor を直す」または「設計上の限界として記録する」。
    •

14.3 データベースバックエンド（SQLite）

    • 
            
  • マイグレーション後の初回起動時に、既存の state.json データが自動的に SQLite にマイグレーションされ、JSON ファイルはバックアップとして state.json.migrated にリネーム。

14.4 センサーヘルス & レート制限

        
    
            
  • ヘルス状態: 各センサーは5つの状態のいずれかを報告: OK（緑）、STALE（橙 — ポーリング間隔の3倍以上データ更新なし）、ERROR（赤 — 最終フェッチ失敗）、INITIALIZING（灰 — 初回データ未取得）、DISABLED（灰 — 手動ミュート中）。HUD の SENSORS インジケーターはセンサーごとに状態色のドットを表示。
    • 
            
  • エラー伝搬: センサーフェッチが失敗した場合（HTTP エラー、タイムアウト等）、エラーは即座にヘルス状態に反映。log_fetch() の失敗呼び出しは、特定のエラーメッセージがなくても自動的にセンサーを ERROR に設定。成功したフェッチはエラー状態をクリア。
    • 
            
  • OpenSky レート制限: 3つのセンサー（OpenSky 空域、ISR ホットスポット、軍事支援航空機）は OpenSky Network API を共有。共有レートリミッターが API コール間に最低10秒の間隔を強制。起動時にセンサーは段階的に起動（0秒、+120秒、+240秒）し、429 レート制限の連鎖を防止。429 レスポンスを受信した場合、Retry-After 期間待機後に1回リトライ。
    • 
            
  • 成功時のみキャッシュ: センサーは少なくとも1つの成功レスポンスを受信した場合のみキャッシュを更新。完全な失敗時は前回のキャッシュデータを返し、一時的な障害中のデータ損失を防止。
    • 
        


        
14.5 オートチューニング Wizard — TOOLS ▾ → Auto-tune Wizard

        
    
            
  • 目的: tier governor + 証拠強度ゲートで自動適用されなかった提案、または組織判断境界外（後述）の提案を、アナリストが 1 画面で apply / dismiss / defer する残余キューのレビュー画面。
    • 
            
  • 自動適用統合: scenario_improver / scenario_structure_proposer の発出は tier governor でゲートされる。ゲートを通過した提案はそのまま state='applied' へ遷移し、Wizard には現れない。
                
      
                    
    • Recall+（weight_too_low / missing_participant）— Tier 1+ で weak/moderate 証拠で自動適用（recall 改善を保留すること自体が recall 削減）。
      • 
                    
    • Recall-（weight_too_high / dormant_participant）— Tier 3 で strong 証拠 AND 非保護ロール AND vitality=active のときのみ自動適用。適用後 24h HIGH cool-down で LOW/MED 自動適用を停止する。弱い証拠の場合は Wizard でアナリスト判断（確認モーダル経由）。
      • 
                    
    • Structure（role_reclassify）— 非保護ロール対象なら Tier 2+ で strong 証拠で自動適用。保護ロールはアナリスト専用。
      • 
                    
    • Discovery（scenario_discovery）— 絶対に自動適用しない。シナリオライフサイクル（どの紛争を追跡するか）はキャリブレータの判断ではなく組織の判断。
      • 
                    
    • Diagnostic（sensor_gap_detected / scenario_dormant / needs_more_data）— 情報提示のみ。7 日経過で日次 scheduler hook が自動 ack（state='dismissed', state_changed_by='auto:diagnostic_acknowledged'）するので Wizard の pending リストが自動で片付く。過渡的「結論不可」はアナリスト確認のため記録は残る。
      • 
                    
    • Sensor Disable: 24h ack 待ちの α-broken センサー無効化提案（tier governor シームとは独立、Phase D pipeline 管轄）。
      • 
                    
    • Drift Signals: dwell-time（≥3 連続検出）を満たした F3 ドリフトイベント。amber/red 重要度で色分け。
      • 
                
    
            
    • 
            
  • マスターフラグ: SCENARIO_IMPROVER_AUTO_APPLY_ENABLED（tier governor の T1+ 安定が観察できるまでデフォルト false）。false の間は全ての提案が state='pending' のままで、Wizard が唯一の apply 経路となり従来挙動が維持される。
    • 
            
  • 確認モーダル: 自動適用されなかった recall 削減提案（証拠が strong 未満、保護ロール対象、フラグ OFF 状態など）にアナリストパスで対応する際に使用。確認モーダル（autotune-confirm-modal）が rationale と evidence を再表示し、「Confirm Apply」を押すまで適用は確定しない。
    • 
            
  • 透明性: 全行に formula_ref、sample_n、構造化された evidence_json が表示される。再現可能性の保証。
    • 
            
  • API エンドポイント: GET /api/v2/proposals/{scenario_improver,sensor_disable}、GET /api/v2/drift_signals、GET /api/v2/discovery/clusters、POST /api/v2/proposals/scenario_improver/<id>/{apply,dismiss,defer}、POST /api/v2/proposals/sensor_disable/<id>/ack、POST /api/v2/drift_signals/<id>/ack。
    • 
            
  • 監査: 全 apply 操作は scenario_proposals.state_changed_by に admin:<username> として記録。GET /api/v2/threshold_history/<id>/lineage で derivation chain を遡及可能。
    • 
            
  • Discovery タブの注意: G.3b LLM 注釈は G3B_SHADOW_ENABLED=true（観察期間）→ G3B_LLM_ENABLED=true（本番）の段階移行を経て初めて UI に出る。デフォルトは両方 false（ハルシネーション防止のため安全側デフォルト）。confidence_self_reported < 0.5 の注釈は灰色化される。
    • 
            
  • 手動トリガー: 管理者は POST /api/v2/calibration/run_now?phase=<name> で個別フェーズを即座に実行可能（phase ∈ {tl, llm_conf, sensor_disable, scenario, structure, discovery, g3b, drift, all}）。

14.6 LLM Feature Hub — TOOLS ▾ → LLM Features (または HUD の LLM chip)

        
    
            
  • 目的: LLM 駆動の全機能を 1 か所で管理する制御面。これまで 8 つ以上の独立した env フラグで分散制御されていたものを、レジストリ + 実行時 override + 監査履歴 + グローバル kill switch に統合。Docker 再起動なしに切替可能。
    • 
            
  • 4 階層構造:
                
      
                    
    • Tier 0 — Core: 根幹機能（センサー LLM intel 抽出）。停止すると新規 intel 流入が止まる。kill switch でのみ操作。
      • 
                    
    • Tier 1 — Decision-Augmenting: auto-judge LLM 再判定、attack-mode 拡張。決定論的判断を補強。admin のみ。
      • 
                    
    • Tier 2 — Narrative: triage 自然言語表示。表示のみで判断には影響しない。analyst でも切替可能。
      • 
                    
    • Tier 3 — Discovery: G.3b クラスタ注釈。構造提案 — admin のみ + 追加確認モーダル。
      • 
                
    
            
    • 
            
  • 状態解決の優先順位（高い順）:
                
      
                    
    1. グローバル kill switch（env LLM_FEATURE_KILL_SWITCH または DB 行）→ 全 feature OFF。
      2. 
                    
    2. 機能別 DB override（Hub UI / API で設定）。
      3. 
                    
    3. env_var / shadow_env_var（既存 config.env 値）。
      4. 
                    
    4. LLM features registry のデフォルト。
      5. 
                
    
            
    • 
            
  • 状態値:
                
      
                    
    • OFF: 機能停止。
      • 
                    
    • SHADOW: 動作するが apply しない（ledger に記録のみ）。supports_shadow=True の機能のみ選択可。
      • 
                    
    • ON: フル稼働。
      • 
                    
    • auto: UI override をクリアし env+default に戻す。Auto (revert) ボタンを使用。
      • 
                
    
            
    • 
            
  • 構造変更確認: 構造影響機能（現状 g3b_cluster_annotator）を ON / SHADOW に切替時、確認ダイアログ + 理由入力を要求。理由は監査履歴に記録される。
    • 
            
  • Kill switch: admin のみ。engage で次回 is_enabled() 呼び出し時に Core 含む全機能 OFF。新規 intel 流入が止まる。緊急時のみ使用（ハルシネーション連鎖の疑い、LLM エンドポイント侵害等）。
    • 
            
  • 監査: 全状態変更で old_state / new_state / 実行者（admin:<name> / analyst:<name>）/ 任意理由を記録。Hub の History トグル または GET /api/v2/llm_features/audit?hours=720&limit=200 で確認。
    • 
            
  • API: GET /api/v2/llm_features、GET /api/v2/llm_features/<key>、POST /api/v2/llm_features/<key>/{set,clear}、POST /api/v2/llm_features/kill_switch、GET /api/v2/llm_features/audit。
    • 
            
  • HUD chip: Row 3 右側に LLM N/M（N 個 on / 計 M 個）形式で表示。shadow 件数は +Ks として末尾追加。色: 緑=全 on、橙=shadow あり、赤=kill switch engaged。クリックで Hub を開く。
    • 
        


        
14.7 LLM モデルルーティング v10 — HUD MODEL chip / /api/v2/llm_routing

        
    
            
  • 目的: 2026-05 LLM サーベイ v10 により、単一 LLM_MODEL 環境変数を use_case ベースの 5 モデルルーティングに置換: mistral-small3.2:24b（sensor 主、verdict 副）、gemma4:26b（sensor 副、verdict 主、narrative）、gemma4:31b（conclusion + ETL/discovery）、gpt-oss-safeguard:20b（ETL on-demand 2nd opinion）、granite-embedding:278m（dedupe）。

      • 
                    
    • model_routing_etl
      • 
                    
    • model_routing_conclusion — 最後（回帰インパクト最大）

  • HUD MODEL chip: Row 3 に MODEL N/M（N 個取得済 / M 個必要）形式で表示。緑=全取得済、橙=1 個以上未取得、赤=Ollama 不通、"OFF"=Ollama down。クリックでルーティングモーダルを開き、(use_case, slot) ごとの解決モデル / サンプリング / Feature Hub state を一覧表示。
    • 
            
  • Preflight: GET /api/v2/llm_preflight は Ollama ≥ 0.22.0（サーベイ v10 が要求する MLX runtime + FA-fix の前提）かつ全 PRIMARY モデルが pull 済の時のみ go_no_go = true を返す。routing feature を ON に promote する前にこれで確認。

  • thinking trace: 解決モデルが thinking_enabled=true（gemma4:31b の <|think|> token、gpt-oss-safeguard の "Reasoning: high"）の時、reasoning テキストを llm_call_log.thinking_trace に記録（監査用）。

14.9 CONTROLS Tools Hub — ハンバーガーメニュー → CONTROLS パネル（Tools Hub をパネル内に埋込み）

        
    
            
  • 目的: 旧来の 3 段階フロー（ハンバーガー → CONTROLS → TOOLS ドロップダウン）を CONTROLS パネル内のカードレイアウトに統合。各カードが panel 状態（開/閉、ドック位置）と動的データバッジ（pending 件数、センサー健全性、エラー状態）を表示。ATTENTION ルールにより「次に注目すべきツール」を自動上位表示。
    • 
            
  • 埋込み式の理由: 脅威インテリジェンスアナリストはツール状態確認中も地図 + シナリオバー + アラートレーンを視認する必要がある。モーダルだと隠れてしまうので、CONTROLS 内に埋込みで地図を遮らない設計。
    • 
            
  • 明示ボタン（クリックトグルではない）: 各カードに独立した [Open] / [Close] ボタン。現在状態のボタンが塗り（open は緑、close はグレー）で表示される。状態と操作意図が同位置で可視化され、緊張時の誤操作を防止。
    • 
            
  • DOCK 操作ボタン: dockable パネルには 3 つの追加ボタン:
                
      
                    
    • ⇄L — 左サイドバーへドック
      • 
                    
    • ⇄R — 右サイドバーへドック
      • 
                    
    • ⤢ — 浮動ウィンドウとして切り離し
      • 
                
    
                現在のドック位置のボタンが塗り（cyan）。従来の「ドラッグでドック」のみだった動作を明示ボタン化。
            
    • 
            
  • アコーディオン: 非アクティブセクションは折り畳まれてパネルがコンパクトに保たれる。ATTENTION + Suggestions は 常時展開、INTELLIGENCE はデフォルト展開、他のセクションはデフォルト折り畳み。各 analyst の展開/折り畳み状態は localStorage.cp_section_open に永続化、ブラウザセッション再開で復元。
    • 
            
  • 検索: 上部の検索ボックスでツール名 + 説明文を部分一致フィルタ。クエリ中は折り畳みセクションも自動展開してマッチ結果を表示。/ でフォーカス、Esc で CONTROLS を閉じる。
    • 
            
  • 意図ベース 6 区分:
                
      
                    
    • INTELLIGENCE: LLM Intelligence / Attack Origin / Telegram SIGINT / Evidence Chain / GreyNoise
      • 
                    
    • SCENARIO & TARGETING: Target Visibility / Strategic Climate / Weather Brief
      • 
                    
    • SIMULATION & ANALYSIS: What-If / SPOF / Sensor Heatmap
      • 
                    
    • TRADECRAFT: Analyst Tradecraft / Sensor Watchpane / History Analysis
      • 
                    
    • AUTOMATION: Auto-tune Wizard / LLM Features（analyst でも切替可能、ADMIN gate なし）
      • 
                    
    • ADMIN: ユーザ管理
      • 
                
    
            
    • 
            
  • ATTENTION セクション: ルールエンジンが 12 条件を 5 秒ごとに評価し重要度（CRITICAL > WARNING > INFO）でランク付け。CRITICAL 例: recall 低下提案 pending、kill switch engaged、センサー ERROR。各 ATTENTION カードは現在値・閾値・人間可読の理由を表示。
    • 
            
  • ヒステリシス: 各ルールに enter/exit 閾値を別設定。値が enter 以上で発火、exit 未満で解消。境界付近の振動で UI が点滅するのを防止。
    • 
            
  • Snooze: WARNING / INFO ルールは 24h スヌーズ可能（カードのボタンから）。CRITICAL ルールはスヌーズ不可（recall 影響イベントは非可視化禁止）。スヌーズはブラウザ再読込後も attention_snooze テーブルで保持。
    • 
            
  • 適応学習: 5 分毎の poll tick で metric 値を attention_metric_observation に記録。夜間 cron で 30 日 window の p50/p95/p99 を計算し attention_metric_p95 に保存。analyst のパターンが固定デフォルトから ≥30% 乖離したら、Suggestions セクションで p95 × 1.20 を推奨閾値として提示。bootstrap mode（sample_count < 30）は suggestion 抑制でノイズ防止。
    • 
            
  • Per-user 閾値: 各 analyst が任意ルールの enter 閾値を PUT /api/v2/attention/thresholds/<rule_id> で個別 override 可能。override 不在時は default にフォールバック。
    • 
            
  • 検索 + キーボード: 検索ボックスでカード名 + 説明文を部分一致フィルタ。/ キーで検索フォーカス、Esc でモーダル閉じる。
    • 
            
  • API: GET /api/v2/attention（rules + tool_status + suggestions）、POST /api/v2/attention/<rid>/snooze、GET /api/v2/attention/thresholds、PUT /api/v2/attention/thresholds/<rid>、DELETE /api/v2/attention/thresholds/<rid>。
